writing-plans Skill

概述

Superpowers 技能，将已批准的规格文档分解为"初级工程师也能执行"的原子级任务清单，每个步骤 2-5 分钟、包含完整代码、精确文件路径、可复现验证命令。

关键内容

  1. 执行者画像假设：
  2. 技术能力合格，但不了解工具链或问题域
  3. 不擅长设计测试

  4. 经验不足、品味糟糕、讨厌写测试的初级工程师也能执行

  5. 首要动作：文件映射：

  6. 先列出哪些文件将被创建/修改及职责
  7. 锁定分解决策
  8. 设计具有清晰边界和良好定义接口的单元

  9. 偏好小文件原则（更能推理清晰、编辑可靠、高内聚性）

  10. 强制 Header： ```markdown # [Feature Name] Implementation Plan

For agentic workers: REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

Goal: [一句话描述构建什么] Architecture: [2-3 句话描述整体方法] Tech Stack: [关键技术/库] ```

  1. 任务粒度：2-5 分钟原则：
  2. Step 1: 写失败测试（包含具体测试代码）
  3. Step 2: 运行确认失败（具体命令+预期输出）
  4. Step 3: 写最少实现代码（完整代码）
  5. Step 4: 运行确认通过（具体命令+预期结果）

  6. Step 5: Commit（具体git命令）

  7. 禁止写法 vs 正确写法：

  8. ❌ "加一个验证函数" → ✅ 提供完整函数代码
  9. ❌ "运行测试" → ✅ pytest tests/specific.py::test_name -v
  10. ❌ "类似地……" → ✅ 每个结构都完整写出
  11. ❌ "参考 X 实现" → ✅ 直接写出实现代码
  12. ❌ "测试应该覆盖边界条件" → ✅ 写出具体的边界条件测试代码

  13. 计划里不能有任何需要执行者自行判断的内容

  14. 计划评审子循环：

  15. 写完计划 → 派遣 plan-document-reviewer 子 Agent 评审
  16. 发现问题 → 同一 Agent 修复（保留上下文）
  17. 最多 5 次迭代，超出 → 升级给人类

  18. 大型计划按 Chunk 分段评审（每段 ≤1000 行）

  19. 存储路径：

  20. docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md

  21. 每个子系统独立一份计划

  22. 执行移交路径：

  23. 有子 Agent 平台（Claude Code、Codex）：使用 subagent-driven-development

  24. 无子 Agent 平台（如 Gemini CLI）：使用 executing-plans

  25. 与 brainstorming 的衔接：

  26. 如果规格文档覆盖多个独立子系统，应拆分为独立计划

  27. 每份计划应独立产出可工作、可测试的软件

  28. 核心原则：

  29. DRY：计划文档本身也要 DRY，重复步骤用引用
  30. YAGNI：严格按规格实现，不加"将来可能用到的"内容
  31. TDD：每个 Task 都以写测试开始（Red → Green → Refactor）
  32. 频繁 Commit：每个 Task 完成后立即 Commit
  33. 精确路径：所有文件路径必须是精确的相对路径
  34. 完整代码：代码必须在计划文档里完整写出
