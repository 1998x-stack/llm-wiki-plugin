Write Tools

概述

Write Tools 是一组分层的文件写入机制，提供多粒度的文件操作能力，包括整文件替换、块级替换和补丁应用。其设计受到 Token 经济学的深刻影响，需要在精确性、效率和成本之间取得平衡。

关键内容

  1. 分层机制：
  2. LLM 输出层 → 解析调度层 → 策略决策层 → 权限校验层 → I/O 执行层 → 验证反馈层

  3. 每一层都有独立的设计权衡，形成了完整的安全与效率保障体系

  4. 多粒度设计与 Token 经济学：

  5. write_file / create_file：整文件替换，适用于新建文件、小文件重构（< 100 行）
  6. str_replace_editor：块级 find-replace，适用于局部修改、函数替换（100~500 行）
  7. apply_patch：unified diff 应用，适用于大文件精确修改（> 500 行）

  8. Token 经济学驱动选择：< 100 行 → full-replace，100~500 行 → str_replace，> 500 行 → patch。500 行文件的 full-replace 约消耗 15K output tokens，成本极高。

  9. 写入策略详解：

  10. Full Replace：最简单但最昂贵，token 消耗与文件大小线性正比，无 patch 失败风险
  11. str_replace：核心武器，具有唯一性约束以确保精确定位。唯一性约束是精心设计的安全锁：强迫 LLM 提供足够的上下文来精确定位目标片段，防止误替换重复代码块。若重复，LLM 必须扩展 old_str 直到唯一

  12. Unified Patch：最节省 token，但 LLM 对行号准确性差，fuzz 不匹配导致 apply 失败率高，工业实践中 Codex 沙箱模式使用，Claude Code 则回避

  13. 安全与权限机制：

  14. 沙箱与权限机制：Codex 使用 OS 级隔离（macOS 的 sandbox-exec/Seatbelt，Linux 的 landlock + seccomp），Claude Code 使用权限门控（路径白名单检查 + 危险路径识别）
  15. Atomic Write：使用 temp → fsync → rename 三步原子写入确保数据一致性，关键细节是 tempfile 必须在同一目录（同一文件系统），否则 os.replace 退化为 copy+delete，失去原子性保证
  16. 唯一性约束：str_replace 要求 old_str 必须唯一，防止误替换重复代码块

  17. Path traversal 检查：确保路径在工作区范围内，防止路径遍历攻击

  18. 工作流程与用户体验：

  19. Approval Gate：写入前计算并显示 unified diff（+ 行绿色，- 行红色，@@ 块青色），支持同步逐步（每次等 y/n）、YOLO 模式（跳过确认）、事后批量（先生成所有 diff 再统一审批）等交互模式
  20. Read-before-Write：str_replace 策略要求先读取文件再修改，因为 old_str 与磁盘内容必须完全一致（空格、换行都算）

  21. 大文件读取策略：行范围读取、Symbol-level 读取（Claude Code 方式，先提取 def/class 骨架再按需读函数体）、Semantic Chunking + RAG（构建代码知识图谱后 retrieve 相关上下文）

  22. 架构对比：

  23. Claude Code：write / str_replace / patch 三件套，权限门控（进程级），同步逐步/YOLO 审批，Symbol-level 大文件读取
  24. Codex CLI：write / patch，OS 沙箱（内核级），suggest/auto-edit/full-auto 模式，行范围读取
  25. Cursor：AST-based diff（最精确方案，直接在语法树层面做 diff，解决行号漂移问题），无沙箱（IDE 内），inline accept/reject
