## 关键观察

### 观察 1：Claude SDK 集成测试揭示的架构问题

`wiki:graph` 在 `claude -p` 非交互模式下触达 `max_turns`（30），根因是 lint 步骤尝试自动修复断链——非交互环境下 Edit 权限被拒，agent 反复重试消耗 turns。**核心洞见：lint/fix 工作流不应嵌入非修复性命令（如 graph 构建）中**。修复方式：lint 步骤改为 report-only，将 auto-fix 职责还给 `wiki:lint`。这是"读写混合 vs 读写分离"设计原则的具体体现。

### 观察 2：两层测试的不同价值

脚本级测试（`scripts/test/run_all.sh`）和 Claude SDK 集成测试（`claude -p`）发现的问题完全不同：
- 脚本级：Python 逻辑 bug（F4 误报、stdout 污染）
- 集成级：命令设计问题（turns 消耗模式、权限交互）

两层测试互补，缺一不可。脚本层快（秒级）、精准；Claude SDK 层慢（分钟级）、揭示 agent 行为。

### 观察 3：lint F4 误报 — regex 模式的边界假设

`lint_wiki.py` F4（empty section）检查使用 `#{1,3}` 匹配 heading，错误地将 h1（页面标题）和有 h3 子节的 h2 父节标记为"空"。根因是 regex 作者隐含假设"所有 heading 后面应有正文"，但 wiki schema 允许 h1=title、h2=parent section 无正文。**洞见：lint 规则 regex 需显式编码 schema 的结构允许列表，而不是依赖"常规情况"。**

### 观察 4：代码审查发现的系统性 Bug 模式（V2.1-V2.3）

12 个 bug 中有两个值得特别记录：

1. **pipe-unaware wikilink regex**（`snapshot_index.py`）：`[[A|B]]` 被解析为 `"A|B"` 字符串。所有使用别名链接的页面被误报为 orphaned。根因是 regex 设计者没有考虑 wikilink 的 `|` 别名语法。**凡解析 wikilink 的地方，必须测试别名格式。**

2. **falsy 0.0 bug**（`build_wiki_pages.py`）：`if conf` 对 `0.0` 为 False，导致置信度为 0 的页面不显示 badge。在 Python 中，数值为 0 的情况必须用 `is not None` 而非 truthy check。

### 观察 5：测试成本与 claude -p 的可行性

4 个集成测试总成本：$0.45 + $0.90 + $0.54 + $0.90 + $1.38 = **$4.17**，总时长约 19 分钟。单次全量集成测试代价较高，适合 milestone 验收而非日常 CI。脚本级测试（秒级、零 API 成本）适合开发循环中频繁运行。

### 观察 6：wiki:graph 命令最终架构

lint 步骤改为只读（`--report-only`）：不执行任何 Edit 操作，仅输出发现的问题。这使得 `wiki:graph` 可以在 non-interactive / CI 环境下安全运行。**设计原则确立：`wiki:graph` = 构建管道（build-only），`wiki:lint` = 修复管道（fix-allowed）。两者职责分离，不可混用。**
