## 关键观察

### 观察 1：Claude Code hooks 协议的普遍误解

三个 hook 脚本都使用 `$CLAUDE_TOOL_ARG_file_path`（一个不存在的环境变量）作为文件路径参数。实际上 Claude Code hooks 通过 **stdin JSON** 传递事件数据（包含 `tool_input.file_path`），而非 shell 环境变量或命令行参数。这导致 hooks 接收到空字符串，路径过滤 `*"wiki/"*` 对空串为 false，hooks 静默退出——**不崩溃、不报错、不记日志**，形成完美的"沉默失败"。

**洞见：沉默失败比崩溃更危险。** 脚本的防御性检查（empty path → exit 0）本意是安全退出非 wiki 文件，却掩盖了输入层面的根本错误。如果脚本在 empty path 时输出一条日志 "WARN: empty file_path"，问题在第一次触发时就会被发现。

### 观察 2：路径匹配的"过宽"陷阱（O22 的又一实例）

`*"wiki/"*` 路径过滤器假设"只有 wiki 内容文件的路径包含 wiki/"，但 `.claude/commands/wiki/maintain.md` 也匹配。这与 O22（lint regex 的边界假设陷阱）是同一类错误：**模式匹配暗含了对路径结构的假设，但没有显式排除已知的例外**。

修复方式：添加 `.claude/` 排除条件。更通用的设计原则：路径匹配规则应该用白名单（`wiki/entities/|wiki/concepts/|wiki/syntheses/|wiki/qa-insights/`）而非黑名单（排除 `.claude/`），但白名单在知识库扩展新子目录时需要同步更新——这是一个 DRY vs 安全性的 tradeoff，当前选择黑名单 + 注释说明理由。

### 观察 3：管道命令的"阶段间合约"设计

wiki:maintain 的设计体现了一种"阶段间合约"思维：
- **reindex** 保证 index.md 和 maps/ 是最新的 → check 可以正确诊断 I1/I2 问题
- **check** 保证有完整的诊断报告 → lint 知道该修什么
- **lint** 保证可修复问题已处理 → build 基于最干净的数据构建
- **build** 保证静态产出与 wiki 状态一致

每个阶段的输出是下个阶段的输入前提。这与 O20（读写分离）互补：O20 说的是"一个命令只做读或写"，这里说的是"多个命令组合时，输出→输入要形成合约"。

### 观察 4：文档同步的系统性——7 处更新的模式

新增一个命令（maintain）需要同步更新 7 处文档：
1. 命令文件本身（.claude/commands/wiki/maintain.md）
2. vault/CLAUDE.md（命令列表 + 快速参考）
3. 根 CLAUDE.md（命令表）
4. README.md（命令表 + vault 结构 commands count）
5. USERGUIDE.md（Tab 补全列表 + 命令详解 + 快速参考卡 + 每周工作流）
6. docs/wiki.md（命令一览 + 目录 + 详解 section + 文件结构）
7. docs/CHANGELOG.md（版本记录）

这种"N 处同步"模式是文档散布（documentation scatter）的典型代价。未来可考虑：(a) 从命令文件 frontmatter 自动生成命令一览表，或 (b) 用 SSOT（Single Source of Truth）原则，只在 docs/wiki.md 维护完整文档，其他文件引用它。

### 观察 5：Consolidate 在知识库早期的局限性

只有 1 天的 episodic 数据时，consolidate 的 Episodic→Semantic 晋升和置信度衰减两个核心步骤都无法执行。系统在初始阶段的主要价值来自 Working→Episodic 压缩和 Journal 模式扫描，而非知识晋升。这意味着**系统的设计价值随时间指数增长**——前几天主要是"录入"，晋升价值在第 3+ 天才开始体现。
