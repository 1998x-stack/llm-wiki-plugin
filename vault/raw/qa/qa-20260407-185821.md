## 问题
Agentic Search 到底是什么

## 回答
根据提供的 Wiki 页面内容，**Agentic Search（代理式搜索）** 是一种模拟资深工程师或专家探索行为的检索范式。它不再依赖静态的向量索引进行一次性匹配，而是通过动态调用工具、多步推理和反思机制，逐步建立对目标领域（如代码库或游戏资产）的“心智模型”，从而找到最准确的信息。

以下是基于文档内容的详细解析：

### 1. 核心定义与理念
*   **模拟人类探索**：Agentic Search 的核心观点是，搜索的最优解并非“寻找最相似片段”，而是像资深工程师一样工作——通过目录浏览、符号追踪、依赖分析等步骤，主动构建上下文 [^agentic-search-design-guide-for-code]。
*   **动态交互 vs. 静态检索**：与传统 RAG（检索增强生成）的“一次性检索”不同，Agentic Search 是一个**交互式循环**。Agent 会根据初步搜索结果调整下一步行动（例如：“这个函数被谁调用了？”），从而解决复杂的多跳推理问题 [^agentic-search-design-guide-for-code]。
*   **工具驱动**：它依赖于一组核心工具（如 `grep`, `read_file`, `list_dir`, LSP 符号导航等）来感知和操作数据，而非仅仅依赖向量数据库 [^agentic-search-design-guide-for-code]。

### 2. 工作原理：ReAct 循环
Agentic Search通常遵循 **Thought-Action-Observation（思考-行动-观察）**循环 [^agentic-search-design-guide-for-code]：
1.  **思考 (Thought)**：LLM 分析当前任务，判断还缺少什么信息。
2.  **行动 (Action)**：选择合适的工具执行操作（如搜索关键词、读取文件）。
3.  **观察 (Observation)**：获取工具返回的结果。
4.  **反思 (Reflection)**：评估信息是否充分。如果不足，规划下一步搜索；如果充足，生成最终答案 [^agentic-search-design-guide-for-code]。

### 3. 与传统 RAG 的关键区别

| 特征 | 传统 RAG (Retrieval-Augmented Generation) | Agentic Search (代理式搜索) |
| :--- | :--- | :--- |
| **检索方式** | 基于向量相似度的一次性召回 (Top-K) | 多步、迭代的主动探索 |
| **上下文理解** | 容易碎片化，缺乏全局逻辑连接 | 通过追踪依赖链和调用图建立完整上下文 |
| **适用场景** static | 静态知识 QA、概念性模糊查询 | 动态探索、Bug 修复、跨文件重构、复杂逻辑追踪 |
| **维护成本** | 高（需维护向量索引、处理增量更新） | 低（直接读取文件系统，无索引滞后问题） [^code-rag-vs-agentic-search-decision-framework] |
| **安全性** | 需将代码向量化存储，存在双重安全风险 | 可直接读取本地文件，无需外部向量库，隐私性更好 [^code-rag-vs-agentic-search-decision-framework] |

### 4. 典型应用场景与选型建议
根据《代码领域 RAG vs Agentic Search 选型决策框架》，以下情况强烈推荐使用 Agentic Search [^code-rag-vs-agentic-search-decision-framework]：
*   **任务类型**：需要多跳推理的任务，如“为什么订单创建后库存没扣减？”（需追踪调用链）、代码生成、Bug 修复。
*   **查询特征**：精确的符号性查询（如已知函数名查找实现），因为 `grep` 或 LSP 比向量检索更准确。
*   **工程约束**：
    *   **代码更新频繁**：Agentic Search 始终读取最新文件，无索引过期问题。
    *   **高安全/隐私要求**：无需将代码上传至向量数据库。
    *   **小型到中型仓库**：在 <50K LOC 的小型仓库中，Agentic Search 效率极高且成本低；在大型仓库中可作为 Hybrid 架构的一部分 [^code-rag-vs-agentic-search-decision-framework]。

### 5. 实际案例
*   **Claude Code**：官方选择 Agentic Search 而非 RAG，理由是本地代码不想建外部向量库（安全），且索引同步麻烦，而现代大模型足以通过自主探索理解代码 [^code-rag-vs-agentic-search-decision-framework]。
*   **游戏资产搜索**：在游戏 Prefab 搜索中，Agentic Search 通过“意图理解 -> 粗排路由（选择类目） -> 细排精选”的工作流，比全量向量检索更节省 Token 且更精准 [^game-prefab-agentic-search-skill-guide]。

### 总结
**Agentic Search 是以 Agent 为骨架，通过工具调用模拟人类认知过程的搜索方法。** 它特别适合处理结构强、逻辑复杂、动态变化的数据（如代码库）。对于大多数中小型项目或复杂推理任务，它是优于传统 RAG 的选择；而在超大规模数据或极低延迟要求的简单问答场景中，则可能需要结合 RAG 形成 Hybrid 混合架构 [^code-rag-vs-agentic-search-decision-framework]。
