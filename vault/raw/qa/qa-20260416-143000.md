## 问题

上下文工程的核心原因只有上下文腐烂吗？还有其他吗，以及这个上下文工程最新的点包含哪些

## 回答

### 一、上下文工程的核心原因：不只是上下文腐烂

上下文工程（Context Engineering）存在**多个核心驱动因素**，上下文腐烂只是其中最显著的一个：

#### 1. 上下文腐烂（Context Rot）— 核心动机
来源：[[上下文腐烂]]、[[Context Engineering]]

Chroma Research 2025 年系统性实验发现：随上下文 token 增加，模型从上下文中准确召回信息的能力**非均匀下降**。这不是崖式崩溃，而是性能梯度下降。所有 18 个主流 LLM 均表现此现象。关键发现：
- 语义相似度越低，退化越快
- 干扰项（相似但不相关的内容）比完全无关内容危害更大
- 信息**如何被呈现**比信息**是否存在**更重要

#### 2. 注意力预算（Attention Budget）— 架构根因
来源：[[注意力预算]]、[[Context Engineering]]

Transformer 的 n² 自注意力机制意味着每个新 token 都从有限"预算"中消耗资源。上下文增长时，每对 token 关系可获得的"有效参数容量"被稀释。这是上下文腐烂的底层架构原因。

#### 3. LLM 无状态性（Statelessness）— 长时任务障碍
来源：[[Context Engineering]]、[[结构化笔记法]]

LLM 天然无状态，每次调用都是独立的。长时任务（数小时/多轮次）需要外部机制维持连贯性，否则每次重启都丢失上下文。

#### 4. Token 成本与经济性
来源：[[渐进式披露 (Progressive Disclosure)]]

上下文窗口中填入无关信息直接浪费 API 调用成本。渐进式披露在 Claude-Mem 案例中实现了约 10 倍的 Token 节省。

#### 5. 信息位置效应（Lost in the Middle）
来源：[[Context Engineering]]

关键信息埋在上下文中间时，模型利用效果显著下降。需要精心设计信息在 prompt 中的位置编排。

#### 6. 经验规律驱动
来源：[[Context Engineering]]

- **Zipf/Pareto**：绝大多数价值来自少数热点上下文
- **Matthew Effect**：早进入上下文的材料会放大后续推理偏向
- **Bradford/Lotka**：少数核心来源覆盖大多数高价值信息

### 二、上下文工程的最新要点（2026）

#### 1. Anthropic 核心定位
来源：[[Context Engineering]]

> "在任意时刻找到**最小化的高信噪比 token 集合**，最大化目标行为的概率。"

核心隐喻：上下文是**有限缓存（Cache）和工作集（Working Set）**，而非日志记录器。

#### 2. 分层记忆架构（L0-L4）
来源：[[分层记忆架构]]、[[Context Engineering]]

将上下文从单一聊天历史升级为五层：
- **L0 Cached Prefix**：系统指令、工具契约（适合前缀缓存）
- **L1 Working Memory**：当前任务最关键信息（token 成本最高）
- **L2 Episodic Memory**：按阶段压缩的结构化 checkpoints
- **L3 Semantic Memory**：按需检索的长期知识层（hybrid retrieve）
- **L4 Raw Archive**：原始数据，只做审计回源

#### 3. 即时上下文检索（Just-in-Time Context）
来源：[[即时上下文检索]]

Agent 不预加载所有数据，而是持有**轻量标识符**（文件路径、URL、查询），运行时按需动态加载。Claude Code 的 glob/grep/Bash 模式是典型实现。元数据本身（路径、文件名、时间戳）就提供决策信号。

#### 4. 长时任务三大技术
来源：[[Context Engineering]]、[[结构化笔记法]]

| 技术 | 最适合场景 |
|------|-----------|
| Compaction（压缩） | 需要频繁往返交互的复杂推理 |
| 结构化笔记法（Agentic Memory） | 有明确里程碑的迭代开发 |
| 多 Agent 架构 | 需要并行探索的复杂研究 |

#### 5. 多 Agent 作为上下文扩展方案
来源：[[多Agent架构]]

子 Agent 通过各自独立上下文窗口并行探索，返回精简摘要（1000-2000 token）而非原始数据。本质是**上下文压缩**：每个子 Agent 可能消耗数万 token 探索，但只返回压缩结果给主 Agent。

#### 6. 检索链路设计
来源：[[Context Engineering]]

```
query understanding → need_retrieval? → hybrid retrieve → contextualize → rerank → diversify → compress → assemble
```

关键环节：need_retrieval 判断、混合检索（dense + BM25 + graph hop）、chunk 补最小必要上下文、反证位（counter-evidence lane）防止 Matthew effect 锚定。

#### 7. 压缩目标：可复用状态，而非摘要
来源：[[Context Engineering]]

压缩应产出四种结构化对象：
- **durable facts**（长期有效事实）
- **decisions**（已做选择和理由）
- **open loops**（未完成事项）
- **source anchors**（原文锚点）

⚠️ 禁止压缩：数字/合同/代码逻辑（会失真）、事实与推断混写（无法审计）。

#### 8. Memory Object 模型
来源：[[Context Engineering]]、[[分层记忆架构]]

上下文管理单元是 memory object 而非 message，包含 id、type、text、source、freshness、salience、reuse_count、confidence、anchors 等结构化字段。

#### 9. Token 预算分配参考
来源：[[Context Engineering]]

| 层 | 比例 |
|---|---|
| Cached Prefix | 10% |
| Working Memory | 15% |
| Recent Turns | 15% |
| Retrieved Evidence | 35% |
| Episodic Summaries | 15% |
| Output Contract | 10% |

#### 10. 评估指标体系
来源：[[Context Engineering]]

Context utilization、Answer quality @ fixed budget、Stale fact rate、Source dominance、Position robustness、Cache hit rate / latency / cost。

#### 11. 候选 Memory 评分函数
来源：[[Context Engineering]]

$$score = 0.35 \cdot relevance + 0.20 \cdot source\_quality + 0.15 \cdot freshness + 0.10 \cdot salience + 0.10 \cdot dependency + 0.10 \cdot novelty - redundancy$$

按 token budget 做 **knapsack 式选择**，而非 top-k 直接截断。

#### 12. 请求路由（Router-first）
来源：[[Context Engineering]]

第一层不是检索，而是路由判断。知识库小于约 200k tokens 且相对稳定时，直接放入 prompt 往往是最简单方案。
