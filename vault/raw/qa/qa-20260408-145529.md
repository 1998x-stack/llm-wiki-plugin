# Q: UrhoX 流程展开

根据提供的 Wiki 页面内容，UrhoX 的项目构建流程（Build Pipeline）是一个从开发、构建到部署的完整生命周期。以下是该流程的详细展开：

### 1. 流程总览 (三个阶段)

UrhoX 构建流程分为三个核心阶段，旨在实现内容寻址存储、多版本共存及前后端资源分离。

*   **开发阶段 (Development)**：
    *   开发者编辑源配置文件（`project.json`, `resources.json`, `settings.json`）。
    *   管理资源文件及其元数据（`.meta` 文件）。
*   **构建阶段 (Build)**：
    *   构建工具扫描本地资源。
    *   生成内容寻址的文件名（包含 Hash）。
    *   计算资源哈希值。
    *   生成版本化的 Manifest 清单（Client/Server 分离）。
*   **部署阶段 (Deploy)**：
    *   将构建产物上传至 CDN。
    *   支持多版本共存（未变更资源不重复上传）。
    *   支持快速回滚。

---

### 2. 详细构建步骤 (Pipeline Architecture)

构建过程由以下具体的 Step 组成，按顺序执行：

1.  **InitBuildDirStep**: 初始化构建目录，清理旧文件或准备临时空间。
2.  **LoadConfigStep**: 加载核心配置文件 (`project.json`, `resources.json`, `settings.json`)。
3.  **ScanLocalResourcesStep**: 扫描项目目录下的所有资源文件，识别新增、修改或删除的资源。
4.  **AssetsCookingStep** (资产烘焙):
    *   **纹理压缩**: 根据目标平台生成特定的压缩格式（iOS/macOS/Android 使用 ASTC，Windows 使用 BC7）。
    *   **XML 内嵌**: 将纹理的 XML 配置清理并内嵌到 KTX 文件元数据中，减少 HTTP 请求。
5.  **GenerateManifestsStep**:
    *   生成内容寻址文件名 `{uuid}-{hash}.{ext}`。
    *   生成 `manifest-{hash}.json`（包含资源列表、依赖、平台特定信息）。
    *   生成 `version.json`（指向当前版本的 Client/Server Manifest Hash）。
6.  **CopyAssetsStep**: 将处理后的最终资源文件复制到输出目录。

---

### 3. 关键机制详解

#### A. 内容寻址 (Content Addressing)
*   **命名规则**: 资源文件重命名为 `{uuid}-{hash}.{ext}`。
*   **优势**:
    *   相同内容拥有相同文件名，利于 CDN 缓存命中。
    *   不同版本间未变更的资源无需重新下载或上传。
    *   物理文件在 `assets/` 目录下跨版本共享。

#### B. 前后端分离 (Client/Server Separation)
*   **标识**: 通过 `.meta` 文件中的 `c_or_s` 字段控制：
    *   `c`: 仅客户端 (Client)。
    *   `s`: 仅服务端 (Server)。
    *   `cs`: 两者通用。
*   **结果**: 构建后生成独立的 Client Manifest 和 Server Manifest，但底层物理资源文件是共享的。

#### C. 资源来源与解析
构建工具根据 `settings.json` 中的 `sources` 配置解析资源：
*   **有 Tag 时**: 请求 `{base_url}/{tag}.json` 获取版本信息。
*   **有 Version 时**: 请求 `{base_url}{version}/version.json`。
*   **直接访问**: 拼接为 `{base_url}assets/{uuid}-{hash}.{ext}`。

#### D. UUID 管理与 Meta 文件
*   **UUID 生成**: 在资源导入时生成 24 字符 Base64 UUID，存储在 `.meta` 文件中。
*   **Meta 文件职责**: 仅存储元数据（UUID, group, c_or_s），**不参与运行时**。
*   **构建处理**: 构建时提取 `.meta` 信息合并到 Manifest 中，随后**剔除**所有 `.meta` 文件，不上传至 CDN。

---

### 4. 构建产物结构

构建完成后，输出目录包含以下关键文件：

1.  **`version.json`**: 版本索引文件。
    ```json
    {
      "format": 1,
      "version": "1.2.5",
      "client": "a1b2c3d4", // Client Manifest 的 Hash
      "server": "e5f6g7h8"  // Server Manifest 的 Hash
    }
    ```
2.  **`manifest-{hash}.json`**: 资源清单。
    *   包含 `files` 列表（UUID, Hash, Ext, Size, Groups, Refs 等）。
    *   包含 `metadata` 统计信息。
3.  **`assets/` 目录**:
    *   存放重命名后的资源文件：`{uuid}-{hash}.{ext}`。
    *   可能包含短期保留的配置文件 `{uuid}.xml`（长期方案将内嵌至 KTX2）。

---

### 5. 常用命令与工作流

开发者通过以下 Python 脚本工具 interact 与构建流程：

*   **生成/补充 Meta 文件**:
    ```bash
    python tools/project-tools/meta_generator.py --project ./MyGame
    ```
*   **执行完整构建**:
    ```bash
    python tools/project-tools/project_builder.py --project ./MyGame --version 1.2.5
    ```
*   **多平台构建** (生成所有压缩纹理):
    ```bash
    python tools/project-tools/project_builder.py --project ./MyGame --platform all
    ```
*   **上传至 CDN** (精准上传策略):
    ```bash
    python tools/project-tools/project_uploader.py --project . --host <cdn_host> --token <token>
    ```
    *   **上传策略**:
        *   **Version 目录**: 全量上传 (`version.json`, manifests)。
        *   **Assets 目录**: 仅上传 Manifest 中引用的**新**资源（基于 Hash 比对）。
        *   **根目录**: 更新 `latest.json` 及 Tags 索引。

### 6. 运行时引用

*   引擎启动时加载 `version.json` 获取当前版本的 Manifest Hash。
*   加载对应的 `manifest-{hash}.json`。
*   代码中通过虚拟路径或 UUID 引用资源（如 `uuid://...` 或 `fs_path`），Manifest 负责将其映射到实际的 Content-Addressed 文件名进行加载。
