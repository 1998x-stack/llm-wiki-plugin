# Q: Claude CLI 核心选择了哪些工具，为什么不选择其他的工具

根据提供的 Wiki 页面内容，**Claude Code**（文中 referred to as Claude CLI/Code）在核心工具选择上遵循了“最少业务逻辑原则”和“模型友好”的设计哲学。以下是其核心选择的工具及其选择原因，以及未选择其他方案的理由：

### 1. 核心选择的四大能力基元 (Capability Primitives)

Claude Code 没有为每个具体任务编写专用集成，而是选择了四个通用的**能力基元**来覆盖所有开发场景：

| 基元 | 代表工具/实现 | 选择原因 (Why Chosen) |
| :--- | :--- | :--- |
| **Read (读)** | `View`, `LS`, `Glob`, `GrepTool` | **精确与廉价**：对于代码库或历史记录的精确查询，传统的 `grep` 比向量检索更准确、更廉价。避免为了“AI 感”而滥用 RAG。 |
| **Write (写)** | `Edit`, `Write/Replace`, `Create` | **原子性与安全性**：支持生成 Patch、全文替换和新建文件，配合严格的写入纪律（Strict Write Discipline）防止索引脏数据。 |
| **Execute (执行)** | **Bash (持久 Shell 会话)** | **通用适配器**：Bash 是通用适配器。通过提供一个持久的、有状态的 Bash 会话，Claude Code 能够使用任何人类开发者会用的 CLI 工具（如 `git`, `npm`, `docker`），**无需为每个工具编写专用的 API 集成代码**。 |
| **Connect (连接)** | **MCP (Model Context Protocol)** | **标准化与解耦**：用于连接 GitHub, Database, Sentry, Slack 等外部服务。MCP 协议标准化了外部服务接入，解耦了工具与模型。 |

### 2. 关键技术栈选型及理由

| 组件 | 选择的技术 | 为什么选择它 (Pros) | 为什么不选其他 (Cons of Alternatives) |
| :--- | :--- | :--- | :--- |
| **编程语言** | **TypeScript** | **模型自编率高**：LLM 非常擅长生成和理解 TypeScript。**90%** 的 Claude Code 代码由 Claude Code 自己编写，证明了该栈对 AI 代理的高度友好性。 | **Rust/C++**：虽然性能更好，但 LLM 生成复杂系统级代码的错误率较高，迭代速度慢。TypeScript 类型安全且生态丰富，适合快速迭代。 |
| **UI 框架** | **React + Ink** | **声明式终端 UI**：结构清晰，模型易于理解和生成。Ink 允许使用 React 组件构建终端界面。 | **Curses/NCurses**：命令式且状态管理复杂，模型难以正确生成和维护复杂的 TUI 逻辑。 |
| **布局引擎** | **Yoga** | **跨平台约束布局**：Meta 开源，完美适配任意终端宽度，确保 UI 在不同尺寸终端下的一致性。 | **手动计算坐标**：极易出错，且难以适应动态变化的终端窗口大小。 |
| **构建工具** | **Bun** | **极速**：比 Webpack/Vite 显著更快，提升开发体验和迭代速度。 | **Webpack/Vite**：启动和构建速度相对较慢，影响“极速迭代”的目标。 |
| **记忆/索引** | **Grep / 指针式索引** | **低成本高精度**：`MEMORY.md` 采用精简索引，配合 `grep` 进行精确查找。 | **向量数据库 (Vector DB/RAG)**：对于代码这种需要精确匹配的场景，向量搜索往往不够准确且成本高昂（Token 消耗大）。Wiki 明确指出：“**Grep > 向量搜索**”。 |

### 3. 核心设计哲学对工具选择的影响

*   **最少业务逻辑原则 (Minimal Business Logic)**：
    *   **选择**：将智能保留在模型中，客户端仅负责 UI 渲染和工具路由。
    *   **不选**：复杂的硬编码状态机或业务逻辑层。
    *   **理由**：调试更容易（复现 Prompt 即可），测试更快速（只需验证工具接口），迭代更迅速（修改 Tool Description 比重构代码快）。

*   **成本驱动架构 (Cost-Driven Architecture)**：
    *   **选择**：Prompt Cache 优化、指针式索引、AutoCompact 熔断。
    *   **不选**：全量数据加载、无限制的上下文膨胀。
    *   **理由**：Token 成本是 AI Agent 的“CPU 时间”。架构设计必须将成本控制内嵌于数据流中。例如，避免全量加载记忆文件，而是通过 `MEMORY.md` 索引按需加载。

*   **Prompt 是最灵活的算法**：
    *   **选择**：Coordinator Mode 的核心调度逻辑是一段精心设计的系统提示词（Prompt）。
    *   **不选**：硬编码的状态机或规则引擎。
    *   **理由**：自然语言描述的行为规范比代码实现的规则更灵活、更易维护。改变行为只需修改 Prompt 而非重新编译部署代码。

### 总结

Claude Code 的核心工具选择围绕 **“模型友好”**、**“成本效率”** 和 **“通用性”** 展开：

1.  **TypeScript/React/Ink**：因为 LLM 擅长生成这些代码，实现了 90% 的代码自生率。
2.  **Bash**：作为通用执行层，避免了为无数 CLI 工具编写专用集成的巨大工程开销。
3.  **Grep/MCP**：取代了昂贵的向量搜索和定制化的 API 集成，提供了更准确、更标准、更廉价的连接方式。
4.  **Prompt 驱动调度**：取代了硬编码逻辑，提供了极高的灵活性和可维护性。

这些选择共同构成了一个高效、低成本且易于 AI 自主维护和迭代的编码 Agent 系统。
