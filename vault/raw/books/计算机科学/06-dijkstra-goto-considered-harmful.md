# 论文分析：Go To Statement Considered Harmful

> Edsger W. Dijkstra 的这封不到两页的编辑来信，是计算机科学史上影响最深远的短文之一。它不仅终结了一种编程习惯，更开启了一场关于"程序应该如何书写"的思想革命。

### 历史背景

1968 年，计算机科学正处于一个关键的转折点。软件危机（software crisis）的阴影笼罩着整个行业——项目频繁超期、严重超预算、交付的软件充满缺陷。同年 10 月，NATO 软件工程会议在联邦德国加米施-帕滕基兴召开，"软件工程"（software engineering）这个术语正是在那次会议上被正式提出的。

当时的编程实践几乎毫无章法可言。主流编程语言——FORTRAN、COBOL、ALGOL、汇编语言——都大量依赖 `goto` 语句来实现程序的控制流。程序员们习惯于在代码中随意跳转：从第 10 行跳到第 150 行，再从第 150 行跳到第 30 行，然后在某个条件下跳到第 200 行。这种编程风格产生了被后人称为"意大利面条式代码"（spaghetti code）的混乱产物——程序的控制流像一团纠缠不清的面条，任何人（包括原作者自己）都几乎无法理解程序在运行时到底在做什么。

Dijkstra 当时已经在荷兰埃因霍芬理工大学（Eindhoven University of Technology）担任数学教授，同时在一家名为 Mathematisch Centrum 的研究机构工作。他深入思考着一个根本性的问题：如何让程序的正确性可以被理性地论证，而不是仅仅依赖测试和运气？在他看来，`goto` 语句是这个目标的最大障碍。

值得注意的是，Dijkstra 写这封信时并非无名小卒。他已经发明了以他名字命名的最短路径算法（1956 年），参与了 ALGOL 60 语言的设计，开发了首个 ALGOL 60 编译器，并提出了信号量（semaphore）概念来解决并发编程中的同步问题。他的声望使得这封信获得了广泛的关注——尽管其中相当一部分关注是愤怒的反驳。

---

## 2. 一句话总结

**Dijkstra 论证了 `goto` 语句从根本上破坏了程序的逻辑结构可理解性，使程序员无法在静态的程序文本与动态的执行过程之间建立可靠的心智对应，主张程序应当仅使用顺序（sequence）、选择（selection）和循环（iteration）三种控制结构来组织，从而为结构化编程运动奠定了思想基石。**

## 3. 当时的时代问题

### 3.1 软件危机：复杂度超越了人的认知极限

1960 年代末，计算机硬件的能力飞速增长，但软件开发的能力却远远跟不上。人们开始意识到，编写大型软件系统与编写小程序之间存在质的差异——不仅仅是"多写几行代码"那么简单。当程序规模从几百行增长到几万行甚至几十万行时，人类理解和管理复杂度的能力就会被远远超越。

具体表现为：

- **项目严重超期**：IBM 的 OS/360 操作系统项目最终投入了 5000 人年的工作量，远超最初预估，项目负责人 Fred Brooks 后来将这段经历写成了经典著作《人月神话》。
- **预算大幅超支**：软件项目的实际成本常常是预算的数倍乃至数十倍。
- **质量低下**：交付的软件充满了 bug，可靠性极差。
- **维护困难**：修改一个 bug 往往会引入更多新 bug，因为没有人真正理解程序在做什么。

### 3.2 "意大利面条代码"：goto 的结构性恶果

`goto` 语句在当时是编程的基本构建块。一段典型的 FORTRAN 程序可能包含数十个甚至上百个 `goto` 跳转，控制流在代码中蛛网般交织。考虑以下伪代码片段：

```
10  IF X > 0 GOTO 50
20  Y = Y + 1
30  IF Y > 10 GOTO 70
40  GOTO 10
50  X = X - 1
60  GOTO 30
70  IF Z = 0 GOTO 20
80  PRINT RESULT
90  GOTO 10
```

仅仅 9 行代码就包含了 5 个 `goto` 跳转，控制流在行号之间来回穿梭。试想一下，当这样的代码扩展到数千行时，理解程序逻辑将变成一项何等艰巨的任务。程序员们不得不用铅笔在打印出的代码清单上画线来追踪控制流——这些线条交叉缠绕，看起来就像一盘意大利面条，"spaghetti code"这个词由此而来。

### 3.3 程序正确性：缺乏系统的验证方法

在那个时代，验证程序正确性的唯一方法就是测试——反复运行程序，输入各种数据，观察输出是否符合预期。但正如 Dijkstra 后来的那句名言所指出的：

> "测试只能证明 bug 的存在，不能证明 bug 的不存在。"
> （"Testing shows the presence, not the absence of bugs."）

人们渴望有一种方法能够像数学证明一样，从程序的文本出发，推导出程序在所有可能输入下的行为都是正确的。但 `goto` 使这种推理成为了不可能的任务。

### 3.4 编程作为"技艺"而非"工程"

当时的编程更像是一种个人技艺，而非工程学科。好的程序员和差的程序员之间的生产力差距可以达到 10 倍甚至更多。编程风格完全取决于个人偏好，没有公认的"最佳实践"。这种状况在小规模编程中或许尚可接受，但在大型软件项目中则是灾难性的。

### 3.5 理论铺垫：Bohm-Jacopini 定理

在 Dijkstra 发表这封信的两年前（1966 年），意大利数学家 Corrado Bohm 和 Giuseppe Jacopini 发表了一个重要的理论结果：任何使用 `goto` 语句的程序，都可以用仅包含**顺序执行**、**条件选择**（if-then-else）和**循环**（while-do）三种结构的等价程序来替换。这个定理从数学上证明了 `goto` 在表达能力上是冗余的——你不需要它就能写出任何程序。

Bohm-Jacopini 定理为 Dijkstra 的论证提供了坚实的理论基础：既然 `goto` 不是必需的，而且它还带来了严重的可理解性问题，那么我们就有充分的理由将它从编程实践中移除。

## 4. 核心问题定义

Dijkstra 在这封信中提出的核心问题，可以用一个精炼的问题来表述：

> **程序员如何在静态的程序文本（program text）和动态的执行过程（program execution）之间建立清晰的心智对应关系（mental correspondence）？**

### 4.1 静态文本与动态过程的鸿沟

程序有两种存在方式：一种是写在纸上（或显示在屏幕上）的**文本**，另一种是在计算机中实际**运行**的过程。程序员编写的是文本，但程序真正做的事情发生在运行时。

这两者之间存在着本质性的差异：

- **程序文本**是静态的、空间性的——它同时呈现在那里，你可以上下翻阅、前后对照。
- **程序执行**是动态的、时间性的——它按照时间顺序一步一步展开，每一步都可能改变程序的状态。

程序员的核心能力在于：阅读静态的文本，在脑中模拟动态的执行，从而理解程序的行为、发现潜在的错误、验证程序的正确性。Dijkstra 认为，编程语言和编程风格的首要设计目标，应该是**尽可能缩小这种静态与动态之间的鸿沟**。

### 4.2 goto 如何摧毁了这种对应关系

在没有 `goto` 的程序中，从程序文本的位置可以相对容易地推断执行的状态。如果你看到执行点在一个循环体内，你知道循环条件曾经为真；如果你看到执行点在一个 `if` 分支内，你知道对应的条件被满足了。程序的文本结构映射了执行的逻辑结构。

但 `goto` 打破了这一切。一个 `goto` 语句可以把执行点抛到代码中的任何位置。更糟糕的是，一个位置可能被多个不同的 `goto` 语句所指向——当执行到达那个位置时，你根本不知道它是从哪里来的、经过了什么路径、程序处于什么状态。"我在哪里"这个简单的问题，在充斥着 `goto` 的程序中变成了一个几乎无法回答的难题。

### 4.3 程序质量与可理解性的等价

Dijkstra 隐含地提出了一个深刻的等式：

**程序的质量 = 程序员理解"程序在任意时刻处于什么状态"的能力**

如果程序员能够清楚地推理出程序在每个执行点的状态，那么他就能验证程序的正确性、预见可能的错误、安全地修改程序。反之，如果程序的控制流混乱到无法追踪，那么程序的正确性就只能靠运气——而运气不是工程师应该依赖的东西。

## 5. 核心方法与思想

### 5.1 坐标系论证：如何描述"程序在哪里"

Dijkstra 的论证方法极具独创性。他没有从编程实践的角度列举 `goto` 导致的具体问题，而是从一个更加抽象和根本的角度切入：**我们需要怎样的"坐标系"来描述程序的执行位置？**

这个类比来自物理学。在物理学中，我们用坐标系来描述物体在空间中的位置——给出三个数（x, y, z），我们就精确地知道物体在哪里。Dijkstra 追问的是：在程序执行的过程中，我们需要什么样的"坐标"来描述"程序现在执行到了哪里"？

他逐一分析了不同控制结构所需的坐标复杂度：

#### 纯顺序执行

对于一段没有任何分支和循环的代码，描述执行位置只需要一个数字——**当前执行到第几行**（文本索引，textual index）。这是最简单的情况。

```
语句 1    ← 文本索引 = 1
语句 2    ← 文本索引 = 2
语句 3    ← 文本索引 = 3
```

一个数字就足以完整描述程序的执行进度。

#### 过程调用（嵌套的子程序）

当程序包含过程调用时，情况稍微复杂一些。假设主程序调用了过程 A，过程 A 又调用了过程 B，那么描述执行位置需要一个**栈**（stack）：

```
主程序第 5 行 → 调用 A
  过程 A 第 3 行 → 调用 B
    过程 B 第 7 行    ← 当前执行点
```

此时的"坐标"是一个序列：`(主程序第5行, 过程A第3行, 过程B第7行)`。这是一个有限深度的栈结构，虽然比纯顺序执行复杂，但仍然是可管理的——栈的深度等于嵌套调用的层数。

#### 循环

加入循环后，仅靠文本索引就不够了。考虑以下代码：

```
while 条件 do
    语句 A    ← 我在这里，但这是第几次循环？
end
```

要完整描述执行状态，我们需要知道：(1) 当前在循环体的第几行；(2) 这是循环的第几次迭代。因此坐标变成了**文本索引 + 循环计数器**的组合。对于嵌套循环，每层循环都需要一个计数器。

#### goto 语句

现在考虑 `goto`。一个 `goto` 可以从代码中的任何位置跳到任何其他位置。更严重的是，一个标签可能被多个 `goto` 语句所指向。这意味着：

- 当执行到达某个标签时，你不知道它是从哪里跳来的。
- 程序可能经历了完全不同的执行路径到达同一个点。
- 没有任何规则的坐标系可以简洁地描述执行位置——你可能需要记录完整的执行历史才能理解当前状态。

Dijkstra 的结论是：**goto 语句使得"程序进度坐标"从一个简洁、有结构的描述退化为一个几乎任意复杂的描述。** 而如果我们连"程序在哪里"都说不清楚，又怎么能推理"程序在做什么"呢？

### 5.2 "思维差距"论证：可管理性的边界

Dijkstra 进一步论证了一个关于人类认知的观点。他指出，人类大脑的工作记忆容量是有限的——我们一次只能追踪有限数量的变量和状态。好的程序结构应该**适配人脑的认知能力**，而不是与之对抗。

这个论证的核心逻辑链条如下：

1. **程序文本是静态的、空间性的**——它像一幅地图，所有部分同时存在。
2. **程序执行是动态的、时间性的**——它像一段旅程，按时间顺序展开。
3. **程序员需要在地图与旅程之间建立对应关系**——看着地图推断旅程。
4. **好的控制结构让这种对应关系清晰、局部、可层次化分解**——就像一张标注了主干道和分支的地图。
5. **goto 打破了所有层次结构**，使对应关系变成了一张由任意箭头连接的混乱网络——就像一张所有道路都可以通向任何地方的地图。

Dijkstra 用"智力上无法管理的"（intellectually unmanageable）来形容含有大量 `goto` 的程序。这不是说某些天才程序员无法理解它们——而是说这种理解的成本如此之高，以至于在工程实践中是不可接受的。

### 5.3 替代方案：三种基本控制结构

Dijkstra 主张，程序应当仅使用以下控制结构：

**顺序执行（Sequencing）**：语句按照书写顺序依次执行。

```
语句 A
语句 B    ← A 完成后执行 B
语句 C    ← B 完成后执行 C
```

**条件选择（Selection）**：根据条件执行不同的分支。

```
if 条件 then
    分支 A
else
    分支 B
end
```

**循环（Iteration）**：在条件满足时重复执行一段代码。

```
while 条件 do
    循环体
end
```

**过程调用（Procedure Call）**：将一段逻辑封装为可命名的子程序。

```
function 过程名()
    过程体
end
```

这四种结构共享一个关键特性：**单一入口、单一出口**（single-entry, single-exit）。每种结构都有一个明确的开始点和一个明确的结束点。控制流从入口进入，经过结构内部的处理，从出口离开。这意味着每种结构都可以被视为一个"黑箱"——从外部看，它就像一条简单的语句。

这种"可嵌套、可层次化"的特性使得程序可以像散文一样被从上到下、从外到内地阅读和理解。每个层次的细节都被封装在对应的结构中，不会泄漏到外层。

根据 Bohm-Jacopini 定理，这三种结构（加上过程调用这种组织手段）在表达能力上是**图灵完备**的——任何可计算的问题都可以用它们来解决。`goto` 在表达能力上是完全冗余的。

## 6. 创新点

### 6.1 首次系统挑战"不言自明"的编程构造

在 Dijkstra 之前，`goto` 是编程语言中最"自然"的控制结构。汇编语言的跳转指令（JMP、BNE 等）直接对应硬件行为，`goto` 不过是高级语言对跳转指令的抽象。几乎所有程序员都把它视为理所当然——就像呼吸空气一样自然。

Dijkstra 的革命性在于：他第一次严肃地质疑了一种被广泛使用、深入人心的编程构造，并给出了系统的论证。这需要非凡的智识勇气——他不仅要面对来自工业界和学术界的激烈反对，还要克服一种深层的思维惯性：既然机器是用跳转指令工作的，为什么程序员不应该用 `goto`？

### 6.2 编程目标的范式转移

在 Dijkstra 之前，编程的首要目标是**"让程序能够正确运行"**。Dijkstra 将目标提升到了一个新的层次：**"让程序的正确性能够被人类理性地推理和验证"**。

这是一个根本性的范式转移。前一个目标关注的是结果——程序是否产生了正确的输出；后一个目标关注的是过程——我们是否有理由相信程序总是会产生正确的输出。这个转变将编程从一种试错的手艺提升为一种可推理的智识活动。

### 6.3 "程序可理解性"作为设计标准

Dijkstra 实质上引入了一个全新的编程语言和编程风格的评价标准：**程序的可理解性**（program comprehensibility）。在此之前，编程语言的设计主要关注表达能力（能否表达各种算法？）、执行效率（生成的代码快不快？）和实现简便性（编译器好不好写？）。

Dijkstra 论证的核心含义是：一种编程构造即使功能强大、执行高效，如果它损害了程序的可理解性，那么它的代价就大于收益。这个标准后来深刻影响了编程语言设计——从 Pascal 到 Java 再到 Rust，"让程序员不容易犯错"逐渐成为了语言设计的核心考量之一。

### 6.4 "Considered Harmful" 文体的开创

Dijkstra 这封信——更确切地说，是 Niklaus Wirth 为其拟定的标题——开创了一种独特的学术批评文体。"X Considered Harmful" 后来成为计算机科学领域（乃至更广泛的技术领域）中最被频繁模仿的标题模式。

仅列举几个著名的后续作品：

- **"GOTO Considered Harmful" Considered Harmful**（Frank Rubin, 1987）——讽刺对 `goto` 的过度恐惧
- **"Considered Harmful" Essays Considered Harmful**（Eric A. Meyer, 2002）——对这种标题模式本身的反思
- **"Null References: The Billion Dollar Mistake"**（Tony Hoare, 2009）——虽然标题不同，但精神一脉相承

这种文体的力量在于：它用一个尖锐的判断（"有害"）来引发讨论，迫使人们认真审视那些被习以为常的实践。

### 6.5 编程方法论的科学化

在 Dijkstra 之前，关于"怎样编程才是好的"这类问题，更多地被视为个人品味和偏好的领域——有人喜欢短变量名，有人喜欢长变量名；有人喜欢密集的代码，有人喜欢稀疏的布局。这些讨论缺乏客观的评判标准。

Dijkstra 将编程方法论从个人偏好提升为可以用逻辑论证来讨论的科学问题。他不是在说"我不喜欢 goto"，而是在论证"goto 使程序的正确性推理在结构上变得不可管理"。这种论证方式为后来的软件工程研究奠定了方法论的基础。

## 7. 论证结果

### 7.1 论证的性质与结构

需要明确的是，这不是一篇包含实验数据的实证研究论文，而是一篇**纯逻辑论证**。Dijkstra 没有做对照实验、没有统计分析、没有性能测量。他的论证完全依赖于逻辑推理和概念分析。

论证的核心结构可以概括为一个三段论：

1. **大前提**：程序的正确性推理要求程序员能够清晰地理解程序在每个执行点的状态（即建立文本-执行对应关系）。
2. **小前提**：`goto` 语句使得这种状态推理变得任意复杂——`goto` 引入的非结构化跳转破坏了任何有序的"程序进度坐标系"。
3. **结论**：因此，应当从编程实践中消除 `goto`，转而使用保持清晰文本-执行对应关系的结构化控制流。

### 7.2 引发的学术争论

这封信发表后立即引发了计算机科学界最激烈的论战之一。

**支持者阵营**认为：

- `goto` 应当被彻底禁止，不留任何例外。
- 结构化编程是编写可靠软件的唯一正确方式。
- C.A.R. Hoare（后来因快速排序和 CSP 获得图灵奖）积极支持 Dijkstra 的立场，并在此基础上发展了公理化程序验证方法（Hoare 逻辑）。

**反对者阵营**认为：

- 在某些场景下，`goto` 比结构化替代方案更清晰、更高效。
- 机械地消除 `goto` 可能导致代码更加复杂（例如引入额外的布尔标志变量）。
- Frank Rubin 在 1987 年发表的 "'GOTO Considered Harmful' Considered Harmful" 中列举了 `goto` 更优的具体案例。

**折中分析**来自 Donald Knuth。这位《计算机程序设计艺术》的作者在 1974 年发表了长达 47 页的详尽论文 "Structured Programming with go to Statements"，对 `goto` 问题进行了迄今为止最全面、最细致的分析。Knuth 的结论是：

> "在某些情况下，我主张消除 goto 语句；在另一些情况下，我主张引入它们。"

Knuth 列举了若干 `goto` 仍然有价值的场景：跳出多层嵌套循环、有限状态机的实现、某些对性能有极端要求的算法优化。但他同时承认 Dijkstra 的核心论点是正确的：大多数情况下，结构化控制流是更好的选择。

### 7.3 工业界的渐进接受

学术争论虽然激烈，但工业实践的变化却是渐进而深远的：

- **1970 年代**：Pascal 语言（由 Wirth 设计）虽然保留了 `goto`，但强烈不鼓励使用，成为教学中结构化编程的首选语言。
- **1970--80 年代**：C 语言保留了 `goto`，但实践中 `goto` 的使用大幅减少，主要限于错误处理模式。
- **1980--90 年代**：Ada、Modula-2 等语言进一步限制了 `goto` 的使用范围。
- **1995 年**：Java 语言将 `goto` 保留为关键字但禁止使用——这是对这场争论的最终表态。
- **2000 年代至今**：Python、Ruby、Swift、Kotlin、Rust 等现代语言要么完全没有 `goto`，要么仅提供极其受限的跳转机制。

## 8. 局限性

### 8.1 形式上的局限：信的篇幅

作为一封编辑来信，全文不到两页。Dijkstra 没有空间展开充分的论证、给出详细的例子、讨论可能的反对意见。许多批评者指出，这封信更像是一个"宣言"（manifesto）而非严格的"论证"（argument）。如果 Dijkstra 将其扩展为一篇完整的论文，配上具体的代码对比和更严密的推理，可能会减少很多不必要的争议。

### 8.2 实践上的局限：goto 的合理用例

在某些特定场景下，`goto` 确实是最清晰、最简洁的解决方案：

**错误清理模式（C 语言）**：在 C 语言中，由于缺乏异常处理机制，`goto` 常被用于集中处理资源清理：

```c
int function() {
    resource_a = acquire_a();
    if (!resource_a) goto cleanup_none;
    
    resource_b = acquire_b();
    if (!resource_b) goto cleanup_a;
    
    resource_c = acquire_c();
    if (!resource_c) goto cleanup_b;
    
    // 使用资源...
    result = SUCCESS;

cleanup_b:
    release(resource_b);
cleanup_a:
    release(resource_a);
cleanup_none:
    return result;
}
```

Linux 内核代码中大量使用这种模式，Linus Torvalds 本人多次为 `goto` 在这种场景下的使用辩护。如果不用 `goto`，替代方案是深层嵌套的 `if-else`，反而更难阅读。

**跳出多层循环**：在没有 labeled break 的语言中，`goto` 是跳出多层嵌套循环最直接的方式：

```c
for (i = 0; i < n; i++)
    for (j = 0; j < m; j++)
        if (found(i, j))
            goto done;
done:
    // 处理结果
```

**有限状态机**：某些有限状态机的实现中，用 `goto` 在状态之间跳转比用 `switch-case` 更高效、更直观。

### 8.3 理论上的局限：认知论证的模糊性

Dijkstra 的核心论证依赖于"人的认知能力有限"和"goto 使推理变得困难"。但他没有给出精确的认知科学依据来量化这种困难程度。具体而言：

- "困难"是多困难？是否存在一个阈值，低于这个阈值的 `goto` 使用是可以接受的？
- 不同类型的 `goto`（前向跳转 vs 后向跳转、局部跳转 vs 远距离跳转）对可理解性的影响是否不同？
- 是否可以通过工具辅助（如 IDE 的跳转可视化）来缓解 `goto` 对可理解性的损害？

这些问题在 Dijkstra 的信中都没有得到回答。

### 8.4 哲学上的局限：绝对主义的风险

Dijkstra 的措辞（"considered harmful"）和立场（主张完全消除 `goto`）带有明显的绝对主义色彩。这种绝对立场虽然在传播上更有力量，但也可能导致另一种教条主义——不分场合地禁止 `goto`，即使在少数场景下 `goto` 确实是更好的选择。

Dijkstra 后来也有所反思。在他的 EWD 手稿和后续著作中，他更多地强调的是**结构化编程的精神**（让程序可以被人理解和推理），而非**字面上禁止 goto** 这一条具体规则。

### 8.5 范围上的局限：未触及更深层的问题

结构化编程解决了"控制流混乱"的问题，但软件工程中的挑战远不止于此。数据结构的复杂性、模块之间的耦合、需求的变化、团队协作的摩擦——这些问题都不在 Dijkstra 这封信的讨论范围之内。Dijkstra 自己在后来的工作中也不断拓展思考的范围，涉及程序的层次化设计、关注点分离、形式化规范等更广泛的主题。

## 9. 历史意义

### 9.1 结构化编程运动的宣言书

如果要为结构化编程运动选定一个标志性的起点文献，这封信当之无愧。虽然 Bohm-Jacopini 的定理在先，Dijkstra 自己此前也有相关思考，但正是这封信以其尖锐的标题和清晰的立场引爆了整个讨论。

在这封信之后，结构化编程从一个学术概念逐渐演变为工业实践标准。1972 年，Dijkstra、Hoare 和 Ole-Johan Dahl 合著了《Structured Programming》一书，系统阐述了结构化编程的理论和方法。这本书成为了结构化编程运动的"圣经"。

### 9.2 对编程语言设计的深远影响

这封信直接或间接地影响了此后半个世纪编程语言的设计决策：

| 语言 | 年份 | 对 goto 的态度 |
|------|------|-------------|
| Pascal | 1970 | 保留但不鼓励使用 |
| C | 1972 | 保留，实践中仅限于特定模式 |
| Ada | 1983 | 保留但严格限制 |
| C++ | 1985 | 继承自 C，实践中极少使用 |
| Java | 1995 | 作为保留字但禁止使用 |
| Python | 1991 | 完全没有 goto |
| Ruby | 1995 | 完全没有 goto |
| C# | 2000 | 保留，但有严格限制 |
| Go | 2009 | 保留，但社区文化不鼓励 |
| Rust | 2015 | 没有 goto，用 labeled break 替代部分场景 |
| Kotlin | 2016 | 没有 goto |
| Swift | 2014 | 没有 goto |

可以清晰地看到一个趋势：越新的语言，对 `goto` 的限制越严格，直至完全消除。

### 9.3 推动形式化方法与程序验证的发展

Dijkstra 在这封信中隐含的核心诉求——让程序的正确性可以被推理——为形式化方法（formal methods）的发展提供了动力。在此之后：

- **Hoare 逻辑**（1969）：C.A.R. Hoare 提出了用前置条件和后置条件来描述和验证程序正确性的公理化方法。结构化控制流是 Hoare 逻辑能够工作的前提条件之一。
- **Dijkstra 的最弱前置条件**（1975）：Dijkstra 自己后来提出了"最弱前置条件"（weakest precondition）方法，为程序推导和验证提供了更系统的理论框架。
- **程序推导**（program derivation）：从规范出发推导出程序，而不是先写程序再验证——这种方法论的基础正是结构化控制流所提供的可推理性。

### 9.4 改变编程教育

在这封信发表之前，`goto` 是编程入门课程的标配内容，与赋值语句和变量声明一样基础。在这封信之后，编程教育发生了根本性的转变：

- 入门课程不再教授 `goto` 作为基本控制结构。
- 循环（`for`、`while`）和条件（`if-else`）成为控制流教学的核心。
- "不要使用 goto"成为编程教科书中最普遍的教条之一。
- 结构化编程的思想被内化为"编程常识"，以至于今天的初学者甚至不知道 `goto` 曾经是编程的主流方式。

### 9.5 "Considered Harmful" 成为文化符号

这封信的标题模式已经超越了计算机科学的范畴，成为了一个广泛使用的文化符号。在技术社区中，"X considered harmful" 意味着对某种流行实践的严肃质疑。这种模式被如此频繁地使用（和滥用），以至于它本身也成为了讽刺和自我指涉的对象。

### 9.6 软件工程方法论意识的觉醒

从更宏观的视角看，这封信标志着计算机科学社区开始严肃思考"如何编程"这个元问题。在此之前，人们主要关心"程序能不能运行"；在此之后，"程序是否可以被理解""程序是否容易维护""程序的正确性能否被验证"逐渐成为与"程序能否运行"同等重要的关注点。

这种意识的觉醒为后来的一系列发展铺平了道路：面向对象编程（强调信息隐藏和封装）、设计模式（强调可复用的结构）、敏捷方法（强调持续重构）、代码审查文化（强调可读性）。

### 9.7 Dijkstra 的图灵奖

1972 年，Dijkstra 获得了图灵奖——计算机科学的最高荣誉。获奖理由是"对编程作为一种高度智力挑战活动的基础性贡献"（for fundamental contributions to programming as a high, intellectual challenge）。虽然获奖不仅仅因为这封信，但这封信无疑是他在编程方法论方面影响力最大的作品之一，也是评奖委员会所认可的贡献的重要组成部分。

## 10. 今天的视角再看

### 10.1 goto 的"死亡"与"残余"

在今天的主流编程实践中，`goto` 确实已经基本消失了。绝大多数现代程序员可能从未在自己的代码中使用过 `goto`，甚至不知道自己使用的语言是否支持 `goto`。从这个意义上说，Dijkstra 的主张获得了完全的胜利。

但如果我们仔细观察，`goto` 的"精神"并没有完全死去——它以各种受控的、结构化的形式残存着：

- **异常处理（try-catch-finally）**：本质上是一种受控的远距离跳转——当异常被抛出时，执行流从抛出点跳到最近的匹配 `catch` 块。可以将其视为一种"结构化的 goto"，它有明确的规则（只能跳到调用栈上方的 catch 块），因此保持了可理解性。
- **labeled break / continue**：Java、Kotlin 等语言提供的 labeled break 和 continue 允许跳出或跳过多层循环——这正是 `goto` 被认为有合理用途的场景之一。
- **early return**：函数中的早期返回（`return`）也是一种跳转——它中断了函数的"自然"执行流。但由于它的目标是确定的（函数调用点），因此不会导致可理解性的损失。
- **尾调用和延续（continuations）**：在函数式编程和某些系统编程中，尾调用优化和 continuation 可以看作是另一种形式的控制流转移。

### 10.2 函数式编程：比结构化编程走得更远

如果说结构化编程消除了 `goto`，那么函数式编程则更进一步——连**循环**和**可变状态**都被视为需要避免的构造。

在 Haskell、Erlang、Clojure 等函数式语言中：

- 循环被**递归**和**高阶函数**（map、filter、reduce）替代。
- 可变变量被**不可变绑定**替代。
- 副作用被**纯函数**和**monad**等机制隔离。

从 Dijkstra 的视角来看，函数式编程是他思想的自然延伸——如果 `goto` 因为破坏可理解性而应该被消除，那么可变状态和不受控制的副作用同样破坏可理解性，也应该被限制。事实上，Dijkstra 在晚年越来越倾向于函数式的思维方式，尽管他始终保持着自己独特的风格。

### 10.3 从控制流复杂度到状态管理复杂度

1968 年的核心挑战是**控制流**的复杂度——程序跳来跳去，没有人知道执行点在哪里。到了 2020 年代，控制流的问题已经基本被解决（感谢结构化编程），但新的复杂度挑战出现了：

- **状态管理复杂度**：现代应用程序（尤其是前端和移动端）的状态空间极其庞大——用户界面状态、网络请求状态、缓存状态、动画状态……如何让这些状态的变化可以被程序员理解和推理，是今天的核心挑战。React 的单向数据流、Redux 的集中式状态管理、ELM 架构——这些都是在尝试解决"状态的可理解性"问题。
- **并发复杂度**：多线程、异步编程、分布式系统中的并发问题使得程序行为变得极其难以推理。竞态条件（race condition）、死锁（deadlock）、数据竞争（data race）——这些问题在概念上与 `goto` 的问题类似：它们都使得从程序文本推断执行行为变得困难。Go 语言的 goroutine、Rust 的所有权系统、Actor 模型——这些都是试图让并发编程"可理解"的尝试。

### 10.4 Dijkstra 的核心洞察在当代的延续

Dijkstra 的核心洞察——**程序应当被设计为可以被人类理解的**——在今天以多种形式被持续践行：

- **代码可读性运动**：Robert C. Martin 的《Clean Code》、Martin Fowler 的《Refactoring》等著作将"代码可读性"提升为软件工程的核心价值。"代码被阅读的次数远多于被编写的次数"——这句格言的精神与 Dijkstra 一脉相承。
- **Code Review 文化**：现代软件开发中，代码审查已经成为标准实践。Code Review 的核心假设恰恰是：代码应该能够被作者之外的人阅读和理解。
- **设计模式与架构原则**：SOLID 原则、设计模式、Clean Architecture——这些都是在更高的抽象层次上追求"可理解性"。
- **类型系统的进化**：TypeScript 给 JavaScript 增加了类型、Rust 引入了所有权和生命周期——更强的类型系统使得编译器可以代替人脑进行更多的"程序行为推理"。

### 10.5 AI 时代的新思考

在 AI 辅助编程和 AI 生成代码日益普及的今天，Dijkstra 的思想获得了新的意义：

- **AI 生成代码的质量评估**：当 AI（如 GitHub Copilot、ChatGPT）生成代码时，"可理解性"仍然是评估代码质量的核心指标。一段由 AI 生成的、人类无法理解的代码，即使它能正确运行，也是危险的——因为当它需要修改时，没有人知道如何安全地修改它。
- **可解释性的回归**：在机器学习领域，"可解释 AI"（Explainable AI）正成为重要的研究方向。这与 Dijkstra 的诉求本质相同：我们不仅需要系统能工作，还需要理解它为什么能工作。

## 11. 通俗科普版解释

### 想象一本可以随意跳页的书

`goto` 就像在一本书中随意翻页。作者在第 5 页写着"请翻到第 173 页继续阅读"，到了第 173 页又写着"回到第 42 页"，第 42 页说"如果你觉得饿了翻到第 89 页，否则翻到第 201 页"。读者在书页之间来回翻找，完全无法理解故事的脉络。更糟糕的是，你永远不知道自己是第一次读到某一页，还是从别的地方跳回来的——而这两种情况下，故事的上下文可能完全不同。

现在想象另一本书：它按照正常的章节、段落、句子组织。有时候会说"如果主角选择了左边的门，请看下一段；如果选择了右边的门，请跳到本页底部"（这就是 `if-else`）。有时候会说"重复以下三个步骤直到完成"（这就是 `while` 循环）。但它永远不会让你随意跳到书中毫不相关的某一页。

Dijkstra 说的是：我们应该像写第二种书那样写程序——有清晰的结构，读者（包括程序员自己、同事、以及未来的维护者）可以按照逻辑顺序理解程序在做什么。

### 好程序应该像好文章

Dijkstra 的论点本质上是一个关于**沟通**的论点。程序不仅仅是写给机器执行的指令——它也是写给人阅读的文本。就像好的文章有清晰的结构（引言、论点、论据、结论），好的程序也应该有清晰的结构（初始化、主循环、条件分支、收尾处理）。

`goto` 破坏了这种结构，就像一篇文章中到处都是"请参见第 X 页脚注 Y"一样——读者不得不在文本中来回跳转，最终迷失在引用的迷宫中。

### 一封改变世界的投诉信

这封信的篇幅极短——不到两页，大约 700 个英文单词。放到今天，它的字数可能还不够发一条长微博。但就是这样一封短信，改变了整个行业写代码的方式。

这有点像一封居民投诉信改变了一座城市的交通规则：有人指出"允许汽车在任何地方随意掉头是危险的"，于是城市规划者开始设置车道、红绿灯、立交桥——这些结构限制了驾驶者的"自由"，但让交通变得安全、有序、可预测。

`goto` 就是编程世界中的"随意掉头"。结构化编程就是"交通规则"。Dijkstra 就是那个写投诉信的市民——只不过他的投诉信改变的不是一座城市，而是全球的软件开发方式。

### 为什么 Dijkstra 是对的（用最简单的话说）

程序在电脑里运行时，就像一个小人在执行一系列指令。如果指令是"做完这个做那个"，我们很容易想象小人在做什么。如果指令是"如果下雨就带伞，否则戴墨镜"，我们也能理解。如果指令是"重复搅拌直到面团光滑"，我们也能跟上。

但如果指令变成了"做完第三步后跳到第一百步，然后在第一百步里可能跳到第五十步，在第五十步里又可能跳回第七步"——我们的脑子很快就会一团浆糊。

Dijkstra 的核心观点就是：写程序的方式应该让人脑跟得上。`goto` 让人脑跟不上。所以，不要用 `goto`。

就这么简单。而有时候，最简单的道理也最难被接受——因为它要求人们改变已经习惯了几十年的做事方式。

## 12. 可引用摘要

**1. 关于核心论点**

> Dijkstra 在 1968 年的这封信中论证了一个看似简单却影响深远的观点：编程构造的价值不在于它能让程序运行，而在于它能否让程序员理解程序为何正确。`goto` 语句因为破坏了程序文本与执行过程之间的结构化对应关系，使得程序的正确性推理从可管理变为不可管理，因此应当被消除。

**2. 关于历史意义**

> "Go To Statement Considered Harmful" 是计算机科学史上最具影响力的短文之一。这封不到两页的编辑来信引发了结构化编程革命，直接影响了此后五十年间几乎所有编程语言的设计决策，并将编程方法论从个人技艺提升为可以理性讨论的科学问题。它的标题模式 "X Considered Harmful" 已成为技术界最广泛使用的批评文体。

**3. 关于认知洞察**

> Dijkstra 的核心洞察可以概括为：程序有两种存在方式——静态的文本和动态的执行。好的编程结构让这两者之间有清晰的对应关系；坏的编程结构（如 `goto`）让这种对应关系变得混乱。由于人类认知能力有限，编程语言和编程风格应当被设计为适配人脑的推理能力，而非与之对抗。

**4. 关于当代启示**

> Dijkstra 五十多年前的诉求——"程序应当可以被人理解"——在今天以代码可读性运动、Code Review 文化、Clean Code 原则、类型系统进化等形式被持续践行。控制流的混乱已被结构化编程解决，但状态管理的混乱和并发编程的混乱成为了新时代的"意大利面条"。Dijkstra 的思想不是一个已经完成的历史事件，而是一个仍在展开的智识传统。

**5. 关于思想遗产**

> Dijkstra 用 700 个单词证明了一件事：在计算机科学中，最重要的进步往往不是发明新的技术，而是认识到某种旧的做法是有害的。从 `goto` 到全局变量，从可变共享状态到未经检查的 null 引用，计算机科学的进步史在很大程度上是一部"认识到什么不应该做"的历史。而 Dijkstra 的这封信，是这部历史中最著名的第一章。
