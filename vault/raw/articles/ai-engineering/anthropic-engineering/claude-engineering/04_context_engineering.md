# 上下文工程：AI Agent 的新核心命题

> **原文**：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)  
> **发布日期**：2025 年 9 月 29 日  
> **作者**：Anthropic Applied AI 团队（Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield 等）  
> **类别**：Context Engineering · Agent 架构 · 长时任务

---

## 摘要

本文系统阐述了"上下文工程（Context Engineering）"这一正在替代"提示工程（Prompt Engineering）"成为 AI 应用核心挑战的新范式。文章从 LLM 注意力预算的有限性出发，分析了系统提示、工具、示例、消息历史等各维度的最优上下文策略，并重点讨论了长时任务中的三大技术：上下文压缩（Compaction）、结构化记录（Structured Note-taking）和子 Agent 架构。这是迄今为止对 Agent 上下文管理最全面的工程指南之一。

---

## 一、概念跃迁：从提示工程到上下文工程

### 1.1 定义的演化

**提示工程（Prompt Engineering）**：如何编写和组织 LLM 指令以获得最优输出——本质上是一次性、静态的文本设计问题。

**上下文工程（Context Engineering）**：在 LLM 推理过程中，策略性地管理和维护最优 token 集合——本质上是动态的、多轮的信息策展问题。

用文章的语言表述：
> "上下文工程是**在 LLM 推理过程中**，从不断演化的可用信息宇宙中策展最优上下文的艺术与科学。"

这一定义将工程挑战从"如何写"升级为"何时加入什么信息"。

### 1.2 范式迁移的驱动力

单次对话 → 多轮 Agent 循环的转变带来了根本性复杂度提升：

```
单次 LLM 调用（提示工程）：
[System Prompt + User Query] → Response

多轮 Agent 循环（上下文工程）：
[System Prompt + Tools + Memory + Message History + Tool Results] × N turns → Behavior
```

每一轮循环都生成新数据，这些数据**可能**对下一轮推理有用，但无限堆积最终导致上下文质量下降。

## 二、上下文有限性的深层原因

### 2.1 上下文衰减（Context Rot）

研究表明，随着上下文 token 数量增加，LLM 准确回忆信息的能力单调下降——即使上下文窗口尚未填满，也会出现"针在草堆里"（Needle-in-a-Haystack）失败模式。

这种现象的成因：
1. **注意力稀释**：Transformer 架构中每个 token 需与所有其他 token 计算注意力，n 个 token 产生 n² 对关系，超过一定规模后关系质量下降
2. **训练分布偏移**：训练数据中较短序列比较长序列更常见，模型对长序列依赖的特化参数相对较少
3. **位置编码插值**：长上下文通常需要位置编码插值（如 RoPE 外推），引入一定的位置理解退化

**关键结论**：即使上下文窗口不断扩大，上下文工程的重要性也不会消失——更大的窗口只是推迟了问题，而非消除它。

### 2.2 注意力预算的经济学比喻

文章将 LLM 的"注意力"类比为有限的认知资源：
- 每个新 token 消耗一定预算
- 边际回报递减
- 最优策略：找到**最小高信噪比 token 集合**，使期望输出质量最大化

## 三、高效上下文的各维度策略

### 3.1 系统提示设计

**核心原则**："适当高度（Right Altitude）"——介于两种极端之间的黄金区间：

```
极端一（过低）：硬编码复杂逻辑
"如果用户说 X，并且条件 A 为真，则执行步骤1、2、3..."
问题：脆弱、难维护、快速失效

极端二（过高）：过度抽象
"智能地处理所有用户请求，保持专业。"
问题：缺乏具体信号，错误假设共享上下文

最优区间：
提供足够具体的行为启发，同时允许灵活处理未预见情形
```

**组织建议**：使用 XML 标签或 Markdown 标题划分系统提示的不同部分：
- `<background_information>`：背景知识
- `<instructions>`：核心指令
- `## Tool guidance`：工具使用指南
- `## Output description`：输出格式说明

**最小化原则**：目标是充分说明预期行为所需的**最少信息量**（注意：不一定是最短，而是最精准）。

### 3.2 工具设计

工具是 Agent 与信息/动作空间的契约，需要满足：

- **Token 高效**：返回信息应精炼，避免冗余
- **行为高效**：鼓励 Agent 采用高效行为模式
- **功能清晰**：每个工具有明确单一的用途
- **最小化工具集**：能说出"此情境应用哪个工具"——若无法确定，Agent 也无法

**常见失败模式**：工具集过于臃肿，功能重叠，导致 Agent 在工具选择上浪费推理资源。

### 3.3 少样本示例（Few-shot Prompting）

**推荐做法**：精心选择多样化、有代表性的**典范示例**，而非穷举所有边缘情况。

**危险做法**：将大量边缘情况堆砌到 prompt 中——示例是"图片"，不是规则集，过多边缘示例会淹没核心模式。

## 四、即时检索（Just-in-Time Context Retrieval）

### 4.1 范式对比

```
传统 RAG（预推理检索）：
查询时间前 → [批量检索] → [排序嵌入] → 注入上下文 → 推理

JIT 检索（动态检索）：
推理过程中 → [Agent 主动用工具检索] → 按需加载到上下文
```

JIT 检索的核心优势：
- **按需加载**：仅在需要时加载数据，避免上下文预置大量可能用不到的信息
- **动态适应**：根据任务进展自动调整信息获取
- **渐进式发现**：Agent 通过探索逐步积累上下文，类似人类研究过程

### 4.2 Claude Code 的实践

Claude Code 是 JIT 检索的典型案例：
- CLAUDE.md 文件**直接注入**上下文（预置的高价值信息）
- glob、grep 等工具允许**按需检索**文件（JIT）
- 绕过了静态索引过期的问题，避免了复杂语法树的维护

### 4.3 混合策略的决策逻辑

| 场景特征 | 推荐策略 |
|---|---|
| 信息高度稳定（如法律文件） | 混合（预置核心 + 按需详情） |
| 信息频繁变化（如代码库） | JIT 为主 |
| 简单单次任务 | 预置上下文（RAG 或直接注入） |
| 复杂长时任务 | JIT + 压缩 + 记录 |

## 五、长时任务的三大技术

### 5.1 上下文压缩（Compaction）

**定义**：当上下文接近窗口限制时，将对话历史进行总结，用摘要替换原始内容，开启新的上下文窗口。

**实现关键**：
- 压缩 prompt 需精心调优，避免丢失关键细节
- 优先删除低价值内容（如旧的工具调用原始输出）
- 保留：架构决策、未解决 Bug、实现细节

**Claude Code 的压缩方案**：
- 将消息历史传给模型，让模型总结关键信息
- 保留最近 5 个访问过的文件
- 保留：架构决策、未解决 Bug + 实现细节
- 丢弃：冗余工具输出、重复消息

**最轻量的压缩**：仅清理深层历史中的工具调用结果（这些结果通常已不再需要原始格式）。

### 5.2 结构化记录（Structured Note-taking）

**定义**：Agent 定期将重要信息写入上下文窗口之外的持久化存储，并在需要时重新加载。

**原理**：外部化工作记忆，突破上下文窗口物理限制。

**典型实现**：
- Claude Code：维护 todo 清单文件
- 自定义 Agent：维护 NOTES.md 文件
- 高级场景：结构化记忆数据库

**案例：Claude 玩宝可梦**

Claude 在游玩宝可梦时自发建立了结构化记忆：
- 精确追踪目标进度："过去 1234 步在 1 号街道训练，皮卡丘升了 8 级，目标升 10 级"
- 维护已探索区域地图
- 记录战斗策略（哪些技能对哪些对手有效）
- 在上下文重置后，通过读取记录恢复多小时的训练序列

这个案例展示了结构化记录如何使 Agent 具备**跨会话长时任务能力**。

### 5.3 子 Agent 架构（Sub-agent Architectures）

**核心思想**：将长时任务分解，专业子 Agent 在各自干净的上下文窗口中处理聚焦任务，将精炼摘要返回给协调者。

**上下文流动模式**：
```
Lead Agent（轻量上下文，高层协调）
    ↓ 派遣任务
Sub-agent A（独立上下文，深度探索 → 摘要）
Sub-agent B（独立上下文，深度探索 → 摘要）
    ↓ 返回精炼结果（~1000-2000 tokens）
Lead Agent（接收摘要，综合分析）
```

**关键数字**：子 Agent 可能探索使用数万 token，但返回给协调者的摘要通常只有 1000-2000 token。

## 六、各技术对比与选择矩阵

| 技术 | 最适合场景 | 主要优势 | 主要成本 |
|---|---|---|---|
| **压缩** | 需要大量来回交互的任务 | 对话连贯性好 | 压缩质量难以保证 |
| **结构化记录** | 有清晰里程碑的迭代开发 | 跨会话持久化 | 需要设计好记录格式 |
| **子 Agent 架构** | 需要并行探索的复杂研究 | 真正的并行处理 | 协调复杂度高 |

## 七、深度辨析

### 7.1 "最小高信噪比 token" 原则的哲学内涵

这个原则看似简单，实则涉及深层的信息论权衡：

**信息论视角**：好的上下文相当于对模型行为空间进行精确约束，使目标行为在条件分布中获得尽可能高的概率。

**过度约束的危险**：系统提示过于详细会将模型锁定在狭窄行为空间，失去处理意外情形的灵活性。

**约束不足的危险**：信息过少导致模型在宽泛的行为空间中"漂移"，无法稳定实现目标行为。

### 7.2 与人类认知的对应

文章多次将 LLM 上下文管理与人类认知进行类比：

| 人类认知 | LLM 上下文 |
|---|---|
| 工作记忆（Working Memory） | 上下文窗口 |
| 外部组织系统（笔记、文件夹） | 持久化存储（NOTES.md、Memory） |
| 注意力集中 | 注意力权重集中 |
| 认知负荷限制 | Context Rot 现象 |

这种类比不仅有助于直觉理解，还提示了解决方案的设计方向——人类如何扩展认知能力，Agent 就可以如何设计。

### 7.3 "越来越少需要工程干预"的趋势

文章末尾的洞见值得特别关注：

> "随着模型能力提升，Agentic 设计会趋向于让智能模型更智能地行动，人类策展的需求会逐渐减少。"

这意味着：
- 短期内，上下文工程将是核心竞争力
- 长期内，模型可能自主掌握上下文管理策略
- 工程师的角色将从"上下文策展者"转向"上下文质量保障者"

## 八、结论

上下文工程代表了 AI 应用工程的成熟化：从关注"说什么"（提示工程）转向关注"在正确时机提供正确信息"（上下文工程）。

文章提炼的核心原则——**找到最小化高信噪比 token 集合**——是所有具体技术的统一基础。无论是系统提示设计、工具定义、JIT 检索还是长时任务技术，都是这个原则在不同维度的具体实现。

对于构建生产级 Agent 系统的工程师，这篇文章提供了一个完整的心智模型和实用工具箱，是值得反复阅读的核心参考文献。
