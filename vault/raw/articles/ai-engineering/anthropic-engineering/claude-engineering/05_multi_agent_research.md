## 摘要

本文是 Anthropic 工程师对其 Research 功能（多 Agent 研究系统）从原型到生产的完整复盘。文章深入探讨了多 Agent 系统的架构设计、Prompt 工程策略、评估方法、以及生产可靠性挑战。核心数据：多 Agent Opus 4 + Sonnet 4 子 Agent 系统相比单 Agent Opus 4，在内部研究评测中性能提升 **90.2%**。这是迄今最详尽的多 Agent 生产系统工程经验分享。

---

## 一、为什么研究任务天然适合多 Agent

### 1.1 开放性与路径依赖

研究任务的核心特征：
- **步骤不可预判**：无法提前确定需要搜索多少次、哪些方向
- **路径依赖**：每个发现都可能改变后续探索方向
- **动态适应**：需要根据中间结果实时调整策略

这些特征使得线性流水线（linear pipeline）无法胜任，而 Agent 系统天然对应这类需求。

### 1.2 并行探索的信息论优势

多 Agent 系统的根本价值在于**压缩**（compression）：

> "搜索的本质是压缩：从海量语料中提炼洞见。子 Agent 通过在独立上下文窗口中并行探索，压缩信息后再传递给主 Agent。"

每个子 Agent 提供：
- **独立探索轨迹**：减少路径依赖，避免陷入局部最优
- **关注点分离**：专用工具、专用 prompt、专用视角
- **并行探索**：同时探索多个研究方向，而非顺序探索

### 1.3 性能数据：Token 是关键变量

**BrowseComp 评测的关键发现**（解释 95% 性能方差的三个因素）：

| 因素 | 方差解释比例 |
|---|---|
| Token 使用量 | **80%** |
| 工具调用次数 | ~10% |
| 模型选择 | ~5% |

**惊人结论**：升级到 Claude Sonnet 4 带来的性能提升，大于**翻倍** Claude Sonnet 3.7 的 token 预算。

**Token 消耗的现实代价**：
- Agent 典型消耗 chat 的 **4 倍** token
- 多 Agent 系统消耗 chat 的 **15 倍** token

这意味着多 Agent 系统的经济可行性依赖于任务价值是否足以支撑这一成本。

## 二、架构设计：Orchestrator-Worker 模式

### 2.1 系统架构图

```
用户查询
    ↓
[LeadResearcher Agent]
├── 规划研究策略
├── 保存计划到 Memory（防上下文截断）
├── 并行派遣子 Agent
│   ├── [SubAgent-A]：主题方向 A
│   │   ├── 迭代搜索工具
│   │   ├── 交织推理（Interleaved Thinking）
│   │   └── 返回凝炼摘要
│   └── [SubAgent-B]：主题方向 B
│       └── ...
├── 综合所有子 Agent 结果
├── 判断是否需要更多研究
│   ├── 是 → 创建新子 Agent 或细化策略
│   └── 否 → 进入引用处理
└── [CitationAgent]：定位具体引用位置
         ↓
    最终研究报告（含引用）
```

### 2.2 动态 RAG vs 静态 RAG

传统 RAG：预先检索 → 静态注入上下文 → 一次生成

Research 系统：
- 多步搜索，**动态发现**相关信息
- 根据新发现**适应搜索策略**
- 迭代分析，生成高质量答案

## 三、Prompt 工程：从经验到原则

文章总结了 8 条多 Agent Prompt 工程原则，每条都有具体失败案例支撑：

### 3.1 像 Agent 一样思考

**实践**：在 Console 中用真实 prompt 和工具构建模拟，逐步观察 Agent 工作。

**发现的常见失败模式**：
- 已有足够结果时继续搜索
- 搜索查询过于冗长具体
- 选择错误的工具

### 3.2 教会 Orchestrator 如何委派

**失败案例**：允许 LeadAgent 给子 Agent 简短指令（如"研究半导体短缺"），导致：
- 子 Agent 重复工作（两个子 Agent 都研究 2025 年供应链）
- 分工不明确（一个研究 2021 汽车芯片危机，另两个研究相同的当前供应链）

**解决方案**：子 Agent 的任务描述必须包含：
- 明确目标
- 输出格式
- 工具和信源使用指南
- 清晰的任务边界

### 3.3 根据查询复杂度缩放工作量

**嵌入到 Prompt 中的缩放规则**：
- 简单事实查询：1 个 Agent，3-10 次工具调用
- 直接比较：2-4 个子 Agent，各 10-15 次工具调用
- 复杂研究：10+ 个子 Agent，清晰分工

**早期失败**：对简单查询过度投入 Agent 和工具调用，浪费资源。

### 3.4 工具设计与选择的关键性

**核心原则**：给 Agent 明确的启发规则——
- 先检查所有可用工具
- 将工具使用与用户意图匹配
- 广泛外部探索用网络搜索
- 专用工具优于通用工具

**工具测试 Agent 的创新实践**：

给定一个有缺陷的 MCP 工具，让 Agent 尝试使用该工具，然后**重写工具描述以避免失败**。通过数十次测试，这个 Agent 发现了关键细节和 Bug。

**量化效果**：新描述使后续 Agent 的任务完成时间减少 **40%**（因为避免了大多数错误）。

### 3.5 让 Agent 优化自己

Claude 4 模型可以充当优秀的"Prompt 工程师"——给定失败模式，它们能诊断原因并建议改进。这创造了**自我改进的 Prompt 工程循环**。

### 3.6 先广后深的搜索策略

**发现**：Agent 默认倾向于使用过于具体的查询，返回结果少。

**解决方案**：在 Prompt 中引导 Agent 模仿专家人类研究者：先用短、宽泛查询探索全局，评估可用信息，再逐步缩小焦点。

### 3.7 引导思维过程

**Extended Thinking**（交织推理模式）的使用：
- LeadAgent 用 thinking 规划整体方法
- SubAgent 在工具结果后用交织 thinking 评估质量、发现缺口、细化下一个查询

**实验效果**：Extended Thinking 改善了指令遵从性、推理质量和效率。

### 3.8 并行工具调用的变革性影响

**早期问题**：顺序搜索极其缓慢。

**两种并行化**：
1. LeadAgent 同时派遣 3-5 个子 Agent（而非串行）
2. 每个子 Agent 同时调用 3+ 个工具

**效果**：复杂查询的研究时间缩短高达 **90%**，从数小时缩短到数分钟。

## 四、评估体系：多维度验证

### 4.1 小样本快速启动原则

**关键洞见**：早期 Agent 开发中，由于低悬果实丰富，仅 20 个测试样本就能发现显著差异（如 30% → 80% 的成功率提升）。

**对抗常见错误认知**：许多团队认为"只有数百个测试案例才有用"，文章明确建议**立即从小规模测试开始**，而非等待构建完整评测框架。

### 4.2 LLM-as-Judge 的最佳实践

研究输出难以程序化评估（自由文本，无单一正确答案），使用 LLM 评判是自然选择。

**评估维度**：
- 事实准确性（声明是否与信源一致）
- 引用准确性（引用信源是否支持声明）
- 完整性（是否覆盖所有请求方面）
- 信源质量（是否优先使用一级信源）
- 工具效率（工具使用次数是否合理）

**最终实现**：单次 LLM 调用 + 单一 prompt 输出 0.0-1.0 评分 + 通过/失败等级——比多评判器方案**更一致**，且与人工判断更对齐。

### 4.3 人工评估的不可替代性

**真实发现的案例**：人工测试者注意到早期 Agent 系统性地选择 SEO 优化的内容农场，而非权威但搜索排名较低的来源（学术 PDF、个人博客）。

向 Prompt 中添加信源质量启发规则后，问题得到解决——但这个问题只有人工测试才能发现。

## 五、生产可靠性：工程挑战

### 5.1 状态性与错误复合

Agent 可长时间运行，在许多工具调用中维护状态。传统软件的 Bug 是局部的，但 Agent 的错误会**复合**——一步出错可能导致后续完全走偏。

**解决方案**：
- 系统支持**从错误发生处恢复**，而非从头重启
- 让模型**感知工具失败**并自适应调整（"当工具失败时通知 Agent 让其适应"）
- 确定性重试逻辑 + 定期检查点

### 5.2 新调试方法论

**问题**：用户报告 Agent"找不到显而易见的信息"，但无法诊断原因（是搜索查询差？选了坏信源？工具失败？）

**解决方案**：添加完整的**生产追踪**，可诊断失败原因。同时：
- 监控 Agent 决策模式和交互结构
- 不监控具体对话内容（保护用户隐私）
- 高层可观察性帮助发现意外行为和诊断根因

### 5.3 彩虹部署（Rainbow Deployments）

**挑战**：Agent 系统是高度有状态的 Prompt + 工具 + 执行逻辑的网络，几乎持续运行。代码更新时，Agent 可能处于流程中的任意位置。

**解决方案**：使用彩虹部署（Rainbow Deployments）——新旧版本同时运行，流量逐步从旧版本转移到新版本，避免中断运行中的 Agent。

### 5.4 同步执行的瓶颈

**当前限制**：LeadAgent 同步执行子 Agent，等待一批子 Agent 完成后才继续。

**潜在改进**：异步执行可以实现额外的并行性，但带来：
- 结果协调复杂性
- 状态一致性挑战
- 跨子 Agent 错误传播问题

## 七、深度辨析

### 7.1 "token 解释 80% 方差"的含义

这个发现揭示了多 Agent 系统的本质：**性能主要是计算资源（token）的函数**，而非仅仅是架构创新的函数。

这有两层含义：
1. **模型能力是乘数**：更强的模型让每个 token 的"效用"更高
2. **架构的作用**：多 Agent 架构主要提供了一种**有效扩展 token 使用量**的机制（并行子 Agent），而非凭空创造智能

### 7.2 涌现行为的管理

文章提到多 Agent 系统存在"涌现行为"——小改变导致大行为变化。这是复杂系统的典型特征，也是多 Agent 工程中最难预测的部分。

**管理策略**：
- 最佳 prompt 不是严格指令，而是**协作框架**（分工、问题解决方法、资源预算）
- 需要理解交互模式，而非仅仅理解单个 Agent 行为

### 7.3 多 Agent 的适用边界

文章直接指出多 Agent 系统**不适合**的场景：
- 所有 Agent 需要共享同一上下文的任务
- Agent 间存在大量依赖的任务
- 大多数编码任务（并行化程度不如研究高）
- LLM Agent 还不擅长实时协调和委派
