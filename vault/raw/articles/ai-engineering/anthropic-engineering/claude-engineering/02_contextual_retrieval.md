# 上下文检索：RAG 系统的关键突破

> **原文**：[Introducing Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)  
> **发布日期**：2024 年 9 月 19 日  
> **作者**：Daniel Ford  
> **类别**：RAG · 检索增强生成 · 信息检索

---

## 摘要

本文介绍了 Anthropic 提出的"上下文检索（Contextual Retrieval）"方法，该方法通过在对文本块进行嵌入（Embedding）和建立 BM25 索引**之前**，为每个文本块添加语境化的解释性前缀，从而显著改善了 RAG 系统的检索准确性。实验表明，结合上下文嵌入（Contextual Embeddings）和上下文 BM25 可将检索失败率降低 **49%**；进一步结合重排序（Reranking）可达 **67%**。这是 RAG 系统工程中一项极具实用价值的改进。

---

## 一、传统 RAG 的"上下文困境"

RAG（检索增强生成）的核心矛盾在于：为了高效检索，文档必须被切分为小块；但切分本身会**破坏上下文**，使检索到的片段缺乏关键语境信息。

文章给出了一个极具说服力的例子：

> 假设在金融数据库中，一个相关文档片段是：  
> *"该公司营收比上一季度增长了 3%。"*

这个片段独立来看无法回答"ACME 公司 2023 年 Q2 营收增长是多少？"这类查询，因为它没有指明是哪家公司、哪个时间段。

这是传统 RAG 的系统性缺陷——即使使用语义嵌入+BM25 混合检索，也无法弥补文本块本身信息密度不足的问题。

---

## 二、Contextual Retrieval 的核心机制

### 2.1 方法原理

Contextual Retrieval 在预处理阶段，为每个文本块生成并前置语境化的说明文本，再进行嵌入和 BM25 索引建立。

**转化示例**：

```
原始文本块：
"该公司营收比上一季度增长了 3%。"

语境化文本块：
"此片段来自 ACME 公司 2023 年 Q2 的 SEC 文件；上一季度营收为 3.14 亿美元。
该公司营收比上一季度增长了 3%。"
```

这个 50-100 token 的语境前缀携带了文档级别的信息，使孤立的文本块变得"可理解"。

### 2.2 生成语境的 Prompt

Anthropic 使用 Claude 3 Haiku 批量生成语境，使用的 prompt 模板为：

```
<document> 
{{WHOLE_DOCUMENT}} 
</document> 
以下是我们想在整个文档中定位的片段：
<chunk> 
{{CHUNK_CONTENT}} 
</chunk> 
请提供一段简短的语境说明，将此片段定位在整体文档中，
以改善搜索检索效果。只需回答简洁的语境说明，不要其他内容。
```

### 2.3 成本优化：Prompt Caching

关键工程细节：利用 Claude 的 **Prompt Caching** 特性，文档只需加载到缓存一次，即可为所有片段重复使用，大幅降低成本。

**成本估算**（假设 800 token 块、8K token 文档、50 token 指令、100 token 语境）：  
→ 一次性生成语境化块的成本：**每百万文档 token 仅需 1.02 美元**

## 三、检索技术全栈解析

### 3.1 传统 RAG 的双引擎机制

文章首先清晰解释了传统 RAG 的两种检索机制：

**语义嵌入（Semantic Embeddings）**：
- 将文本块转换为向量，捕获语义关系
- 擅长理解意图和上下文相似性
- 弱点：对精确词汇/标识符匹配能力有限

**BM25（Best Matching 25）**：
- 基于 TF-IDF 的词汇精确匹配排序函数
- 擅长精确的词语或短语匹配
- 强项：技术术语、错误代码等精确标识符
- 弱点：无语义理解

**经典场景对比**：

查询 "错误代码 TS-999"：
- 嵌入模型：可能找到关于错误代码的通用内容，但错过 "TS-999" 精确匹配
- BM25：直接定位包含该精确字符串的文档

两者互补形成混合检索。

### 3.2 Contextual Retrieval 的三层增强

```
标准 RAG Pipeline：
文档 → 切分 → [嵌入 + BM25] → 检索 → 生成

Contextual Retrieval Pipeline：
文档 → 切分 → [LLM生成语境 + 前置] → [语境嵌入 + 语境BM25] → 检索 → [Reranking] → 生成
```

## 四、性能实验结果

### 4.1 消融实验设计

实验跨越多个知识领域（代码库、小说、ArXiv 论文、科学论文），多种嵌入模型，采用 **1 - recall@20** 作为主要评估指标（衡量前 20 个块中检索失败的比例）。

### 4.2 核心结果

| 方法 | 检索失败率 | 相对降低 |
|---|---|---|
| 基准（嵌入 + BM25） | 5.7% | — |
| + 语境嵌入 | 3.7% | **↓35%** |
| + 语境嵌入 + 语境 BM25 | 2.9% | **↓49%** |
| + 语境嵌入 + 语境 BM25 + Reranking | 1.9% | **↓67%** |

### 4.3 重排序（Reranking）的作用

重排序是在初始检索（取前 150 块）之后，通过重排序模型对块进行精细打分，最终取前 20 块传给生成模型。

**工作流程**：
1. 初始检索 → 取 Top 150 候选块
2. 重排序模型对每块评分（查询相关性 + 重要性）
3. 取 Top 20 块传给生成模型

**成本-性能权衡**：重排序增加了推理延迟，需要在性能提升和延迟增加之间找到平衡点。

## 五、实现工程考量

### 5.1 块边界设计

块大小、边界位置和重叠量都会影响检索性能。没有万能答案，需要针对具体知识库进行实验。

### 5.2 嵌入模型选择

实验表明，不同嵌入模型的提升幅度有所不同：

- **表现最佳**：Gemini Text 004、Voyage 系列
- **重要发现**：Contextual Retrieval 对所有测试的嵌入模型均有提升效果

### 5.3 最优 Top-K 选择

实验比较了 5、10、20 个块传入模型的效果：
- Top-20 > Top-10 > Top-5
- 但更多块不一定总更好，因为过多的信息对模型可能造成干扰

## 六、深度辨析

### 6.1 与其他方法的比较

文章明确区分了 Contextual Retrieval 与其他类似思路：

| 方法 | 效果评估 |
|---|---|
| 通用文档摘要添加到块 | 效果有限（实验验证） |
| 假设文档嵌入（HyDE） | 方向不同，未直接比较 |
| 摘要索引（Summary-based Indexing） | 性能较低（实验验证） |
| **Contextual Retrieval（本文）** | 显著提升，且各方法效益可叠加 |

### 6.2 技术深层原因

从信息论角度理解 Contextual Retrieval 的效果：

**传统 RAG** 的向量嵌入本质上是对孤立文本块的压缩表示，丢失了文档结构信息和跨块依赖关系。

**Contextual Retrieval** 的做法实质上是在嵌入前将**局部信息**和**全局信息**融合——相当于给每个文本块添加了"文档指纹"。这种做法借鉴了语言学中的**指示词消解（Coreference Resolution）**概念，将隐式引用变为显式描述。

### 6.3 局限性

1. **预处理成本**：虽然有 Prompt Caching 优化，但生成语境仍需额外 LLM 调用，增加了索引构建时间
2. **动态知识库挑战**：知识库频繁更新时，需要重新生成受影响文本块的语境
3. **语境质量依赖**：语境生成 prompt 的质量直接影响检索效果，可能需要针对领域定制
4. **适用性边界**：对于已经有丰富自包含信息的文本块，提升可能有限

## 七、对 RAG 工程实践的启示

### 7.1 技术选型矩阵

| 知识库规模 | 推荐方案 |
|---|---|
| < 200K token | 直接放入 Context Window（配合 Prompt Caching） |
| 200K - 10M token | 标准 RAG + Contextual Retrieval |
| > 10M token | Contextual Retrieval + Reranking + 多阶段检索 |

### 7.2 实施路径

1. **快速验证**：使用提供的 Cookbook 在小型知识库上测试
2. **成本评估**：计算语境生成的一次性费用（利用 Prompt Caching）
3. **逐步叠加**：先加语境嵌入，再加语境 BM25，最后加 Reranking，分步评估收益
4. **领域定制**：针对特定领域（如法律、医学）调整语境生成 prompt

### 7.3 与 LightRAG/GraphRAG 的对比

Contextual Retrieval 是在**块级别**添加上下文，而 LightRAG/GraphRAG 是在**图结构**层面建模文档关系。两种方法不互斥：
- Contextual Retrieval 更轻量、易实施
- 图结构方法在多跳推理任务上可能有额外优势
- 实际工程中可以先采用 Contextual Retrieval，复杂查询场景再考虑图增强

---

## 八、结论

Contextual Retrieval 是一项极具工程价值的 RAG 改进技术。它的核心洞见——**信息的可理解性依赖于上下文，而传统 RAG 切分过程系统性地破坏了这种上下文**——尽管直觉上易懂，但在实际系统中却长期被忽视。

该方法的优势在于：实现相对简单、可与现有 RAG 基础设施兼容、成本经过 Prompt Caching 优化后可接受，且收益是可叠加的（嵌入 + BM25 + Reranking 三者互补）。

对于构建知识密集型 AI 应用的工程师，这是一项应该成为标配的技术。
