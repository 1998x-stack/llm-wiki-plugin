# "Think" 工具：让 Claude 在复杂工具调用中停下来思考

> **原文**：[The "think" tool: Enabling Claude to stop and think in complex tool use situations](https://www.anthropic.com/engineering/claude-think-tool)  
> **发布日期**：2025 年 3 月 20 日  
> **类别**：Agent 推理 · 工具设计 · 性能优化

---

## 摘要

本文介绍了 Anthropic 发现的一种简单却高效的技术——"think" 工具：通过为模型提供一个显式的"思考空间"，让 Claude 在复杂工具调用链中暂停并分析中间结果，从而显著提升策略遵从性和决策质量。在 τ-Bench 航空域测试中，配合优化 prompt 的"think"工具相比基准提升了 **54%**（pass@1 从 0.370 → 0.570）。本文还明确区分了 "think" 工具与 Extended Thinking 的适用场景。

> ⚠️ **更新说明（2025 年 12 月）**：Extended Thinking 能力已大幅提升，在大多数场景下 Anthropic 现推荐使用 Extended Thinking 替代专用的 think 工具。但本文的分析仍具有重要的理论和实践价值。

---

## 一、核心概念：两种"思考"机制的区分

文章做出了一个常被混淆的关键区分：

| 特性 | Extended Thinking | "think" 工具 |
|---|---|---|
| **触发时机** | 模型开始生成**之前** | 已开始生成**之中** |
| **适用场景** | 深度计划、数学、编程 | 长工具调用链中处理工具输出 |
| **信息基础** | 主要基于用户查询 | 基于**外部工具返回的新信息** |
| **推理深度** | 更全面 | 更聚焦于新发现信息 |
| **最优领域** | 非工具场景（编码/数学/物理） | 策略密集、顺序决策场景 |

**直觉类比**：Extended Thinking 像是专家**开始工作前**的深度规划；"think" 工具像是专家在**看到化验结果后**的即时分析。

---

## 二、工具定义与实现

"think" 工具的实现极其简单，其定义仅需：

```json
{
  "name": "think",
  "description": "使用此工具来思考某件事。它不会获取新信息或改变数据库，只是将想法追加到日志中。当需要复杂推理或某些缓存记忆时使用。",
  "input_schema": {
    "type": "object",
    "properties": {
      "thought": {
        "type": "string",
        "description": "要思考的内容。"
      }
    },
    "required": ["thought"]
  }
}
```

**关键设计特征**：
- **无副作用**：明确声明不获取新信息、不修改系统状态
- **透明性**：思考内容出现在工具调用日志中，可供调试
- **最小化接口**：仅一个 `thought` 字符串参数

## 三、τ-Bench 评估：严格实验设计

### 3.1 评估框架

**τ-Bench（tau-bench）**专为测试 LLM 在真实客服场景中使用工具的能力而设计，评估三个核心能力：
- 与模拟用户进行真实对话
- 一致地遵循复杂客服策略指南
- 使用各种工具访问和操作环境数据库

**关键评估指标 pass^k**：
- 不同于 pass@k（k 次中至少一次成功），pass^k 衡量**k 次独立试验全部成功**的概率
- 这种指标在客服场景中更有意义——一致性比偶发成功更重要

### 3.2 航空域结果

| 配置 | k=1 | k=2 | k=3 | k=5 |
|---|---|---|---|---|
| 基准（无 think，无 ET） | 0.332 | 0.206 | 0.148 | 0.100 |
| Extended Thinking | 0.412 | 0.290 | 0.232 | 0.160 |
| "think" 工具（无 prompt 优化） | 0.404 | 0.254 | 0.186 | 0.100 |
| "think" 工具 + 优化 prompt | **0.584** | **0.444** | **0.384** | **0.340** |

**核心发现**：
1. "think" + 优化 prompt 在航空域的改进远超 Extended Thinking
2. 单独 Extended Thinking 和单独 "think" 工具（无 prompt 优化）性能相近
3. **Prompt 优化是航空域的关键杠杆**——策略越复杂，示例越重要

### 3.3 零售域结果

| 配置 | k=1 | k=2 | k=5 |
|---|---|---|---|
| 基准 | 0.783 | 0.695 | 0.583 |
| Extended Thinking | 0.770 | 0.681 | 0.548 |
| "think" 工具（无 prompt 优化） | **0.812** | **0.735** | **0.626** |

**有趣的不对称性**：零售域策略相对简单，仅凭"think" 工具（无 prompt 优化）就超过了基准和 Extended Thinking。这说明：
- 策略简单时，提供思考空间本身就足够
- 策略复杂时，还需要示例引导思考方向

## 四、优化 Prompt 的设计原理

航空域大幅提升的秘密在于 **prompt 中的示例**。这些示例向模型展示了在"think"工具中应该做什么类型的推理：

```
## 使用 think 工具

在收到工具结果后采取任何行动或回应用户之前，使用 think 工具作为草稿纸来：
- 列出适用于当前请求的具体规则
- 检查是否已收集所有必要信息
- 验证计划的操作是否符合所有策略
- 对工具结果进行正确性迭代

以下是在 think 工具中需要迭代的示例内容：

<think_tool_example_1>
用户想要取消航班 ABC123
- 需要验证：用户 ID、预订 ID、原因
- 检查取消规则：
  * 是否在预订 24 小时内？
  * 如果不是，检查票类和保险
- 验证没有已乘坐或过去的行程
- 计划：收集缺失信息，验证规则，获取确认
</think_tool_example_1>
```

**Prompt 工程洞见**：
- 示例帮助模型理解**推理的粒度**（多具体？多深入？）
- 示例展示了**决策树结构**（先检查什么，再验证什么）
- 示例为模型提供了**策略核对表模板**

## 五、SWE-Bench 上的表现

除 τ-Bench 外，"think" 工具还被集成到 SWE-Bench 评估中：

- 实验规模：n=30（有 think 工具） vs n=144（无 think 工具）
- 性能提升：**平均提升 1.6%**（Welch t 检验：p < 0.001，效应量 d=1.47）
- SWE-Bench 的 think 工具定义更具体，专注于代码理解和 Bug 修复场景

效应量（d=1.47）相当大，但平均提升仅 1.6%，这表明 think 工具在编码场景中**改善了稳定性**（减少极端失败），而非系统性提升所有任务。

## 六、深度辨析："think" 工具的本质

### 6.1 认知科学视角

"think" 工具从认知科学角度可理解为**外化工作记忆（Externalized Working Memory）**。

人类在面对复杂问题时，也需要"写下来"帮助思考——清单、草稿纸、白板。LLM 在处理长工具调用链时同样面临"工作记忆"压力：
- 之前哪些工具已调用
- 收集到了哪些信息
- 还缺少哪些信息
- 当前状态是否符合策略要求

"think" 工具提供了一个**持久化的中间状态缓存**，减轻了模型在下一次推理时需要从对话历史中重新推导中间状态的负担。

### 6.2 与 Chain-of-Thought 的关系

"think" 工具与 Chain-of-Thought（CoT）提示有内在联系，但存在重要区别：

| 特性 | CoT 提示 | "think" 工具 |
|---|---|---|
| 触发 | 通过 prompt 隐式引导 | 显式工具调用 |
| 时机 | 固定在响应开始 | **动态**，在需要时才触发 |
| 可见性 | 混在响应文本中 | 结构化工具调用，易于追踪 |
| 适用性 | 单步推理 | 多步工具调用链中的动态推理 |

"think" 工具本质上是**结构化的、按需触发的 CoT**。

### 6.3 工具调用开销的权衡

"think" 工具的主要代价是**额外的 token 消耗**：
- 每次"think"调用消耗工具调用 token
- 思考内容本身也占用 context 空间
- 但在复杂任务中，这种开销通常物有所值

## 七、何时使用，何时不用

### 适用场景

1. **工具输出分析**：需要仔细处理前一个工具调用的输出，并可能需要回溯
2. **策略密集环境**：需要遵循详细指南并验证合规性
3. **顺序决策**：每个行动都依赖于前一个，错误代价高

### 不适用场景

1. **非顺序工具调用**：仅需单次或多个并行调用时
2. **简单指令遵循**：约束少，默认行为已足够好时

## 八、实践建议

### 8.1 最小化实现（开始阶段）

```python
think_tool = {
    "name": "think",
    "description": "使用此工具在行动前进行结构化分析。不获取新信息，仅用于推理。",
    "input_schema": {
        "type": "object",
        "properties": {
            "thought": {"type": "string", "description": "分析内容"}
        },
        "required": ["thought"]
    }
}
```

### 8.2 System Prompt 中的引导模板

```
## 使用 think 工具的时机
在以下情况调用 think 工具：
- 收到工具结果后，验证信息完整性
- 做出不可逆操作前，核对所有策略规则
- 发现多条可能路径时，分析最优选择

示例推理结构：
1. 当前状态：已获得哪些信息
2. 缺失信息：还需要什么
3. 策略检查：当前计划是否合规
4. 下一步：最优行动是什么
```

### 8.3 监控与迭代

- 观察模型实际在 think 中写了什么，识别推理模式
- 若 think 内容质量低，可在 prompt 中提供更具体的示例
- 定期清理工具调用历史，避免 context 膨胀

## 九、结论

"think" 工具的价值在于其**简单性与有效性的极端不对称**：仅需定义一个无副作用的工具，就能为模型提供结构化推理空间，在复杂场景中带来显著的性能提升。

这一发现揭示了一个深层规律：LLM 在执行复杂工具调用链时，不仅需要工具来访问外部信息，还需要一种"内部记账"机制来维护推理状态。"think" 工具正是这种机制的最简实现。

随着 Extended Thinking 的不断完善，专用 think 工具的使用场景可能会进一步收窄，但其背后的核心洞见——**为模型提供显式的中间推理空间**——将持续指导 Agent 系统设计。
