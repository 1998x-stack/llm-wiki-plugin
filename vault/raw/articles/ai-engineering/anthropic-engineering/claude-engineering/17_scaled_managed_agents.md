# 可扩展的受管理 Agent：解耦"大脑"与"双手"

> **原文**：[Scaling Managed Agents: Decoupling the brain from the hands](https://www.anthropic.com/engineering/managed-agents)
> **发布日期**：2026 年（最新）
> **类别**：Agent 架构 · 可扩展性 · 系统设计

---

## 摘要

本文探讨了"受管理 Agent（Managed Agents）"架构——将 Agent 的推理能力（大脑）与工具执行能力（双手）解耦，分别独立扩展的系统设计模式。这种架构允许使用不同规模和专业化程度的模型处理推理和执行，在保持高质量输出的同时显著降低成本。

---

## 一、"大脑"与"双手"的分离

传统 Agent 设计中，一个模型承担所有职责：
- 理解任务（大脑）
- 规划步骤（大脑）
- 执行工具调用（双手）
- 处理结果（大脑）
- 决定下一步（大脑）

这种"全能模型"设计面临根本矛盾：大型、高能力模型适合推理但成本高；小型、快速模型适合简单执行但能力有限。

---

## 二、受管理 Agent 的架构

### 2.1 分层设计

```
战略层（Strategy Layer）
→ 大型推理模型（如 Opus 4）
→ 负责：任务理解、规划、决策
→ 调用频率：低

战术层（Tactical Layer）
→ 中型模型（如 Sonnet 4）
→ 负责：子任务规划、工具序列决策
→ 调用频率：中

执行层（Execution Layer）
→ 小型/专业化模型（如 Haiku 4.5）或确定性代码
→ 负责：具体工具调用、数据处理
→ 调用频率：高
```

### 2.2 接口设计

层间通信的关键是清晰的接口：

战略层 → 战术层：高层目标描述（"收集 S&P 500 IT 行业所有董事会成员信息"）

战术层 → 执行层：具体操作指令（"搜索 Apple Inc 董事会成员，返回 JSON 格式"）

执行层 → 战术层：结构化结果（包含成功/失败状态、原始数据、元数据）

---

## 三、扩展性的实现

### 3.1 独立扩展

解耦后，各层可以独立扩展：

- **推理负载增加**：扩展战略层实例
- **工具调用量增加**：扩展执行层实例
- **特定类型任务增加**：为特定领域创建专业化执行 Agent

### 3.2 成本优化

每次工具调用使用大型推理模型是巨大的成本浪费，受管理 Agent 架构允许：

- 搜索查询构建：战略层决策（需要高质量）
- 实际网络请求和解析：执行层（轻量任务）
- 结果综合：战略层分析（需要高质量）

实际成本可降低 60-80%，同时保持关键推理步骤的质量。

---

## 四、关键工程挑战

### 4.1 状态同步

受管理 Agent 的多层架构引入了状态同步挑战：
- 哪些上下文需要传递到哪一层？
- 如何避免信息重复传递（浪费 token）？
- 当执行层失败时，战术层如何得知并适应？

### 4.2 错误传播

在单 Agent 系统中，错误相对容易定位。在多层架构中：
- 执行层错误可能因延迟报告而在战术层累积
- 战术层的误解可能导致执行层的系统性错误
- 跨层的错误追踪需要统一的追踪 ID

### 4.3 延迟 vs 质量权衡

层次越多：
- 通信开销增加
- 但并行执行机会增加
- 总体延迟是权衡的结果

**最优配置**：任务复杂度越高，多层架构的收益越大。

---

## 五、与多 Agent 系统的对比

| 维度 | 受管理 Agent | 传统多 Agent |
|---|---|---|
| 层次结构 | 明确的层次 | 可以是扁平的 |
| 模型多样性 | 不同层使用不同大小模型 | 通常使用相同模型 |
| 扩展方向 | 各层独立扩展 | 整体扩展 |
| 成本优化 | 显著（匹配任务复杂度与模型能力） | 有限 |
| 设计复杂度 | 高（需要设计层间接口） | 相对低 |

---

## 六、实践建议

1. **先分析任务的计算分布**：找出哪些步骤需要高级推理，哪些是机械执行
2. **从两层开始**：先实现"规划层"和"执行层"，复杂度可控
3. **设计可观察的接口**：每层的输入/输出都应该有日志，便于调试
4. **逐步降低执行层的模型大小**：从安全的大模型开始，验证质量后再降级

---

## 七、结论

"解耦大脑与双手"是 AI Agent 系统走向工程成熟的重要一步。将高质量推理与高效工具执行分离，不仅降低了成本，更使系统具备了细粒度的扩展能力和更清晰的架构边界。

这种架构思想也反映了一个更普遍的工程原则：**不同的职责应该由最适合的组件处理，而非由单个组件承担所有职责**。
