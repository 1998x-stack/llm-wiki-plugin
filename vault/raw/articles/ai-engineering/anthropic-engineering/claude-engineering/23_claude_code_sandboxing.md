# 超越权限提示：让 Claude Code 更安全、更自主

> **原文**：[Beyond permission prompts: making Claude Code more secure and autonomous](https://www.anthropic.com/engineering/claude-code-sandboxing)
> **发布日期**：2025 年 10 月 20 日
> **类别**：Claude Code · 安全工程 · 沙箱

---

## 摘要

本文介绍了 Claude Code 的沙箱（Sandboxing）机制——通过 OS 级别的隔离，让 Claude Code 在更安全的环境中更自主地工作，同时减少对用户持续确认的依赖。文章深入探讨了沙箱设计的技术实现、安全边界定义，以及这一机制如何在安全性与自主性之间达到更好的平衡。

---

## 一、权限提示的局限性

默认的 Claude Code 权限模型在每个潜在危险操作时提示用户：

**问题一：用户疲劳**
长时间工作后，用户开始机械地批准而非真正审查，失去了安全屏障的实际意义。

**问题二：工作流中断**
频繁的中断破坏了 Agent 的连续工作流，降低了体验质量。

**问题三：权限粒度不匹配**
"允许所有文件操作"太宽泛，"逐一批准每个文件操作"太细粒度，用户需要中间地带。

## 二、沙箱机制的技术实现

### 2.1 分层安全架构

```
用户进程（Claude Code）
    ↕ 受限系统调用接口
沙箱层（系统调用过滤）
    ↕ 受控资源访问
OS 内核
```

### 2.2 文件系统隔离

沙箱允许 Claude Code 访问**预定义的目录**：

```
允许访问：
✅ 项目目录（/Users/user/myproject/）
✅ 临时目录（/tmp/claude-sandbox/）
✅ 只读系统路径（/usr/lib/、/usr/local/lib/）

禁止访问：
❌ 主目录根（/Users/user/ 但不在项目目录下）
❌ 系统目录（/etc/、/var/、/Library/）
❌ 其他用户目录
❌ SSH 密钥、密码文件等敏感路径
```

### 2.3 网络访问控制

```
允许：
✅ 访问指定的包管理器仓库（npm、pypi、cargo）
✅ 访问 Anthropic API（必需）
✅ 用户显式加入白名单的域名

默认禁止：
❌ 任意外部网络请求（防止数据泄露）
❌ 内部网络扫描（防止横向移动）
```

### 2.4 进程控制

```
允许：
✅ 生成子进程（用于运行测试、编译等）
✅ 在项目目录下的 git 操作

限制：
⚠️ 子进程继承父进程的沙箱限制
⚠️ 资源使用（CPU、内存、文件描述符）有上限

禁止：
❌ setuid/setgid（权限提升）
❌ 修改网络接口
❌ 访问原始设备
```

## 三、"授权范围"而非"逐操作审批"

### 3.1 设计哲学的转变

旧模型（逐操作审批）：
> 每次操作 → 提示用户 → 用户批准 → 执行

新模型（授权范围 + 沙箱）：
> 会话开始 → 用户定义工作范围 → 沙箱保证范围内的操作安全 → Claude Code 自主工作

**关键区别**：用户从"实时监督者"转变为"范围定义者"。

### 3.2 三种操作类别

```
类别 A：完全沙箱内（无需审批）
- 读写项目文件
- 运行测试
- npm install / pip install
- git commit / push

类别 B：需要确认（一次性）
- 访问未在项目目录内的文件
- 发出到新域名的网络请求
- 安装系统级软件

类别 C：始终禁止
- 修改系统配置
- 访问密钥/凭证文件
- 向不在白名单的外部服务发送数据
```

## 四、沙箱实现的技术选择

### 4.1 macOS：App Sandbox + seccompBPF

在 macOS 上，Claude Code 利用 Apple 的 App Sandbox 框架：
- 声明式权限模型（entitlements）
- 系统级执行保证

### 4.2 Linux：seccomp-BPF + namespace

在 Linux 上使用内核级机制：
- seccomp-BPF 过滤系统调用
- Linux namespace 隔离文件系统、网络、PID

### 4.3 性能影响

沙箱机制的开销：
- 文件访问：< 5% 开销（内核检查）
- 进程启动：~10ms 额外延迟（namespace 设置）
- 网络请求：< 1% 开销（路由规则检查）

对交互式使用几乎不可感知。

## 五、提示注入防御的沙箱维度

沙箱在防御 prompt injection 方面也有独特价值：

**场景**：Claude Code 读取一个包含恶意指令的文件，被操控尝试：
- 上传项目文件到外部服务器
- 修改系统配置
- 访问其他项目的代码

**沙箱的作用**：
- 网络请求 → 被拦截（未在白名单）
- 系统文件修改 → 被拦截（范围限制）
- 其他项目访问 → 被拦截（文件系统隔离）

即使 Claude 被注入的指令欺骗，底层操作也无法执行。

---

## 六、与 Auto Mode 的协同

沙箱机制与 Auto Mode 是互补的安全层：

| 机制 | 保护层次 | 阻止内容 |
|---|---|---|
| Auto Mode（分类器） | 语义层 | "这个操作超出了任务范围" |
| 沙箱 | 系统层 | "这个系统调用不被允许" |

两层叠加实现纵深防御：分类器阻止不合适的意图，沙箱阻止危险的实现。

---

## 七、结论

沙箱机制代表了 Claude Code 安全设计的重要进步：将安全保证从"用户持续监督"转移到"系统级执行约束"。这使得 Claude Code 能够在自主工作的同时保持安全性，而不需要用户承担持续审查的认知负担。

这种"安全即基础设施"的设计理念，是 AI Agent 从工具走向可靠助手的必经之路。
