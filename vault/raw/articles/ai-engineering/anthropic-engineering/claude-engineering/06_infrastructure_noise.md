# 量化 Agentic 编码评测中的基础设施噪声

> **原文**：[Quantifying infrastructure noise in agentic coding evals](https://www.anthropic.com/engineering/infrastructure-noise)  
> **发布日期**：2026 年（Featured）  
> **作者**：Gian Segato 及贡献者  
> **类别**：评测方法论 · 基础设施工程 · Benchmark 可靠性

---

## 摘要

本文通过严格的受控实验，量化了基础设施配置对 Agentic 编码评测基准（SWE-bench、Terminal-Bench 2.0）的影响。核心发现：在 Terminal-Bench 2.0 上，不同资源配置之间的成功率差距可达 **6 个百分点**（p < 0.01）——这超过了主流模型排行榜上顶级模型之间的差距。这是对 AI 评测方法论的一次重要警示，揭示了当前 Leaderboard 文化的严重可信度问题。

---

## 一、核心问题：Agentic 评测不是静态评测

### 1.1 静态评测 vs Agentic 评测

| 类型 | 特征 | 基础设施影响 |
|---|---|---|
| **静态评测**（如 MMLU） | 直接评分模型输出，运行环境不参与评分 | 几乎为零 |
| **Agentic 编码评测** | 模型在完整环境中写程序、运行测试、安装依赖、多轮迭代 | **显著且可量化** |

Agentic 评测中，"运行环境不再是被动容器，而是问题解决过程的核心组件"。

具体来说，两个资源配置不同的 Agent 实际上在"做不同的测试"——一个在贫资源下，一个在富资源下。

### 1.2 Terminal-Bench 2.0 的资源规范问题

Terminal-Bench 2.0 已在 2.0 版本中引入了每任务推荐的 CPU 和 RAM 规格。但文章指出：**规定资源 ≠ 一致执行**。

关键发现：**执行方法论会改变 benchmark 实际测量的内容**。

---

## 二、问题发现的偶然性

### 2.1 Anthropic 的内部场景

Anthropic 在 Google Kubernetes Engine（GKE）集群上运行 Terminal-Bench 2.0 时：
- 自己的分数与官方排行榜不匹配
- 基础设施错误率意外地高：**多达 6% 的任务因 Pod 错误失败**

大多数 Pod 错误与模型解题能力无关，而是容器资源问题导致的。

### 2.2 发现的根本原因

问题出在容器资源执行机制：

```
Linux 容器资源两个参数：
1. requests（保证分配）：预先保留的资源
2. limits（硬性上限）：超过则被终止（OOM Kill）

Kubernetes 严格执行（Anthropic 的初始配置）：
requests = limits → 零余量
任何瞬时资源波动超过上限 → 容器立即被终止

Terminal-Bench 官方排行榜的沙箱供应商配置：
允许临时超额分配，不立即终止容器
→ 基础设施稳定性更好，但评分方式实际上更宽松
```

## 三、受控实验：六种资源配置

### 3.1 实验设计

**控制变量**：相同的 Claude 模型、相同的 harness、相同的任务集

**变量**：资源配置，从严格执行（1×规格）到完全不限制（Uncapped）

六个配置：1x → 1.5x → 2x → 3x → 4x → Uncapped

### 3.2 核心实验结果

```
关键发现一：基础设施错误率随资源增加单调下降
1x:       5.8% 基础设施错误
→ 3x:     2.1% 基础设施错误（降低 63%，p < 0.001）
→ Uncapped: 0.5% 基础设施错误

关键发现二：成功率的两阶段行为
阶段一（1x → 3x）：成功率在噪声范围内波动（p=0.40）
  →  基础设施修复的任务多是"原本就会失败的任务"
阶段二（3x → Uncapped）：成功率跳跃 +4 个百分点
  →  额外资源真正帮助 Agent 解决了之前无法解决的任务

总提升：1x → Uncapped：+6 个百分点（p < 0.01）
```

### 3.3 两个阶段的本质区别

**3x 以下**：额外资源主要解决**基础设施可靠性**问题（容器被意外杀死）

**3x 以上**：额外资源开始帮助 Agent 采用**需要大量资源的解题策略**，如：
- 拉取 pandas、networkx、scikit-learn 等大型依赖库
- 生成昂贵的子进程
- 运行内存密集型测试套件

### 3.4 典型案例分析

**案例：`bn-fit-modify`（贝叶斯网络拟合）**

富资源策略：先安装标准 Python 数据科学栈（pandas + networkx + scikit-learn）→ 在资源充足时能成功

贫资源策略：在资源受限时，安装过程本身就会 OOM，被迫使用标准库从零实现数学

**关键观察**：不同模型对两种策略有不同偏好，资源配置决定了哪种偏好能成功——这意味着**不同资源配置在评测不同的模型能力**。

## 四、SWE-Bench 的交叉验证

为验证发现的普适性，文章在 SWE-Bench 上进行了交叉实验：

- 样本量：227 个问题，每题 10 次采样
- RAM 变化：1x → 5x
- **结果**：成功率随 RAM 单调增加
- **提升幅度**：5x vs 1x 仅高 **1.54 个百分点**

SWE-Bench 效应更小的原因：SWE-Bench 任务资源需求普遍较低，资源约束较少成为瓶颈。

**但重要结论相同**：资源配置对 SWE-Bench 也不是中性的。

## 五、其他噪声来源

基础设施噪声不仅来自资源配置：

- **时间效应**：通过率随一天中的时段波动（可能与 API 延迟的流量模式相关）
- **并发级别**：并发请求数影响响应时间
- **出口带宽**：网络带宽可能成为瓶颈
- **集群健康度**：集群整体状态影响所有任务

**关键洞见**："模型能力"与"基础设施行为"之间的边界比单一 benchmark 分数所暗示的**更加模糊**。

## 六、对 Benchmark 方法论的建议

### 6.1 最优方案（理想但难以实现）

在完全相同的硬件条件下运行所有评测——包括 eval scaffold 运行所在硬件和推理栈。

问题：对外部评估者来说难以实现（模型提供商可以专用硬件屏蔽这个问题，但第三方评估者无法做到）。

### 6.2 实际可行方案

**核心建议**：分别规定资源的"保证分配"（requests）和"硬性上限"（limits），而非单一固定值。

```
不推荐（当前实践）：
per_task_spec = {cpu: 2, ram: 4GB}  # requests = limits，零余量

推荐方案：
per_task_spec = {
    requests: {cpu: 2, ram: 4GB},    # 保证分配
    limits: {cpu: 2*3=6, ram: 4*3=12GB}  # 硬性上限（约为 3× requests）
}
```

**校准原则**：两者之间的带宽应使得：
- floor 和 ceiling 配置下的分数差异处于噪声范围内
- 在 Terminal-Bench 2.0 中，**3× 上限**是一个合理的起点：
  - 将基础设施错误率降低 2/3（5.8% → 2.1%，p < 0.001）
  - 成功率提升保持在噪声范围内（p = 0.40）

### 6.3 对不同利益方的建议

**模型实验室（如 Anthropic）**：
- 将资源配置作为第一类实验变量，与 prompt 格式、采样温度同等严格控制和记录

**Benchmark 维护者**：
- 像 Terminal-Bench 2.0 已做的那样发布推荐资源规格
- 进一步规定**执行方法论**（requests 和 limits 的比例关系）

**Benchmark 消费者**：
- 对 Leaderboard 分数保持适度怀疑
- 分差 < 3 个百分点时，不应轻易解读为能力差异

## 七、深度辨析

### 7.1 "分差 < 3% 应保持怀疑"的量化基础

文章给出了明确的量化阈值：

```
置信区间来源（叠加效应）：
1. 朴素二项置信区间：±1-2 个百分点
2. 本文记录的基础设施混淆因素：额外叠加于上方

总不确定性：仅适中资源范围内就接近 2 个百分点

Terminal-Bench 极端资源配置（1x → Uncapped）：差距高达 6 个百分点
```

这意味着当前排行榜上的小分差（1-3%）很可能处于基础设施噪声的范围之内。

### 7.2 资源配置对模型能力解读的影响

这篇文章揭示了一个深层问题：**不同的资源配置在测试不同的能力维度**。

- 严格资源约束：奖励高效、轻量级解题策略
- 宽松资源配置：奖励能利用丰富资源的暴力搜索策略

两者都是合理的测试目标，但将它们折叠进一个分数而不标注配置，使得分数难以与实际部署场景对应。

**工程实践影响**：如果你的生产环境资源受限，应该在受限配置下测试；如果环境资源充足，则应在充足配置下测试。

### 7.3 与传统软件测试的对比

传统软件测试中，"基础设施噪声"通常通过：
- 固定测试硬件（专用测试机）
- 环境隔离（容器化）
- 多次运行取平均

Agentic 评测在这方面的成熟度明显落后，本文的价值在于推动这一领域向工程严谨性靠拢。

## 八、实践价值

对于内部评测：
- 建立资源配置的"实验参数"记录习惯
- 对比不同配置下的分数差异，隔离基础设施效应

对于使用公开 Benchmark：
- 查阅 Benchmark 的资源规范和执行方法论文档
- 在解读排行榜时，将基础设施不确定性纳入误差估计

对于 Benchmark 维护者：
- 提供参考实现（含 requests 和 limits 的完整规范）
- 公开报告基础设施错误率

---

## 九、结论

这篇文章是 AI 评测方法论领域的一项重要贡献。其核心价值不在于否定 Benchmark 的作用，而在于揭示了一个被普遍忽视的混淆因素，并提供了量化估计和可行的工程建议。

> "一个 2 分的领先可能反映真实能力差距，也可能仅仅是一台更强的 VM。"

在"Benchmark 数字决定模型排名、模型排名影响资源分配"的当前生态中，这种警示具有重要的实际价值。
