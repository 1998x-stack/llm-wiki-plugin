# LLM 工程三阶段：对比分析与未来预测

> 从 Prompt Engineering → Context Engineering → Harness Engineering，
> 这是一条从"手工艺"到"工程学"再到"环境科学"的进化路径。

---

## 一、三阶段核心对比矩阵

### 1.1 基础维度对比

| 维度 | Prompt Engineering | Context Engineering | Harness Engineering |
|------|---------------------|----------------------|----------------------|
| **核心问题** | "怎么说，让 AI 听懂？" | "给 AI 什么信息，它才能做好？" | "设计什么环境，AI 才能持续做好？" |
| **操作对象** | 自然语言指令文本 | 上下文窗口中的信息内容与结构 | 代码库环境、约束系统、反馈循环 |
| **人类角色** | 指令设计师 | 信息架构师 | 环境架构师 |
| **AI 角色** | 执行单次任务的工具 | 在信息流中工作的助手 | 自主编码的主体 |
| **关注层次** | 输入端（Token 级别） | 信息流（系统级别） | 工程环境（组织级别） |
| **主要挑战** | 幻觉、不稳定、不可迁移 | 检索质量、上下文稀释、记忆管理 | 熵增、约束设计、人机协作边界 |
| **主要工具** | 文字编辑器、Playground | LangChain、LlamaIndex、向量数据库 | Claude Code、CI/CD、Linter、GC Agent |
| **可扩展性** | 差（每个任务手工调） | 中（管道可复用，但需持续维护） | 高（约束一次建立，持续生效） |
| **技术成熟度** | 成熟 | 成熟 | 新兴（2024–2025） |

### 1.2 技术机制对比

| 技术维度 | Prompt Engineering | Context Engineering | Harness Engineering |
|----------|---------------------|----------------------|----------------------|
| **核心机制** | 条件概率引导 `P(y｜prompt)` | 信息检索 + 上下文组装 | 机械约束 + 反馈循环 |
| **约束类型** | 软约束（语言描述） | 半软约束（结构化注入）| 硬约束（CI 门控，不可绕过） |
| **状态管理** | 无状态（每次独立） | 有状态（记忆系统） | 持久状态（代码库+文档是持久化状态）|
| **错误恢复** | 手动重新 Prompt | 检索修正/记忆更新 | CI 失败 → Agent 自动重试 |
| **质量保障** | 人工评估输出 | RAGAs 等自动评估 | linter + 测试 + GC Agent 自动 |
| **知识表示** | 自然语言 | 向量嵌入 + 结构化文档 | 代码 + 文档 + 约束规则（三位一体）|
| **并发能力** | 单轮 | 多轮对话 | 多 Agent 并行（需协调）|

### 1.3 价值主张对比

| 价值维度 | Prompt Engineering | Context Engineering | Harness Engineering |
|----------|---------------------|----------------------|----------------------|
| **主要价值** | 快速验证 AI 能力 | 让 AI 访问正确的领域知识 | 让 AI 持续、自主、规模化地产出 |
| **ROI 模型** | 低投入，低天花板 | 中投入，中天花板 | 高初始投入，指数级回报 |
| **规模化路径** | 靠人工叠加 Prompt 模板 | 靠检索管道和记忆系统扩展 | 靠约束系统和 GC 自动扩展 |
| **维护成本** | 高（模型更新后需重调） | 中（管道和索引需维护） | 低（约束一次建立，长期生效） |
| **失败模式** | 幻觉/格式错误/指令遗忘 | 检索失误/上下文稀释 | Agent 架构漂移/熵增 |

## 二、演化驱动力分析

### 2.1 每次跃迁的触发条件

```
Prompt → Context 的触发：
┌──────────────────────────────────────────────────┐
│ 触发条件 1：上下文窗口突破 4K → 128K             │
│   → "塞什么进去"变得比"怎么说"更重要             │
│                                                  │
│ 触发条件 2：LLM 推理能力提升，已不是瓶颈          │
│   → 问题转移到"信息质量"                         │
│                                                  │
│ 触发条件 3：企业级 RAG 需求爆发                   │
│   → 单次 Prompt 无法满足知识密集型场景            │
└──────────────────────────────────────────────────┘

Context → Harness 的触发：
┌──────────────────────────────────────────────────┐
│ 触发条件 1：Agent 能力跃迁，可以完成完整编码循环  │
│   → AI 开始替代人类成为"编码者"                  │
│                                                  │
│ 触发条件 2：规模化代码生成后的质量崩溃            │
│   → 没有约束的 Agent 产出"意大利面代码"           │
│                                                  │
│ 触发条件 3：OpenAI Harness 案例的示范效应         │
│   → 证明 100 万行/3 人/5 个月可实现               │
└──────────────────────────────────────────────────┘
```

### 2.2 共同演化主线

```
问题迁移路径（向右是问题解决后，新问题暴露）：

"怎么让 AI 理解指令？"
    → Prompt Engineering 解决
    → 新问题暴露：AI 缺乏领域知识，且知识过时

"怎么让 AI 获取正确知识？"
    → Context Engineering 解决
    → 新问题暴露：AI 能获取知识，但代码输出规模化后质量无法保障

"怎么让 AI 持续产出高质量代码？"
    → Harness Engineering 解决
    → 下一个问题（见未来预测部分）
```

## 三、三阶段叠加关系

**重要认知：三个阶段不是替代关系，而是叠加关系！**

```
Harness Engineering
    ↑ 包含并扩展
Context Engineering
    ↑ 包含并扩展
Prompt Engineering

现代最优实践 = 三层叠加：

Layer 3（Harness）：
  环境约束 + CI 门控 + GC Agent + 文档地图

Layer 2（Context）：
  RAG 检索 + 记忆系统 + 动态上下文组装 + MCP

Layer 1（Prompt）：
  System Prompt + 角色定义 + 输出格式 + CoT 诱导
```

## 四、关键指标对比

| 指标 | Prompt Engineering | Context Engineering | Harness Engineering |
|------|---------------------|----------------------|----------------------|
| **人均代码产出** | ~1x（基准）| ~3–5x | ~10–50x（OpenAI Harness 案例） |
| **质量保障方式** | 人工审核 | 人工审核 + 自动评估 | 机械约束 + 自动 GC |
| **上手时间** | 几小时 | 几天到几周 | 几周到几个月 |
| **最佳团队规模** | 个人/小团队 | 中小团队 | 任意规模（尤其适合小团队高产出）|
| **适用项目规模** | < 1 万行 | 1–10 万行 | 10 万行以上 |
| **对模型版本依赖** | 高（Prompt 常需重调）| 中（管道稳定，Prompt 需调整）| 低（约束独立于模型版本）|

## 五、未来预测：第四阶段及更远

### 5.1 可见的近期演化（2025–2026）

**趋势一：Harness 基础设施产品化**

```
当前：每个团队手工建 docs/_map.md，手写 linter 规则
未来：
  - Harness-as-a-Service：
    一键生成代码库 Harness 脚手架
    自动分析代码库，推荐约束规则
    GC Agent 作为托管服务
  - 类比：从手写 CI 脚本 → GitHub Actions 模板生态
```

**趋势二：多 Agent 协作标准化**

```
当前：单 Agent 线性工作
未来：
  - Agent 角色分工：
    Planner Agent → 分解任务
    Coder Agent   → 实现代码
    Reviewer Agent → 检查约束
    GC Agent      → 持续清理
  
  - 需要新的协调协议（超越 MCP）
  - 共享状态管理原语
```

**趋势三：自进化约束系统**

```
当前：人类设计约束规则，Agent 遵守
未来：
  Agent 分析代码库 bug 模式
  → 自动提议新的 linter 规则
  → 人类审批
  → 约束系统自我完善

  "约束由 Agent 学习，而非人类猜测"
```

### 5.2 中期预测（2026–2028）：第四阶段萌芽

#### 预测名称：**Organizational Engineering（组织工程）**

```
核心转变：
  不再是"设计代码库环境"，
  而是"设计人机协作的整个组织系统"

特征：
  - 软件研发组织本身被重新设计为"AI-native"
  - 人类专注于：目标设定、价值判断、伦理边界、战略方向
  - AI Agent 负责：研究、设计、实现、测试、运维、监控

新问题（将驱动第四阶段）：
  ① Agent 系统的目标对齐（Alignment at Scale）
  ② 多 Agent 系统的不可解释性（Interpretability）
  ③ AI 产出的知识产权与责任归属
  ④ 人类技能退化与核心竞争力重建
```

**第四阶段技术预测**：

| 技术方向 | 预测内容 |
|----------|---------|
| Agent 编排协议 | 超越 MCP，出现完整的"AI 工作流操作系统" |
| 形式化验证集成 | Agent 生成代码 → 自动形式化证明正确性 |
| 自适应约束 | 约束系统根据项目演进自动调整 |
| 跨组织 Agent 市场 | 专业领域 Agent 作为"API 服务"被订阅 |
| Harness OS | 专为 AI-native 开发团队设计的操作系统级工具链 |

### 5.3 长期预测（2028–2030+）：范式革命

#### 预测一：软件即意图（Software as Intent）

```
当前（Harness 时代）：
  人类写规格/约束 → Agent 写代码 → CI 验证

未来（Intent 时代）：
  人类表达意图（自然语言/UML/原型）
  → 意图编译器（AI）→ 形式化规格
  → 实现 Agent → 验证 Agent
  → 自动部署

  "从写代码 → 写意图"的最终完成
  代码变成中间态，不再是人类表达的终点
```

#### 预测二：自我演进软件系统（Self-Evolving Systems）

```
软件系统本身包含：
  - 目标规格（人类定义）
  - 约束边界（人类定义）
  - 实现演化能力（AI 负责）

运行中的系统：
  检测性能瓶颈 → Agent 优化实现
  发现 bug → Agent 自动修复
  用户行为变化 → Agent 调整策略

人类只需要维护"目标规格"和"约束边界"
```

#### 预测三：工程师角色的最终演变

```
2020（Prompt 时代）：
  工程师 = 主要编码者 + AI 辅助工具使用者

2023（Context 时代）：
  工程师 = RAG/记忆系统设计者 + 少量编码

2025（Harness 时代）：
  工程师 = 环境架构师 + 约束设计者

2027（Org Engineering 时代）：
  工程师 = 目标设定者 + AI 系统监督者

2030+（Intent 时代）：
  工程师 = 领域专家 + 意图表达者
  （"工程师"这个职位名称本身可能消失）

  技术专家的稀缺性从"会写代码"
  转移到"理解复杂系统的因果关系和边界条件"
```

### 5.4 风险与反力量预测

| 风险维度 | 预测 | 缓解路径 |
|----------|------|----------|
| **技能空心化** | 新一代工程师可能不懂底层原理 | 基础教育重新强调"理解"而非"实现" |
| **约束系统失效** | Agent 找到约束漏洞 | 形式化验证 + 对抗性测试 |
| **对齐漂移** | 长期运行的 Agent 系统目标偏移 | 持续对齐监控 + 人类审计层 |
| **集中化风险** | 少数 AI 平台控制大多数软件产出 | 开源 Harness 工具链生态 |
| **责任真空** | AI 生成的 bug 由谁负责？ | 法律框架更新（进行中）|

## 六、总结：三阶段的本质跃迁

```
┌─────────────────────────────────────────────────────────────────┐
│                    三阶段本质对比                                  │
├────────────────────┬────────────────────┬────────────────────────┤
│ Prompt Engineering │ Context Engineering│ Harness Engineering    │
├────────────────────┼────────────────────┼────────────────────────┤
│ 本质：             │ 本质：             │ 本质：                  │
│ 操控语言           │ 操控信息           │ 操控环境                │
├────────────────────┼────────────────────┼────────────────────────┤
│ 隐喻：             │ 隐喻：             │ 隐喻：                  │
│ 厨师（调味）       │ 图书馆员（选书）   │ 赛道设计师（建护栏）    │
├────────────────────┼────────────────────┼────────────────────────┤
│ 瓶颈：             │ 瓶颈：             │ 瓶颈：                  │
│ 模型能力上限       │ 检索/记忆质量      │ 约束设计能力            │
├────────────────────┼────────────────────┼────────────────────────┤
│ 核心资产：         │ 核心资产：         │ 核心资产：              │
│ Prompt 模板库      │ 知识库+检索管道    │ 约束系统+文档地图       │
├────────────────────┼────────────────────┼────────────────────────┤
│ 人类稀缺性：       │ 人类稀缺性：       │ 人类稀缺性：            │
│ 表达能力+领域知识  │ 系统设计+数据工程  │ 架构判断+约束设计       │
└────────────────────┴────────────────────┴────────────────────────┘

三阶段共同揭示的深层规律：
    随着 AI 能力提升，
    人类工程师的价值不断从"执行"向"设计"迁移，
    最终从"设计代码"迁移到"设计系统"，
    再到"设计系统中的规则"，
    最终到"设计系统中规则的规则"（元设计）。

这不是工程师的消亡，
而是工程师的升华。
```

> **最后的预言**：
> 
> 未来最稀缺的工程能力，不是会写代码，不是会设计 RAG，
> 也不是会设计 Harness 约束——
> 
> 而是**理解"什么值得被构建"**，
> 以及**用清晰的意图和边界表达这个理解**。
> 
> 这是人类最持久的优势，也是 AI 最难习得的能力。
