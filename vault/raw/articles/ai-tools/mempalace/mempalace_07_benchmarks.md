# MemPalace 深度解析（七）：Benchmark 深度解析

> 96.6% 是怎么来的？架构进化的完整实验记录

---

## 0. 数字背后的故事

MemPalace 的宣传核心是这个数字：**LongMemEval Recall@5 = 96.6%**，据称超过了 Mem0（~85%）和 Zep（~85%）。

但这个数字背后，有一段值得深入研究的实验历史。MemPalace 在 `benchmarks/BENCHMARKS.md` 中罕见地公开了整个架构迭代过程——包括失败的尝试。

这不仅是一份测评报告，更是一份**RAG 架构演化的第一手工程记录**。

---

## 1. LongMemEval：测什么？

**LongMemEval** 是专门测试 AI 长期记忆能力的基准数据集，特点：

- 包含多轮、跨会话的长对话记录
- 问题需要跨多个历史会话才能回答
- 核心指标：**Recall@K**——在返回的 Top-K 结果中，有多少比例包含了正确答案

**Recall@5** 的含义：返回 5 个候选 Drawer，正确答案在其中的概率。

**LoCoMo** 是另一个用到的数据集，专注于人际关系和个人历史的长期记忆场景。

## 2. 架构迭代史：从失败到 96.6%

### 基线：扁平向量搜索

```
架构：所有内容存入 ChromaDB，无任何组织结构
方法：直接向量搜索
结果：R@5 = 60.9%
问题：无法区分相关度，全局搜索噪声太大
```

这就是"朴素 RAG"的天花板。60.9% 意味着接近 40% 的时间，正确答案不在 Top-5 里。

---

### Architecture v1：LLM 路由 + 全局分类

```
架构：
  索引时：Haiku 模型给每个会话分配 Room 标签
  查询时：Haiku 模型把问题路由到 1-2 个 Room
方法：LLM 决定路由
结果：R@5 = 34.2%，62.5% 的查询零召回
问题：索引时的 Room 标签和查询时的路由词汇不匹配
      两次独立的 LLM 调用没有共享上下文
```

**这是 v1 的灾难性失败**：比朴素基线还低 26 个百分点。

根因分析：两个独立的 LLM 调用（索引期 vs 查询期）产生了**词汇不匹配**问题。索引时 Haiku 把某个会话标记为"relationship_advice"，查询时 Haiku 把同一个问题路由到"personal_guidance"——这两个标签的向量相似度不够高，导致路由失败。

**教训：用 LLM 做双端路由，必须保证两端共享同一套词汇体系。**

---

### Architecture v2：关键词路由（去掉查询期 LLM）

```
架构：
  索引时：同 v1（Haiku 生成 Room 标签）
  查询时：用关键词重叠度（而非 LLM）路由到 Room
          关键词来自各 Room 的聚合摘要文本（与索引用的文本相同）
方法：无 LLM 查询路由
结果：R@5 = 75.6%（R@10 = 84.8%）
改进：+ 14.7pp（vs v1），+ 15pp（vs 基线）
```

去掉查询期的 LLM，改用关键词重叠度（词频统计），把问题和各 Room 摘要做匹配。由于索引期和查询期都用同一批文本，词汇匹配度大幅提升。

但仍然有 4.1pp 的差距没补上（vs 后来的混合方案）。

---

### Architecture v3：宫殿结构 + 混合搜索

```
架构：引入 Wing/Room 层级，混合向量搜索 + 关键词搜索
方法：宫殿结构路由 → 混合搜索（BM25 + 向量）
结果（LoCoMo 数据集）：
  R@10 = 88.9%（超过 Memori 的 81.95%，+7pp）
  R@5 = 未公开
```

关键改进：引入 BM25 关键词搜索与向量搜索的混合，两者互补：
- 向量搜索捕捉语义相似性（"体力劳动" ≈ "搬东西"）
- BM25 捕捉精确词匹配（"token"这个词不该被语义泛化为"钱"）

---

### Architecture v4-v5：精准 Bug Fix

v3 之后的两个版本，重点在修复特定类型的检索失败。官方在 BENCHMARKS.md 中记录了三个具体的 Fix：

**Fix 1：精确短语引号提取**

失败案例：问题包含引号短语 `'sexual compulsions'`，对应会话里有这个精确短语，但向量搜索因为语义偏移没找到。

修复：识别问题中的单引号包裹短语，为包含该精确短语的会话施加 60% 距离缩减（强制提升排名）。

效果：目标会话从"未排名"跳到 **排名第 1**。

**Fix 2：人名权重增强**

失败案例：问题"Rachel 和 ukulele 是什么时候的事"，向量模型给人名的权重不够高。

修复：从问题中提取大写专有名词，为包含该名词的会话施加 40% 距离缩减。

效果：目标会话从"未排名"跳到 **排名第 2**。

**Fix 3：记忆/怀旧模式识别**

失败案例：问题关于高中聚会偏好，答案在一段包含 "I still remember the happy high school experiences" 的会话里，但向量搜索没抓到。

修复：增加记忆/怀旧关键词模式列表，触发时提升相关会话排名。

---

### 最终架构：Hybrid v5

```
组件：
  1. 宫殿结构路由（Wing/Room 层级导航）
  2. 向量搜索（ChromaDB 默认 embeddings）
  3. BM25 关键词搜索
  4. 精确短语引号提取 + 距离缩减
  5. 人名权重增强
  6. 记忆/怀旧模式识别

结果（LongMemEval）：R@5 = 96.6%
```

**34% 的提升分解**：

```
60.9% （朴素向量搜索）
  +34.1pp 来自宫殿结构（路由精准化）
  ≈ 94.8% （结构化检索基线）
  + 1.8pp 来自混合搜索 + 三项 Fix
= 96.6% （最终结果）
```

## 3. 最重要的发现：原文存储 > AI 提取

MemPalace BENCHMARKS.md 中最值得所有 AI 工程师注意的段落：

> "Every competitive memory system uses an LLM to manage memory... They all start from the assumption that you need AI to decide what to remember. MemPal's baseline just stores the actual words and searches them with ChromaDB's default embeddings. No extraction. No summarization. No AI deciding what matters. And it scores 96.6% on LongMemEval."

**核心结论**：

| 方案 | LongMemEval R@5 |
|------|----------------|
| MemPalace（原文模式） | 96.6% |
| Mem0 | ~85% |
| Zep | ~85% |
| MemPalace（AAAK 模式） | 低于 96.6%（官方承认） |
| MemPalace（Rooms 模式单独） | 低于 96.6%（官方承认） |

**AAAK 模式和 Rooms 模式的分数低于原文模式**——这是官方诚实披露的信息。96.6% 的成绩来自最朴素的"存原文 + 好的结构化检索"组合，而不是来自 AAAK 压缩或 Room 分类这些复杂功能。

这意味着：**AAAK 和 Rooms 的价值不在于提升召回率，而在于降低 Token 消耗和提升 Agent 的工作效率**。两者服务于不同的目标。

## 4. 社区的质疑与官方回应

MemPalace 发布数小时后，社区就在 README 中发现了问题，官方当天更新并公开承认：

**质疑 1：AAAK 节省 token 的声明有误**

原始 README 用 `len(text)//3` 估算 token 数，而非真实分词。

官方修正：
> "使用 OpenAI 分词器的真实统计：英文示例 66 tokens，AAAK 示例 73 tokens。AAAK 在小规模场景不省 token——它是为大规模重复实体设计的。"

**质疑 2：96.6% 是在哪种模式下测的**

官方澄清：96.6% 来自**原文逐字存储模式**，AAAK 模式和 Rooms 模式分数更低，但官方未公开具体数字。

**质疑 3：Benchmark 的可复现性**

官方回应：`benchmarks/` 目录下有完整的运行器脚本，可以自行复现。

这种"承认错误并当天修正"的透明度，反而赢得了社区好感，是开源项目处理争议的范本。

## 5. 对 AI 工程师的启示

**启示 1：别低估"朴素方案"**

60.9% → 96.6% 的跃升，70% 来自**宫殿结构**（层级路由），而不是来自 LLM 提取、摘要、重排。在把系统复杂化之前，先试试把数据组织好。

**启示 2：向量搜索 + BM25 是黄金组合**

两者各有盲区，混合使用几乎总是优于单用一种。LongMemEval 上的结果再次验证了这个已知结论。

**启示 3：针对性 Fix 有奇效**

三个专项 Fix（引号提取、人名权重、怀旧模式）加在一起贡献了约 1.8pp 的提升，对于高精度场景来说意义重大。系统性分析失败案例，往往比全面升级架构更高效。

**启示 4：两端 LLM 路由要共享词汇**

v1 的失败是一个经典的工程教训：索引期和查询期如果用两个独立的 LLM 调用做路由决策，必须确保它们使用相同的分类词汇。最安全的方式是 v2 的思路——查询期改用确定性匹配。

**启示 5：公开失败，和公开成功一样重要**

MemPalace 的 BENCHMARKS.md 记录了 v1 的 34.2% 失败和 v2、v3 的逐步提升。这种透明度比只展示最终数字更有学习价值。
