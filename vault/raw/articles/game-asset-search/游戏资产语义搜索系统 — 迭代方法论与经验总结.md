**3. 核心方法论**

**3.1 多通道召回 + 加权 RRF 融合**

**架构模式**: 每个检索通道独立排序，通过 Reciprocal Rank Fusion 合并结果。

|  |
| --- |
| Plaintext Score(doc) = Σ (channel\_weight / (k + rank\_in\_channel)) |

**通道设计原则**:

* 每个通道应覆盖不同的"语义空间"，互为补充
* 稠密向量通道（BGE/CLIP）：捕获语义相似性，处理同义词、口语化表达
* **文本编码器选型**: 专用文本 embedding 模型（如 BGE）优于跨模态模型的文本端（如 CLIP text）。CLIP 的文本编码器为对齐图像空间而训练，文本-文本匹配不是其强项
* 稀疏匹配通道（BM25）：精确关键词匹配，高置信度信号
* 跨模态通道（图像）：作为辅助验证，权重不宜过高

**权重调优经验**:

|  |  |  |  |
| --- | --- | --- | --- |
| 通道 | 特征 | v11推荐权重 | v12最优权重 |
| BM25 关键词 | 精确匹配最强信号，判别力最高 | 0.45 | **0.53** |
| 文本语义 (BGE) | 语义泛化能力强，口语化查询主力 | 0.45 | **0.45** |
| 图像跨模态 (CLIP) | 判别力为负值，应极低权重 | 0.10 | **0.02** |

**权重调优方法**:

1. ~~手动分析~~（v11之前）→ **基于判别力自动推导**（v12）
2. v12 方法：对每个通道计算 discriminative power = (mean\_correct - mean\_wrong) / std\_all
3. BM25 power=0.27 > TEXT power=0.23 >> IMAGE power=0.01（负值被截断）
4. 按 power 归一化得到最优权重，无需手动调参

**关键发现（v12 通道判别力分析）**:

* BM25: correct\_mean=10.32, wrong\_mean=8.81, gap=1.51 → 最强判别信号
* TEXT: correct\_mean=0.620, wrong\_mean=0.603, gap=0.017 → 有效但较弱
* IMAGE: correct\_mean=0.438, wrong\_mean=0.461, gap=**-0.024** → **负判别力**（正确答案反而得分更低）

**3.2 Query Understanding (QU) vs Query Rewriting (QR)**

**早期发现（v3, qwen2.5:0.5b）**: Query Rewriting 效果不稳定 — 小模型容易过度泛化，丢失关键词。

**v7 重新验证（qwen3.5-plus）**: 换用更强的大模型后，Query Rewrite 效果显著改善，与 QU 各有所长：

|  |
| --- |
| Plaintext QU 输入: "那个背上有炮的大乌龟" QU 输出: {"object": "水箭龟", "synonyms": ["乌龟"], "features": ["炮", "背部武器", "大型"], "category": "怪物"}  QR 输入: "猪头人身的怪物" QR 输出: "猪人 猪头怪 拟人化猪 怪物 游戏角色 野猪人 半兽人" |

**QU vs QR 对比（v7, 70条测试集, qwen3.5-plus）**:

|  |  |  |
| --- | --- | --- |
| 维度 | QU (结构化提取) | QR (查询改写) |
| Hit@1 | **0.8000** | 0.7857 |
| Hit@3 | 0.9286 | **0.9571** |
| Hit@5 | **1.0000** (完美召回) | 0.9714 |
| MRR | 0.8752 | **0.8761** |
| NDCG@3 | 0.8774 | **0.8887** |
| 实现复杂度 | 高（JSON解析+字段拼接） | **低**（直接文本替换） |
| 失败模式 | JSON 格式错误 | 改写偏移 |

**结论**: QU 的优势在于**完美召回**（结构化字段展开同义词），QR 的优势在于**排序质量**（改写后 BM25 匹配更精准）。两者互补，推荐线上使用 QR（NDCG@3 最高，实现简单），对召回要求极高的场景使用 QU。

**关键经验**: 同一种方法在小模型(qwen2.5:0.5b)上失败不代表方法本身有问题 — 换用更强模型(qwen3.5-plus)后 QR 从"退化"变为"最优排序"。模型能力是 LLM-in-the-loop 搜索系统的瓶颈。

**v12 QU vs QR 进一步验证（128条测试集, 657 prefabs）**:

|  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- |
| 配置 | Hit@1 | Hit@3 | MRR | vs Baseline | 耗时 |
| baseline | 0.5625 | 0.7891 | 0.6752 | — | 0.05s |
| qu-only | 0.5234 | 0.8047 | 0.6724 | -0.0028 | 1.45s |
| qr-only | **0.6016** | **0.8203** | **0.7263** | **+0.0511** | 1.27s |
| qr+qu | 0.5469 | 0.7969 | 0.6859 | +0.0107 | 2.58s |

**新发现（v12）**:

* QU 单独使用在大测试集上**反而有害**（MRR -0.0028），可能因为 JSON 解析偶尔出错引入噪声
* QR+QU 组合**不如 QR 单独使用**（MRR 0.6859 vs 0.7263），QU 的 BM25 查询增强反而干扰了 QR 已优化的查询
* 结论更新：在大规模评测中，**QR 是唯一值得使用的查询增强方案**

**QU Prompt 设计要点**:

1. 定义明确的字段 schema（object, synonyms, style, color, category, features, action）
2. 提供 6+ few-shot 示例，覆盖主要失败模式
3. 针对已知的"别名鸿沟"设计示例（水箭龟↔乌龟，曼珠沙华↔彼岸花）
4. 用 .replace("{query}", query) 避免 JSON 模板与 Python format 冲突

**BM25 查询增强策略**:

* 核心物体名 (object): 重复 2x（最强 boost）
* 同义词 (synonyms): 重复 2x（关键桥梁）
* 风格/颜色/类别/特征/动作: 各 1x

**3.3 文本编码器选型：BGE vs CLIP Text**

v5 将文本通道从 Chinese CLIP text encoder 替换为 BAAI/bge-base-zh-v1.5，效果对比（40条原始测试集）：

|  |  |  |  |
| --- | --- | --- | --- |
| 指标 | CLIP text baseline | BGE baseline | Delta |
| Hit@1 | 0.8250 | 0.8250 | ±0 |
| Hit@3 | 0.9250 | **0.9500** | +0.0250 |
| Hit@5 | 0.9500 | **0.9750** | +0.0250 |
| MRR | 0.8854 | 0.8842 | -0.0012 |
| NDCG@3 | 0.8748 | **0.8973** | +0.0225 |

**关键改进**: BGE 在无 QU 增强时就能解决部分 CLIP 无法匹配的 case（如"背上有炮的大乌龟"→水箭龟），说明 BGE 的中文语义理解能力更强。

**选型原则**:

* 文本-文本检索：优先选择专用文本 embedding 模型（BGE, M3E, GTE 等）
* 文本-图像检索：只能用跨模态模型（CLIP）
* 混合架构：各通道用各自最优的编码器，不必统一

**3.4 Reranker 对比（v12 新增）**

v12 引入了检索后二次排序（reranker），在 3-channel RRF 初排后，对 top-30 候选进行精排：

**两种 Reranker 对比**:

|  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| Reranker | 方法 | Hit@1 | Hit@3 | MRR | vs No-Rerank | 耗时增量 |
| 无 Reranker | RRF 直出 | 0.6016 | 0.8203 | 0.7263 | — | 0s |
| DashScope BGE | API 调用 gte-rerank 模型 | 0.5938 | 0.8125 | 0.7226 | **-0.0036** | +0.25s |
| Prompt Reranker | qwen3.5-plus LLM 排序 | **0.7031** | **0.8750** | **0.7976** | **+0.0713** | +2.4s |

**关键发现**:

* **DashScope BGE reranker（gte-rerank）反而轻微降低了效果**。原因：BGE 重排器使用的是通用文本相关性，对游戏资产的领域知识不足（如"铁疙瘩手雷"→ 重排器不理解这是手榴弹）
* **Prompt reranker（qwen3.5-plus）大幅提升 +7.1% MRR**。原因：大语言模型具备游戏领域知识和中文口语理解能力，能够理解"像方块拼起来还能防身的石片"→"石质护甲"的语义映射
* Reranker 的核心价值在于**纠正初排中的语义鸿沟错误**，而非优化已经匹配的结果

**Prompt Reranker 设计**:

1. 输入：用户 query + 30 个候选的 name + doc\_text
2. 提示 qwen3.5-plus 按相关性排序，输出逗号分隔的名称序列
3. 按输出位置赋分：position 1 → score=1.0, position 2 → score=0.5, position 3 → score=0.333...
4. 用 rerank score 重排候选

**方法论启示**: 在垂直领域搜索中，**通用 embedding reranker < 大语言模型 reranker**。LLM 的领域理解力和跨语言映射能力是传统 reranker 不具备的。但代价是延迟从 1.3s 增加到 3.7s。

**3.5 A/B 评估框架**

**测试集设计**:

* 35 组资源 × 2 种查询（精确 + 口语化）= 70 条
* 测试集外置为 test\_cases.json，与代码解耦
* 每条标注 expected\_uuids（1-3 个正确答案）
* 精确查询：使用标准描述词（"蓝色卡通鲨鱼模型"）
* 口语化查询：模拟真实用户说法（"来条凶巴巴的大鲨鱼"）
* 覆盖多种类别：角色、怪物、动物、载具、武器、建筑、道具、家电、植物、机械

**评估指标**:

|  |  |  |
| --- | --- | --- |
| 指标 | 含义 | 侧重点 |
| Hit@1 | Top1 命中率 | 首选结果准确性（最关键） |
| Hit@3 | Top3 命中率 | 用户浏览前3条能找到的概率 |
| Hit@5 | Top5 命中率 | 召回覆盖度 |
| MRR | 平均倒数排名 | 正确结果排在多前面 |
| NDCG@3 | 归一化折损累积增益 | 多个正确答案的排序质量 |

**A/B 对比方法**:

* Baseline: 纯 3 通道 RRF（无任何查询增强）
* Enhanced: 同架构 + 待验证的增强模块
* 两组使用完全相同的 CLIP/FAISS/BM25 索引
* 逐 query 对比，标记 IMPROVED / REGRESSED / HIT / MISS

**Per-query 分析模板**:

|  |
| --- |
| Plaintext [IMPROVED] 一只巨大的会飞的虫子 - Baseline: hit@1=0 mrr=0.00 (BM25=0, CLIP排到暗影牛怪) - Enhanced: hit@1=1 mrr=1.00 (QU提取"飞蚁"→BM25命中) - 原因: QU将口语"虫子"映射到标准名"飞蚁" |

**3.6 分类别分析**

将查询按 precise/colloquial 分组统计，能发现：

* 口语化查询通常是改进空间最大的类别
* BM25 在精确查询上表现最好（关键词直接匹配）
* 语义通道在口语化查询上是主力（BM25 经常 score=0）

**3.7 Agent 渐进式披露（v7 实验）**

**设计思路**: 参考 RAG 架构，将搜索拆为两轮 LLM 推理：

* Round 1（粗排）: 从 13 个分类中选 1-3 个最相关的类别
* Round 2（精排）: 加载选中类别的参考文件，从中精选 top 3 资源

**实测结果（70条测试集）**:

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| Agent 后端 | Hit@1 | Hit@3 | MRR | Avg Time |
| qwen3.5-plus | 0.7857 | 0.8714 | 0.8238 | 3.35s |
| Claude haiku-4.5 | **0.8429** | 0.9143 | 0.8786 | 4.73s |
| v5 baseline (对照) | 0.7714 | 0.8714 | 0.8345 | 0.05s |

**核心问题 — 分类路由"一错全错"**:

Agent 的 Hit@5 被限制在 Hit@3 水平（只返回3个结果），且分类路由错误不可恢复：

|  |  |  |  |
| --- | --- | --- | --- |
| 失败案例 | 路由结果 | 正确分类 | 原因 |
| "那个背上有炮的大乌龟" | CAT-04(动物) | CAT-02/03(怪物) | 水箭龟是游戏怪物而非普通动物 |
| "像超级马里奥里面的毒蘑菇那种" | CAT-06(植物) | CAT-03(怪物) | 毒蘑菇在游戏里是怪物 |
| "身上流着岩浆的大龟" | CAT-01/04 | CAT-03(怪物) | 熔岩龟是游戏怪物 |

**结论**: Agent 的分类路由不适合有边界模糊的分类体系（怪物 vs 动物）。向量检索 + BM25 的"软匹配"比分类路由的"硬分类"更鲁棒。

**3.8 可插拔 LLM 后端设计（v7）**

**设计模式**: 将 LLM 调用抽象为 llm\_fn(prompt) → str 函数签名，QU 和 QR 均接受 llm\_fn 参数：

|  |
| --- |
| Python def understand\_query(query, llm\_fn=None): # QU def rewrite\_query(query, llm\_fn): # QR |

**已实现的后端**:

* call\_ollama\_chat(): 本地 Ollama（qwen2.5:3b），免费，0.5s/query
* call\_dashscope(): DashScope API（qwen3.5-plus），1.5s/query
* call\_claude(): Anthropic API（Claude haiku-4.5），5s/query

**DashScope 注意事项**:

* qwen3.5-plus 默认开启 thinking mode（reasoning tokens），单次调用可达 80-90s
* 必须设置 "enable\_thinking": false 以关闭思维链，降至 1-2s/query
* 模型名为 qwen3.5-plus（非 qwen3-plus），需通过 /v1/models 接口确认

**LLM 模型能力对搜索质量的影响**:

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| 模型 | 参数量 | QU Hit@5 | QR NDCG@3 | Avg Time |
| qwen2.5:3b (本地) | 3B | 0.9571 | N/A | 0.50s |
| qwen3.5-plus (API) | ~100B+ | **1.0000** | **0.8887** | 1.50s |

模型能力是 LLM-in-the-loop 搜索系统的第一瓶颈。

**4. 踩坑记录**

**4.1 技术陷阱**

|  |  |  |
| --- | --- | --- |
| 问题 | 原因 | 解决方案 |
| .format() 与 JSON 模板冲突 | Prompt 中的 {} 被 Python 当作格式化占位符 | 改用 .replace("{query}", query) |
| LLM 返回嵌套 list | qwen2.5:3b 有时输出 ["a", ["b"]] | 统一用 \_add() 辅助函数处理 str/list/None |

| DashScope 模型名错误 | qwen3-plus 返回 404，实际模型名为 qwen3.5-plus | 通过 /v1/models 接口查询可用模型列表 |
| Agent 分类路由错误不可恢复 | 怪物/动物边界模糊导致路由到错误类别，mrr=0 | 向量检索"软匹配"比分类路由"硬分类"更鲁棒 |
| CLIP 单视角 false negative | 某些 prefab 默认角度遮挡关键特征（如背部武器） | 4-view max scoring：编码 4 个视角，取 max similarity |
| BM25 缓存跨数据集污染 | build\_bm25\_index 从全局 INDEX\_DIR 加载旧缓存（657 docs vs 355 docs） | 为 BM25 添加 index\_dir 参数，按数据集隔离缓存 |
| 图像置信度阈值无效 | v11 测试 CLIP score 阈值(0.20/0.25/0.30)过滤低质量图像通道，但所有 CLIP 分数都 >0.30 | CLIP similarity 的绝对值范围与预期不同，阈值应基于实际分布设定 |

| CLIP 图像通道负判别力 | v12 分析发现正确答案的 CLIP 分数（0.438）反而低于错误答案（0.461） | 图像通道权重应基于判别力分析设定，不能凭直觉给 0.10-0.20 |
| Hyphenated Python package name | prefab-search-v12 不是合法 Python 包名，from prefab\_search\_v12 import 失败 | 创建 symlink prefab\_search\_v12 → prefab-search-v12 |
| CLIP 融合方法差异极小 | 4 种融合方法的判别力 gap 仅差 0.001-0.003，在 IMG 权重 0.02 下对最终结果无实质影响 | 当通道权重接近零时，优化通道内部实现 ROI 极低 |
| Reranker 候选数过多降质 | K=30 让 LLM 在噪声候选中排序，反而比 K=10 差 | LLM reranker 的最优候选数需要实验确定，不能想当然用大值 |
| UUID-strict 低估同名变体资源 | "绿叶大树"有 40 个 UUID 变体，只标注 1 个导致其余 39 个被判为错误 | 使用 name\_to\_uuids 映射扩展期望集，或改用 Name-based 评估 |

**4.2 方法论陷阱**

|  |  |
| --- | --- |
| 陷阱 | 教训 |
| "加模块一定更好" | Query Rewriting 反而降低了 Hit@1，过度泛化 |
| "端到端改写更优雅" | 结构化 QU（只做加法）比端到端改写更稳定 |
| "图像通道应该很有用" | 实际上图像通道噪声最大，权重不能超过 0.20 |
| "通道越多越好" | 每个通道有信噪比，低SNR通道需要低权重或不如不加 |
| "用同一个模型处理所有通道" | 每个通道的任务不同，应选各自最优的编码器 |
| "测试集越大越好" | 扩充测试集会暴露更多边界问题，但也会拉低指标，需区分"系统变差"和"发现了更多难case" |
| "精确匹配一定比模糊匹配好" | ES-style 字段精确匹配反而不如 BM25 分词模糊匹配，召回是搜索系统的底线 |
| "小模型失败=方法失败" | QR 在 qwen2.5:0.5b 上退化，但在 qwen3.5-plus 上成为最优排序方法。模型能力是瓶颈 |
| "分类路由比向量检索更精准" | Agent 分类路由的"硬分类"在边界模糊场景下不如向量检索的"软匹配"鲁棒 |
| "API大模型一定值得" | Agent+Claude(Hit@1=0.8429)比v5+QR(NDCG@3=0.8887)贵10x慢3x，但综合指标并不更优 |
| "算法优化是最重要的" | 4-view 描述带来 +138% Hit@1，远超所有算法改进（QU/Rewrite 最多 +10%）。**数据 > 算法** |
| "同时改多个变量也能归因" | v8 同时改了描述+语料库大小，无法归因。v10 控制变量实验证明了描述质量是主因 |
| "QU+QR 组合一定更好" | v12 证明 QR+QU 组合(MRR=0.6859)不如 QR 单独使用(MRR=0.7263)。QU 的 BM25 增强干扰了 QR 已优化的查询 |
| "专用 reranker 模型一定优于通用 LLM" | DashScope BGE reranker(gte-rerank) MRR 反降 0.004，而 qwen3.5-plus prompt reranker 提升 +0.071。LLM 的领域理解力 > embedding 模型的向量相似度 |
| "图像通道至少有正向贡献" | v12 通道判别力分析证明图像通道的判别力为**负值**（correct < wrong），应近乎关闭（0.02） |
| "调参需要手动网格搜索" | v12 通道判别力分析可自动推导最优权重，且效果（MRR=0.8081）优于手动调参（MRR=0.7976） |
| "CLIP 融合方法可以拯救图像通道" | v13 测试 4 种融合方法（max-score/mean/weighted-mean/element-max），判别力都是负值，差异 <0.002。当权重仅 0.02 时优化通道内部实现是边际递减的 |
| "Reranker 候选数越多越好" | v13 证明 K=10 比 K=30 更好（MRR +0.007）且更快（1.2s vs 2.7s）。LLM 在精炼上下文中排序更准，噪声候选反而干扰判断 |
| "快模型可以替代慢模型" | qwen-turbo 比 qwen3.5-plus 快 ~0.1s 但 MRR 降 5-6%，速度优势微不足道而质量损失显著 |
| "UUID 匹配就是搜索质量" | v13 双轨评估证明 40% 的"UUID 错误"实际是名称正确的变体匹配。对含同名变体的资产库，Name-based 指标更真实 |

**7. v6 实验：ES-style Field-Boosted BM25（已回退）**

**7.1 设计思路**

v5 的 QU 增强方式是将提取字段拼接回 BM25 query 字符串，依赖 BM25 分词器做模糊匹配。v6 尝试参考 Elasticsearch 的 multi\_match + field boost 思路：QU 提取的每个字段精准匹配文档的对应结构化字段，给予不同的 boost 权重。

|  |
| --- |
| Plaintext final\_bm25\_score = base\_bm25\_score + field\_boost\_score |

**Field Boost 匹配规则**:

|  |  |  |  |
| --- | --- | --- | --- |
| QU 字段 | 匹配文档字段 | Boost | 匹配方式 |
| object | name | 5.0 | 子串匹配 |
| object | tags | 3.0 | 精确包含 |
| synonyms | name | 4.0 | 子串匹配 |
| synonyms | tags | 2.5 | 精确包含 |
| category | category + subcategory | 2.0 | 子串匹配 |
| color | color\_theme | 2.0 | 子串匹配 |
| style | style | 1.5 | 子串匹配 |
| features | tags + description | 1.0 | 子串匹配 |
| action | description + use\_cases | 0.8 | 子串匹配 |

**7.2 实验结果（70条测试集）**

|  |  |  |  |
| --- | --- | --- | --- |
| 指标 | v5 Enhanced (QU拼接) | v6 Enhanced (Field Boost) | Delta |
| Hit@1 | 0.7857 | **0.8000** | +0.0143 |
| Hit@3 | **0.9000** | 0.8857 | -0.0143 |
| Hit@5 | **0.9571** | 0.9143 | -0.0429 |
| MRR | **0.8574** | 0.8686 | +0.0112 |
| NDCG@3 | **0.8537** | 0.8488 | -0.0049 |

**7.3 失败分析**

**根本原因**: 精确子串匹配丢失了 BM25 分词器的模糊匹配能力。

**典型失败 case**:

* QU 提取 object: "风车" → 文档名 "简易风力发电机" → **子串不匹配**（"风车"≠"风力发电机"）
* 而 v5 拼接方式下，BM25 分词器会将 "风车" 和 "风力" 做部分 token 匹配
* QU 提取 object: "矿车" → 文档名含 "矿车" → 子串匹配成功 → 但 BM25 原本也能匹配，field boost 的增量价值有限

**核心矛盾**: Field Boost 用精确子串匹配替代了 BM25 的 tokenized 模糊匹配，在 Hit@1 上略有提升（精确匹配更有信心），但在 Hit@3/Hit@5 上严重退化（丢失了分词器带来的近似召回）。

**7.4 结论**

|  |  |  |
| --- | --- | --- |
| 维度 | v5 QU 拼接 | v6 Field Boost |
| BM25 匹配方式 | 分词后模糊匹配 | 精确子串匹配 |
| 召回能力 | 更强（分词器覆盖近似词） | 更弱（子串必须精确命中） |
| 精确度 | 略低 | 略高（Hit@1 +0.0143） |
| 综合效果 | **更优**（召回是搜索系统的底线） | 不如 v5 |

**方法论启示**: 在小语料库搜索中，**召回优先于精确度**。用户更能接受"正确答案在前3"而非"前1精确但前5丢失"。BM25 的分词模糊匹配是宝贵的特性，不应被精确子串匹配替代。

*代码已备份为 prefab\_search\_v6\_backup.py，主代码回退至 v5 架构。*

**8. v5 扩充测试集暴露的新失败模式**

扩充 15 组 case 后新增的失败 query（baseline miss）:

|  |  |  |  |
| --- | --- | --- | --- |
| 查询 | 目标 | 失败原因 | 类型 |
| "踩上去会爆炸的东西" | 地雷 | 纯功能描述，无关键词命中 | 功能→实体鸿沟 |
| "方块风格巫师用的棍子" | 像素法杖 | "棍子"≠"法杖"，"巫师"非资源属性 | 别名+角色视角鸿沟 |
| "猪头人身的怪物" | 野猪人战士 | "猪头人身"是外观描述而非名称 | 外观描述→名称鸿沟 |
| "画了花纹的彩色鸡蛋" | 彩绘蛋 | "鸡蛋"≠"蛋"，"花纹"≠"彩绘" | 近义词匹配失败 |
| "紫色的龙的蛋" | 暗鳞龙蛋 | "暗鳞"在query中完全缺失 | 关键属性缺失 |
| "工厂里搬东西的机器手臂" | 极简工业机械臂 | 资源库中有多个机械臂，区分度低 | 低区分度+描述视角差异 |

**新发现的失败模式分类**:

1. **功能→实体鸿沟**: 用功能描述（"踩上去爆炸"）搜索物体（"地雷"），三个通道都很难命中
2. **外观→名称鸿沟**: 用外观描述（"猪头人身"）搜索标准名（"野猪人战士"）
3. **低区分度资源**: 多个相似资源（两个机械臂）导致精准排序困难
4. **生活化别名**: "鸡蛋"→"蛋"、"棍子"→"法杖"，日常用语与游戏术语的差距

这些失败模式比之前的更难解决，需要更丰富的同义词库或更强的 LLM（QU prompt 增加更多 few-shot）。

**9. v7 推荐方案**

基于 6 种方法的全面对比，推荐以下方案：

**线上推荐**: v5 + Query Rewrite (qwen3.5-plus, enable\_thinking=false)

* NDCG@3=0.8887（排序最优），Hit@3=0.9571
* 实现简单，不需要 JSON 解析
* 可降级：API 不可用时 fallback 到 baseline（0.05s）

**高召回场景**: v5 + QU (qwen3.5-plus)

* Hit@5=1.0000（完美召回）
* 适合推荐场景返回 5+ 候选

**离线/内网**: v5 + QU (Ollama qwen2.5:3b)

* 无需外部 API，本地运行
* 质量可接受（Hit@3=0.9143）

**11. v9: Multimodal Embedding (One-Peace/DashScope) + BM25**

**12. v10: 4-View vs 单图描述对比（控制变量实验）**

**12.1 实验设计**

v10 不是新架构，而是一个**控制变量实验**，回答核心问题：4-view 描述（qwen-vl-max 分析 4 个角度）是否真的比单图描述（Gemini 分析 1 张图片）更好？

**控制变量**:

* 语料库：355 交集 prefabs（同时存在于 old 和 new 数据中）
* 测试集：94 条有效测试用例（覆盖 12 个类别，CAT-06 植被因无交集数据排除）
* 图像通道：**相同的 4 张实际图片**（default + FrontView + SideView + TopView）
* 搜索算法：3-channel Weighted RRF（BGE=0.35, BM25=0.45, IMAGE=0.20）
* 唯一变量：**文本描述来源**

**实验变量**:

|  |  |  |  |
| --- | --- | --- | --- |
| 组别 | 描述来源 | 描述语言 | 描述视觉信息 |
| OLD | Gemini（单张图片） | 中文 | 单一角度 |
| NEW | qwen-vl-max（4张图片） | 中文 | 四角度综合 |

**12.2 技术增强：4-View Max Image Scoring**

v10 同时引入了图像通道的增强——从每个 prefab 1 个 CLIP 向量变为 4 个（每个视角一个）：

|  |
| --- |
| Plaintext 旧方案: FAISS index [N vectors] → 1 image per prefab 新方案: FAISS index [4N vectors] + view\_to\_prefab mapping → max(sim) across 4 views |

搜索时：

1. FAISS 返回 top-k×4 个向量结果
2. 按 view\_to\_prefab 映射聚合到 prefab 级别
3. 每个 prefab 取 4 个视角中的 **max similarity** 作为图像通道得分
4. 使用该 max score 进行 RRF 排名

此增强对 OLD 和 NEW 两组测试**同时生效**（均使用 4 张实际图片）。

**12.3 实验结果（94 测试用例，355 prefabs）**

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| 指标 | OLD (单图描述) | NEW (4-view描述) | Delta | 提升幅度 |
| Hit@1 | 0.2234 | **0.5319** | +0.3085 | **+138%** |
| Hit@3 | 0.3936 | **0.7872** | +0.3936 | **+100%** |
| MRR | 0.3262 | **0.6679** | +0.3418 | **+105%** |
| NDCG@3 | 0.3197 | **0.6833** | +0.3636 | **+114%** |

**12.4 分析**

**为什么 OLD 指标这么低（Hit@1=0.2234）？**

OLD 的测试用例是基于 NEW 描述生成的（colloquial Chinese queries），而 OLD 描述虽然也是中文但信息量少得多（仅从 1 张图片提取）。查询与 OLD 描述之间的语义鸿沟比与 NEW 描述之间更大。

**4-view 描述的具体优势**:

* 多角度信息互补：背部武器、侧面纹理、俯视比例等单图不可见的特征被捕获
* 更丰富的 tags/description：4 张图输入使 VLM 生成的结构化描述更全面
* BM25 关键词覆盖更广：更多特征词意味着更高的 BM25 命中率

**关键结论**:

***描述质量（数据层面）是搜索质量的第一瓶颈****。v7 时所有 LLM 增强方法（QU/Rewrite/Agent）加起来对 baseline 的提升不超过 +0.10 Hit@1，而换用 4-view 描述直接提升 +0.31 Hit@1。****数据 > 算法****。*

**12.5 方法论启示**

|  |  |
| --- | --- |
| 启示 | 说明 |
| **数据质量 > 算法优化** | 4-view 描述带来的提升（+138%）远超任何算法改进（QU/Rewrite 最多 +10%） |
| **多视角 VLM 描述值得投入** | 每个 prefab 多花 3 张图片的 API 调用，换来搜索质量翻倍 |
| **控制变量实验是必要的** | v8 同时改了描述和语料库大小，无法归因。v10 只改描述，证明了因果关系 |
| **4-view max image scoring** | 图像通道从单视角变为 max(4视角)，减少了角度不佳导致的 false negative |

**16.1 核心变化**

|  |  |  |
| --- | --- | --- |
| 实验 | 核心问题 | 结论 |
| Exp1: CLIP 图像融合 | 4种融合方法能否改善图像通道的负判别力？ | 否，所有方法判别力均为负值，差异极小 |

**16.2 实验一：CLIP 图像通道融合对比**

**背景**: v12 发现 CLIP 图像通道的判别力为负值（correct=0.438 < wrong=0.461），权重被压到 0.02。v13 探索 4 种多视角融合方法是否能改善这一问题。

**4 种融合方法**:

|  |  |  |
| --- | --- | --- |
| 方法 | 原理 | FAISS 索引 |
| Original (max-score) | 4 views × N 向量，搜索时 max 聚合 | 4N vectors |
| Mean Pooling | 4 views 取平均 → 1 vector per prefab | N vectors |
| Weighted Mean | 加权平均 (default=0.4, front=0.3, side=0.2, top=0.1) | N vectors |
| Element-wise Max | 逐元素取最大值 → 1 vector per prefab | N vectors |

**判别力分析结果**:

|  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- |
| 融合方法 | Correct Mean | Wrong Mean | Gap | Power | 最优IMG权重 |
| Original (4-view max) | 0.4377 | 0.4613 | -0.0236 | 0.01 | 0.02 |
| Mean Pooling | 0.4393 | 0.4623 | -0.0230 | 0.01 | 0.02 |
| Weighted Mean | 0.4395 | 0.4618 | -0.0223 | 0.01 | 0.02 |
| Element-wise Max | 0.3958 | 0.4216 | -0.0258 | 0.01 | 0.02 |

**Pipeline 指标（默认权重 BM25=0.53/TEXT=0.45/IMG=0.02）**:

|  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| 融合方法 | UUID Hit@1 | UUID MRR | Name Hit@1 | Name MRR | Bad(UUID) | Bad(True) |
| Original (4-view max) | 0.7422 | 0.8177 | 0.8438 | 0.8890 | 15 | 9 |
| **Mean Pooling** | 0.7422 | **0.8204** | 0.8359 | 0.8878 | **14** | **8** |
| Weighted Mean | 0.7344 | 0.8177 | 0.8359 | 0.8885 | 14 | 9 |
| Element-wise Max | 0.7266 | 0.8127 | 0.8359 | 0.8870 | 14 | 9 |

**关键发现**:

* 所有融合方法的判别力都是**负值**，差异微乎其微（gap 在 -0.022 ~ -0.026 之间）
* Mean Pooling 在 UUID MRR 上略优（0.8204 vs 0.8177），但仅 +0.003
* 在 IMG 权重仅 0.02 的情况下，融合方法的选择**对最终指标几乎无影响**
* 原因：CLIP text-to-image 的跨模态匹配本身就不够精确，融合方式无法从根本上解决这一问题

**方法论启示**: 当某个通道的权重已被压到接近零（0.02），优化该通道的内部实现（融合方法）是**边际递减**的。应该将精力放在权重更高的通道（BM25=0.53, TEXT=0.45）上。

**16.3 实验二：Reranker 候选数 × 模型速度矩阵**

**背景**: v12 的 Prompt Reranker 使用 qwen3.5-plus 对 top-30 候选精排，平均耗时 2.5s/query。v13 探索减少候选数和换用更快模型是否能在保质的前提下提速。

**2D 矩阵（4 候选数 × 2 模型 = 8 runs）**:

|  |  |  |  |  |  |  |
| --- | --- | --- | --- | --- | --- | --- |
| 模型 | K | UUID Hit@1 | UUID MRR | Name MRR | Rerank均值 | Rerank P95 |
| qwen3.5-plus | 30 | 0.7500 | 0.8164 | 0.8903 | 2.746s | 4.016s |
| qwen3.5-plus | 20 | 0.7500 | 0.8229 | 0.8910 | 1.766s | 2.693s |
| qwen3.5-plus | 15 | 0.7500 | 0.8191 | 0.8891 | 1.371s | 1.957s |
| **qwen3.5-plus** | **10** | **0.7578** | **0.8236** | **0.8913** | **1.218s** | **1.508s** |
| qwen-turbo | 30 | 0.6641 | 0.7636 | 0.8317 | 1.359s | 1.673s |
| qwen-turbo | 20 | 0.6797 | 0.7787 | 0.8461 | 1.081s | 1.616s |
| qwen-turbo | 15 | 0.6641 | 0.7741 | 0.8510 | 1.112s | 2.058s |
| qwen-turbo | 10 | 0.6953 | 0.7869 | 0.8559 | 1.232s | 2.716s |

**关键发现**:

1. **候选数少反而更好**: qwen3.5-plus K=10（MRR=0.8236）> K=20（0.8229）> K=15（0.8191）> K=30（0.8164）。原因：LLM 在面对更少候选时排序更精准，30 个候选中的噪声干扰了 LLM 的判断
2. **qwen-turbo 质量损失严重**: UUID MRR 下降 5-6%（0.82 → 0.77），速度提升有限（1.2s vs 1.1s at K=10），不值得
3. **最优配置**: qwen3.5-plus K=10 — 比 K=30 提速 56%（2.75s → 1.22s），质量反升 +0.007 MRR
4. **P95 延迟**: K=10 的 P95 仅 1.508s（vs K=30 的 4.016s），尾部延迟大幅改善

**方法论启示**:

* **"越多候选越好"是误区**: LLM reranker 不是 embedding reranker，候选多 ≠ 上下文多 ≠ 质量好。LLM 在精炼上下文中表现更好
* **模型质量不可替代**: qwen-turbo 的速度优势（~0.1s）远不足以弥补质量损失（-5% MRR）
* **Reranker 调优的 ROI 很高**: 仅调整一个参数（K=30→K=10）就同时提升了速度和质量

**16.4 实验三：双轨评估（UUID-strict vs Name-based）**

**背景**: 游戏资产库中 87 个名称对应多个 UUID（如"绿叶大树"有 40 个变体 UUID）。UUID-strict 评估会将"找到了正确名称但不同 UUID 的变体"判定为失败，可能低估搜索质量。

**整体对比**:

|  |  |  |  |
| --- | --- | --- | --- |
| 指标 | UUID-strict | Name-based | Delta |
| Hit@1 | 0.7344 | **0.8359** | **+0.1016** |
| Hit@3 | 0.8828 | 0.9297 | +0.0469 |
| Hit@5 | 0.8984 | 0.9375 | +0.0391 |
| MRR | 0.8147 | **0.8870** | **+0.0723** |
| NDCG@3 | 0.8229 | 0.8430 | +0.0201 |

**Bad Case 重新分类**:

15 个 UUID-strict 错误中：

* **6 个 uuid-only-bad（40%）**: 名称匹配正确，但返回了同名不同 UUID 的变体
* **9 个 true-bad（60%）**: 名称也不匹配，是真正的搜索错误

**受影响最大的类别**:

|  |  |  |  |  |
| --- | --- | --- | --- | --- |
| 类别 | UUID MRR | Name MRR | Delta | 原因 |
| CAT-06 (植被) | 0.2867 | 0.5667 | **+0.2800** | 树类资源（绿叶大树/绿冠大树/绿荫大树）有大量同名变体 |
| CAT-08 (建筑) | 0.6711 | 0.9500 | **+0.2789** | 木栅栏/石柱等建筑构件有多个变体 |
| CAT-10 (特效) | 0.6500 | 0.7667 | +0.1167 | 特效资源变体较多 |
| CAT-12 (家具) | 0.9000 | 1.0000 | +0.1000 | 家具有几组同名变体 |

**uuid-only-bad 典型案例**:

* "那种叶子很绿的大树" → 期望UUID对应某棵"绿叶大树"，但返回了另一棵同名"绿叶大树"
* "那种棕色的木头栅栏" → 返回了同名"木栅栏"的不同变体
* 这些在实际使用中**不应算作搜索错误**——用户搜"绿叶大树"，返回任何一棵绿叶大树都是正确的

**方法论启示**:

* **评估指标必须匹配业务需求**: UUID-strict 适合"精确找到特定资源"场景，Name-based 适合"找到某类资源"场景
* **同名变体是游戏资产库的常见特征**: 树木、栅栏、石柱等素材通常有多个外观相似的变体，严格 UUID 匹配会系统性低估搜索质量
* **推荐**: 以 Name-based MRR 作为主要评估指标，UUID-strict 作为辅助参考

**17. 适用场景**

本方法论适用于：

* 中文语义搜索系统（尤其口语化查询场景）
* 多通道混合检索系统的设计与调优
* 小型语料库（<10K 文档）的高精度搜索
* 需要支持别名/俗称/口语化表达的垂直领域搜索
* LLM-in-the-loop 检索系统的可插拔后端设计
* 含同名变体资源的资产库（推荐双轨评估）
