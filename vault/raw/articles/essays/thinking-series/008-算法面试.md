1. 多路召回的结果，你是怎么组织、怎么排序的？
2. 没有标注数据的时候，相似度阈值你定多少？筛选后没结果怎么办？

本文会完整拆解这场面试里的所有技术细节、行业真相，给所有想在AI行业落地的从业者，一份可直接复用的工业级指南。

## 一、RAG落地的核心：从多路召回到重排，工业级方案到底怎么做？
面试的前2分半，全程围绕一个核心问题：**多路召回的结果，到底该怎么处理？**

这是所有做RAG的人都绕不开的坎：你用了向量检索、关键词检索、知识图谱检索三路召回，每一路的评分标准都不一样，向量检索是0-1的余弦相似度，BM25是0到几十的关键词得分，怎么把这些结果合并、排序、筛选？

### 1. 排序的标准答案：RFF融合+重排模型，才是工业界标配
候选人给出的方案，是目前2026年RAG系统的绝对主流：**先RFF融合，再BG重排**。

这里先纠正一个面试里的口误：候选人说的「BG re rank模型」，其实是智源研究院开源的**BGE-Reranker系列重排模型**，也是目前中文场景下性价比最高的重排利器；而「RFF融合」，全称是**Reciprocal Rank Fusion（倒数秩融合）**，专门解决多路异构召回结果的融合难题。

#### （1）RFF融合：让不同召回通道“说同一种语言”
很多人做多路召回，最容易犯的错就是直接把不同通道的分数加权相加——但向量相似度和BM25分数的尺度完全不同，相加只会让结果更混乱。

RFF的巧妙之处在于：**它不看分数，只看排名**。
它的核心公式极其简单：
```
RRF_score(d) = ∑ 1 / (k + rank(d))
```
- `rank(d)`：文档在某一路召回结果中的排名（从1开始）
- `k`：常量，行业通用默认值为60，用于降低低排名文档的影响

举个例子：文档A在向量召回排第3，在BM25召回排第5，它的RFF得分就是`1/(60+3) + 1/(60+5) ≈ 0.0313`。

这个算法的优势极其明显：
- 无需训练、无需调参，完全无监督，天然适配异构召回通道；
- 能同时兼顾多路召回的优势，实测中混合召回+RFF融合，能把召回率从单路向量检索的85%提升到92%，同时准确率不降反升；
- 目前Elasticsearch等主流搜索引擎已经原生支持RFF，接入成本极低。

面试里候选人提到的「每一路选择1/3 TOPK再融合」，是RFF之外的备选方案，但缺点很明显：会丢失部分低排名但高相关的文档，召回率上限远低于RFF融合。

#### （2）BGE重排：RAG准确率的最后一公里
RFF融合之后，还有一个关键步骤：**重排**。

很多人会发现：明明召回了相关文档，大模型却还是答偏了。核心原因就是初筛结果里混着大量语义接近但逻辑无关的“噪音文档”，而重排模型，就是专门解决这个问题的“裁判员”。

BGE-Reranker采用Cross-Encoder架构，不是分别编码查询和文档再比距离，而是把查询和文档拼成一个完整序列输入模型，通过双向自注意力机制，逐词分析两者的语义匹配关系，最终输出一个0-1的相关性分数。

工业级的落地流程是：
1. 多路并行召回，每一路返回Top50的候选文档；
2. 用RFF融合所有结果，去重后得到Top20的候选集；
3. 将用户查询和这20个文档批量送入BGE-Reranker模型，重新打分排序；
4. 按最终分数筛选，送入大模型上下文。

实测数据显示，加入BGE重排后，RAG系统的MRR@10能提升37.2%，单点问题回答准确率能从80%提升到95%以上，和面试里候选人给出的项目数据完全吻合。

### 2. 筛选的灵魂拷问：阈值怎么定？没数据怎么办？
面试官紧接着问了一个所有RAG从业者都会遇到的问题：**阈值一般设多大？没有数据怎么办？**

这是一个极其考验工程能力的问题——论文里只会告诉你用余弦相似度，但不会告诉你，真实业务里，固定阈值会害死你。

#### （1）阈值的设定：不是拍脑袋，而是数据驱动
候选人给出的默认阈值是0.78，这个数字不是凭空来的，而是工业界的标准实践：
- 用的模型是BGE-M3（面试里的M31是口误），这是目前中文场景下最主流的多语种、多粒度嵌入模型；
- 阈值的确定方法：先构建大量正例（同义句）和负例（无关句）测试集，人工标注相似和不相似，再构建相似度分数的直方图，找到正负例的分界点，最终确定阈值；
- 行业通用的分级标准：>0.85为极度相似，0.6-0.85为语义相关，<0.6为基本不相关，0.78刚好是高精度需求下，平衡召回率和精确率的最优值。

#### （2）没数据、没结果的终极解决方案：接受向量检索的局限性
面试官追问：如果按这个阈值筛选后没数据，怎么办？

候选人的回答戳中了本质：**单纯靠向量检索，这个问题是永远绕不开的**。

这是很多新手的误区：总想着靠调阈值、换模型，解决所有检索问题。但真实情况是，余弦相似度本身不具备绝对语义意义，它的分布受文本长度、领域、语言复杂度的影响极大，固定阈值永远无法适配所有场景。

工业界的成熟解决方案，从来不是死磕阈值，而是多路径兜底：
1. 阈值和TOPK双兜底：先按阈值筛选，若结果不足N条，直接取TOPK的结果补充，避免无内容可用；
2. 分块策略优化：纯检索的核心痛点是分块切断了文本之间的联系，所以要引入父子分块、语义分块，保留上下文关联；
3. 检索范式升级：从纯向量检索，升级为“向量+关键词+知识图谱”的三路检索，用知识图谱的多跳推理能力，解决纯检索无法覆盖的复杂问题；
4. 兜底方案：若所有检索都无结果，直接触发大模型的通用知识兜底，同时给用户明确提示“该内容暂无知识库支撑，以下为通用回答”，避免幻觉。

## 二、2026年AI编码的真相：工具链、Skill与MCP，你真的用对了吗？
面试的第二部分，从开发工具切入，聊到了2026年AI编码的核心范式，这部分内容，刷新了很多人对“AI写代码”的认知。

### 1. AI编码IDE选型：没有最好的，只有最适配的
候选人给出的工具链，是2026年开发者的主流选择：
- 开发语言：Python（算法开发的绝对主流）；
- IDE：之前用Cursor、VS Code，现在主要用Open Code、Cloud Code；
- 模型：复杂项目用Cloud Code搭配Claude Opus，小项目用Open Code搭配通义千问Code Max。

这里给大家做一个2026年主流AI编码IDE的核心对比，直接帮你做选择：
| IDE | 核心定位 | 核心优势 | 适合人群 |
|-----|----------|----------|----------|
| Cursor | AI原生编辑器（VS Code分支） | 与VS Code操作习惯完全一致，迁移成本为零，多文件重构能力强，中文支持优秀 | 从传统IDE转AI编码的所有开发者，中小型项目 |
| Cloud Code（Claude） | CLI+云端AI编码工具 | 深度集成Claude全系列模型，对大型项目的上下文理解能力极强，自带gunplan规划模式 | 企业级复杂项目开发，Claude生态用户 |
| Open Code | 开源CLI AI工具 | 本地优先、完全开源、轻量无冗余，支持多模型适配 | 开源爱好者，本地部署需求，极简主义开发者 |
| GitHub Copilot | VS Code插件 | 与github生态深度集成，PR自动审查功能实用 | VS Code重度用户，github生态企业开发者 |

很多人对AI编码的误区，是总想着找一个“万能工具”，但真实情况是：**CLI工具适合自动化、批量化的任务，IDE适合日常编码、调试，两者搭配才能效率最大化**。

### 2. Skill与MCP：90%的人都搞混了，用错了
面试官问了一个非常前沿的问题：**你用过哪些Skill和MCP？**

这两个概念是2025-2026年AI Agent开发的核心，但绝大多数人都搞混了。这里给大家讲透两者的本质区别，一句话总结：**MCP是USB接口，Skill是使用说明书+SOP**。

#### （1）MCP：AI与外部世界的标准化通信管道
MCP全称Model Context Protocol（模型上下文协议），是Anthropic提出的开放标准协议，核心解决的问题是：AI如何安全、统一地“伸手出去”，调用外部系统、工具、数据。

在MCP出现之前，每个AI应用连接数据库、API、文件系统，都要写专用的适配器，开发成本高、不兼容。而MCP就像USB-C接口，统一了AI和外部工具的通信语言，开发者只需要写一次MCP Server，任何支持MCP的Agent都能直接调用。

它的核心是**刚性的、确定性的API调用**，不涉及任何业务逻辑，只解决“连接”的问题。

#### （2）Skill：给AI封装的专家经验
Skill是结构化、可复用的Prompt+工作流包，核心解决的问题是：AI怎么专业地、符合规范地完成特定任务。

比如面试里候选人提到的：
- `planning with FILES`：让AI按照标准工作流，搭建项目文件结构，生成todo list，分步完成开发；
- 基于Playwright封装的网页爬取Skill：把爬虫的最佳实践、异常处理、文档规范都封装进去，AI只需要说“爬取这个网页”，就能按照预设的规范完成任务，而不是每次都从头写代码。

Skill的核心是**柔性的、可解释的专家经验固化**，它不提供新的工具能力，而是教AI怎么用好现有的工具，怎么符合业务规范，怎么少踩坑。

很多人用不好AI编码，核心原因就是：只知道让AI直接写代码，却没有给它封装好对应的Skill。没有规范和SOP，AI写出来的代码永远是“一次性玩具”，无法落地到生产环境。

### 3. AI时代的软件工程范式：从“代码优先”到“规格优先”
面试里有一个非常关键的细节：面试官提到了SDD（Spec-Driven Development，规格驱动开发），而候选人提到了OpenAI的Harness Engineering（驾驭工程，面试里的honeycomb是口误）。

这两个概念，恰恰代表了AI时代软件工程的范式跃迁：**从“先写代码，再补文档”，变成“先定义规格，让代码去满足规格”**。

#### （1）SDD规格驱动开发：AI编码的正确打开方式
很多人用AI写代码，都是直接说“帮我写一个XX系统”，结果写出来的东西完全不符合预期，改来改去比自己写还慢。核心原因就是：你没有给AI一个精确的、可执行的规格。

SDD的核心理念是：**规格即蓝图，契约即真理**。
在SDD中，系统的“规格”是唯一权威的、可执行的真理来源，它不是一份静态的Word文档，而是用结构化语言编写的、可被机器读取和验证的定义。

完整的SDD流程是：
1. Specify（定义规格）：明确系统的功能需求、非功能需求、接口规范、验收标准；
2. Plan（技术规划）：把规格翻译成技术架构、技术栈、实现路径；
3. Task（任务拆解）：把规划拆解成原子化的开发任务，生成todo list；
4. Implement（实现）：AI根据规格和任务，自动生成代码，人类只做终审。

这就是为什么面试里，候选人会用planning with FILES这个Skill——本质上，就是把SDD的流程，固化成了AI可执行的Skill。

#### （2）Harness Engineering：OpenAI用5个月写了100万行代码，核心秘密
候选人提到的Harness Engineering，是OpenAI在2026年初公布的颠覆性工程范式：他们用3人团队，5个月时间，从零构建了一款百万行代码的生产级产品，全程没有手写一行代码，所有代码都由Agent自主生成。

这个范式的核心，不是提示工程，而是**给AI搭建一个可以安全奔跑的“马具（Harness）”**，核心工作分为三件事：
1. 设计工程环境和架构约束：给AI定义严格的依赖方向、编码规范、黄金原则，就像给马套上缰绳，避免它乱跑产生技术债务；
2. 定义任务和意图：把高层目标拆解成AI可执行的构建块，用清晰的语言描述验收标准，也就是SDD的核心；
3. 创建反馈循环：建立自动化机制，让AI能够自我验证、自我评审、自我修复，比如让AI直接读取日志、复现Bug、验证修复效果。

这才是AI编码的终极形态：**人类不再是写代码的工人，而是定义规则和环境的设计者。AI的效率上限，从来不是模型的能力，而是你给它搭建的Harness有多完善**。

## 三、算法工程师的核心壁垒，从来不是会多少模型，而是工程思维
面试里有一个让我印象极深的细节：候选人是土木工程背景，面试官问他，你的数理逻辑和工程思维，主要体现在哪？

他的回答，戳中了当下AI行业最致命的问题：
“不是说方法越高级、越复杂，效果就越好。要适配它对应的任务：任务特别复杂，你就用对应的复杂Agent；任务简单，要求速度快、Token少，那就用最简单的方式达成。”

这句话，就是工程思维的核心。

现在AI行业里，90%的算法工程师都陷入了一个误区：沉迷于追最新的模型、最火的论文、最复杂的技术架构，却忽略了业务的本质需求。

- 一个简单的FAQ问答场景，明明用关键词检索+规则就能做到99%的准确率，非要上大模型+RAG，结果成本翻了10倍，准确率还下降了；
- 一个内部工具的开发，明明用SDD+AI编码一周就能上线，非要堆微服务、云原生架构，结果搞了3个月还没落地；
- 一个to B的业务场景，客户最看重的是稳定性、可解释性，非要上黑盒的大模型，结果出了问题根本无法排查。

土木工程的底层逻辑，和AI落地的工程思维，本质上是一模一样的：**不管黑猫白猫，抓到老鼠就是好猫。技术没有高低贵贱，能解决问题、控制成本、稳定运行的，就是好技术**。

我见过太多简历上写着“精通LLM、RAG、AIGC，发过顶会论文”的候选人，一到真实业务场景里，连最基本的“阈值怎么定”“出了问题怎么兜底”都答不上来。

2026年的AI行业，已经从“有没有”的时代，进入了“好不好”的时代。**会用模型、懂论文的人，已经严重过剩；能把AI从demo变成稳定赚钱的产品的人，永远稀缺**。

而后者的核心壁垒，从来不是技术深度，而是工程思维：能不能把复杂的业务问题，拆解成可落地的技术方案；能不能在效果、成本、稳定性之间，找到最优的平衡点；能不能接受技术的局限性，用多路径兜底解决问题。

## 四、初创公司AI平台搭建，到底要做什么？别再做重复的RAG玩具了
面试的最后，候选人问了两个核心问题：公司的业务流程是怎样的？算法团队有多少人？

面试官的回答，代表了2026年绝大多数初创公司做AI平台的现状：团队正在从头构建，预期只有几个人，核心目标不是做PM产品，而是搭建自研的AI平台。

这里我必须泼一盆冷水：90%的初创公司做AI平台，从一开始就走错了方向。

很多人对AI平台的理解，就是做一个封装了RAG、Agent的低代码工具，结果做出来的东西，和市面上的开源产品没有任何区别，既没有壁垒，也没有业务价值。

而面试里面试官提到的AI平台，才是初创公司应该做的正确方向：**AI平台的核心，不是做一个通用的工具，而是做贴合自身业务的AI基础设施**。

一个能给业务创造价值的AI平台，核心能力应该分为四层：
1. **数据层**：统一接入各个业务系统的结构化、非结构化数据，做数据治理、数据血缘、特征存储，解决“数据孤岛”的问题。这是AI平台的核心根基，没有统一的数据，所有AI能力都是空中楼阁；
2. **模型层**：提供AI基础能力，包括模型推理、微调、知识库管理、Prompt工程、Agent编排，解决“AI能力复用”的问题，不用每个业务系统都重复造轮子；
3. **开发层**：提供标准化的开发框架、SDK、API网关，让业务团队能基于平台快速开发AI应用，解决“开发效率”的问题；
4. **应用层**：基于平台能力，开发面向业务的具体应用，比如数据分析、数据报表、数据预警、智能问答，直接给业务创造价值。

初创公司做AI平台，最忌讳的就是“大而全”，上来就想做一个对标阿里云、百度智能云的通用平台。正确的做法是：**从业务痛点出发，先解决一个核心问题，再逐步沉淀成平台能力**。

比如面试里的公司，核心业务是PM产品，那AI平台的第一步，就应该是先解决业务系统的数据打通问题，再做数据分析和预警，最后再沉淀通用的AI能力。只有这样，AI平台才不会变成一个没人用的玩具，而是真正能驱动业务增长的引擎。
